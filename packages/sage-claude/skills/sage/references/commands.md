# The common commands

Each row gives a command of the sage state tool and its full rules. Run each as the sage skill says: node, the state tool's absolute path and the command, without quotes.

| Command | Does |
| --- | --- |
| `init` | Makes the project's logbook and its standing orders. A new logbook has each table with only its header line. `init` writes tasks.tsv last, so a folder with tasks.tsv has every table. On an existing logbook it makes no table: a lost one refuses (see "The logbook check"). It adds the logbook's folder to the known project list, `projects.tsv` in the sage root, under the root's lock; it never removes a line. It checks the list and takes the root's lock before it writes the logbook, so a refusal there (a busy lock, a damaged or missing list) makes nothing. |
| `standing` · `standing add "<order>"` | Prints the standing orders as written, or adds one. Every agent reads them before it starts: a brief's STANDING field points to this command, and does not copy the orders. Tabs stay, CRLF line ends print as plain lines, and hidden characters are removed (see "Hidden characters"). |
| `task add --title "<t>" --size tiny\|small\|large\|investigate [--risk auth,data,schema,money,secrets,input] [--add <blocks> --why "<reason>"] --priority P0\|P1\|P2\|P3 [--kind <kind>] [--waits <T,T>] [--milestone <M>]` | Frames a task and its route. The size gives the least route. A risk adds the security review. `--add arena` on a tiny task also adds the code review, because a judge's graft is new code that nobody read. An investigation takes no build block: a build that it needs is its own task. Every task needs a priority, and `task add` refuses without one, with the scale: P0 the owner's current focus and what blocks it; P1 next: function or safety bugs, work in flight, pre-pilot items; P2 later: polish, hardening lows, follow-ups; P3 parked but kept. Give each task its priority on this scale. The kind is optional. The board shows both as tags on the task's card. A kind is one of: design, ui, orchestration, optimization, bug-fix, logbook, docs, security, providers, checks. Choose the task's main one. Another value refuses, with the list. |
| `task <T> set priority=P0\|P1\|P2\|P3` · `task <T> set kind=<kind>\|none` | Sets the task's priority, or sets or clears (`none`) its kind, from the lists of `task add`. An open task's priority does not clear: only a merged, concluded or abandoned task takes `priority=none`. An older task with no priority still works: `status` names the open ones, the board marks each card "no priority", and you set one. A follow-up task of `finding move` gets P2. |
| `task <T> set waits=<T,T>` · `waits=` (or `waits=none`) | Sets or clears the tasks that this task waits for: task ids of this logbook, separated by commas or spaces (`waits=T7,T9`). A wait is met when that task is merged or concluded; an abandoned task never meets it, so remove or change the wait, or ask the user. While a wait is unmet, the task takes no lead, implementer, investigate or arena-judge run and no `state=building` or `state=merged`, and the merge check refuses it; its designer and pe runs, and review and QA runs, go on. A wait on a task of the same pull request (`--pr`, or else the same recorded PR) is met at the merge check when that task passes too; a task of another pull request, or an abandoned one, never meets it. When the waiting task is not on that pull request, the refusal names the `pr=` to set. The tool refuses a word that is not a task id, a duplicate, the task itself, more than 20 tasks, a task that the logbook does not have, and a loop (it names the loop: T8, T9, T8). Each change writes a decision row (`waits <old> → <new>`). `task <T>` and `status` show each wait with its task's state, and which are unmet. |
| `config start=sage-mode\|normal` | Sets the start key of the project's own logbook, in a config command of its own. `start=sage-mode` starts each new session of the project in sage mode, from any checkout of the project, in Claude, and in Codex too when the two share the logbook; `start=normal` (the default) starts it with sage mode off. The off phrase still turns sage mode off for the rest of that session. Run it only when the user asks for it. |
| `config name="<name>"` · `config archived=yes\|no` | Sets a key of the project's own logbook, in `config.json` of its logbook folder (not the config for all projects). `name` is the project's name on the board: 1 to 60 characters, with no space at an end or two together, and no control, format or hidden character (a tab, a line break, a zero-width space, a right-to-left mark). `name=` alone removes it. Without a name, the board shows the repository name of the checkout's `upstream` remote, then of `origin`, then the main checkout's folder. `archived=yes` folds the project into the board's Archived group: its tasks leave the columns. `lint_offer=never` stops the lint offer, and `lint_offer=ask` brings it back. Set these keys in a config command of their own. Run it only when the user asks for the name or the archive. |
| `task <T> set state=<state> [branch=<b>] [pr=<n>]` | Moves the task. The tool refuses a move that the design does not allow, and "verifying" or "concluded" while a finding is open. A PR number is only digits, with no leading zero. A branch (here and in `run add --branch`) is letters, digits and `. _ / -`, such as `claude/t12` or `tool/t12-short-name`: not main, master, HEAD or `refs/…`, and not a name that starts with `-` or holds `..` or `@{`. In `task set` it must also be a branch of that task, `[<prefix>/]t12[-<words>]`, or the branch that another task of the logbook names, so that two tasks share one pull request. `branch=` clears it. An investigation takes no PR number; `pr=` clears one. Each change of a build's PR writes a decision row (`PR <old> → <new>`, with `none` for no PR). `--why "<reason>"` goes only with `state=abandoned`, and the abandon's decision row keeps it. |
| `round <T> [--why "<reason>"]` | Starts a repair round on the open findings marked fix, also on low findings only, and names the roles to re-run on the repair's diff: the sources of those findings. After the last round, or when a round did not fix its findings, it holds or re-plans the task. With autopilot on, `--why` gives the chief one more round past `max_rounds`, up to 5 in all (below). |
| `run add <T> --role <role> [--branch <b>] [--candidate <k>]` · `run done <R> --status done\|blocked\|question\|failed [--tokens <n>] [--report <path>]` | Records an agent run. A done review, QA or evidence-review run needs `--tokens` with its tokens as a whole number. A lead run that ends with a report (`done`, `blocked` or `question`) needs `--tokens` too: the `subagent_tokens` of its notice. When its notice gave no usage (for example after a restart), end it with `--usage unavailable --usage-source "<source>" --usage-evidence "<reason>" --report <path>`. A lead with no report ends as `failed`, without them. A run ends once: a later `run done` of an ended run, with the same `--status`, only adds the `--tokens` or the `--report` that it lacks (a re-plan ends a run with neither); it never replaces a value, and any other call is refused. The role is one of lead, implementer, pe, designer, arena-judge, code-reviewer, security-reviewer, ux-reviewer, qa, investigate and evidence-review; it is read in lower case, without spaces or hidden characters at its ends (`Lead ` is lead), and any other role is refused. One writer (implementer, designer, arena-judge) per branch: finish the running one first, or use another branch. A branch name in another letter case is the same branch. An arena-judge run needs `--branch`, and its branch differs from each candidate run's branch for good, also after a run ends. A candidate's branch stays its own: no other run that writes takes it, not another candidate (also one with the same number on another task or role) and not a run with no number; only the same candidate of the same task and role may run on it again. While a task's arena step is open (its route has the arena block or it has a candidate run, and no arena-judge run of it ended done), an implementer or designer run needs `--candidate`, a whole number from 1. After that, a repair needs no number. An implementer is no candidate of a large task before briefed: its arena is a design arena. A build route with no code review takes no candidate: frame the task with `--add arena`. The refusal of an open step names the way out: finish a judge, or for a task that needs no arena, abandon it and frame it again. An abandoned task has no open step. A lead run (`--role lead`) needs a task with a build that is not concluded, merged or abandoned (the refusal names the state; a verified task takes one): a task has at most one running lead run, and the project at most `max_leads` (default 5), and each refusal names the running lead runs. A lead run of a task that waits (its waits, or its milestone's pilot) prints `upstream reports:` with the report of the last lead or investigate run of each such task, or `no report recorded`: put each report in full in the lead's CONTEXT. `run add` prints the model of the run (`R12 running · qa on T3 · model sonnet`) and records it in the runs column `model`: pass it as the `model` of the agent call. No model on the line means the agent's own model: pass none. An arena candidate `<k>` takes the k-th model of arena_models; any other run with a risk flag first takes `model.<role>.risk`, then `model.<role>.<size>` (the task's size), else `model.<role>`. |
| `finding add <T> --source <role> --severity high\|medium\|low --summary "<s>" [--key <K>] [--run <R>] [--class <class>]` | Records a finding. A known key opens it again, with the new severity, source and summary; the decision trail keeps the old summary. Without `--summary`, a known key keeps its summary; an empty one is refused. Without `--key`, the finding gets a new key. `--run` is the run whose report holds the finding: a run of the same task. `--class` is the problem class: state-edge, speed, copy, layout, security or other. A finding whose source is a review or QA role (code-reviewer, security-reviewer, ux-reviewer, qa or evidence-review) needs both, given or kept by its known key; the refusal names the classes. Another source, such as the sage's own note, may leave them out. A lead's `--run` is a run of its own task. |
| `finding triage <T> <K> fix\|dismiss\|ask [--reason "<r>"]` · `finding close <T> <K>` | Triage every finding. A dismissal needs its reason. A low fix key of the current round is not dismissed while a medium or high finding of the task is open, in any triage and any state: it joins the next round with it. Close a fix after a review confirms it, also a finding that `finding move` brought in: its lead closes it like any fix finding, after a re-check of a round confirms it. A closed finding is not dismissed. |
| `finding move <T> <K> --to "<title>" [--size tiny\|small\|large]` · `finding move <T> <K> --into <T>` | Moves an open medium or low finding to a new follow-up task (small by default), which it frames, or with `--into` into an open task (not merged, concluded or abandoned) of this logbook; in a shared logbook, a task of your own. `--into` takes no `--to` and no `--size`, and `--to` refuses a task id (such as `T12`): it names `--into`. The finding gets the task's key and arrives triaged fix, with the reason "moved from <K>": it needs no proof check there, because the proof belongs to the task it came from. The decision trail records the move. A high finding cannot move: it blocks its task until it is fixed. A fix key of the task's current round moves, at any severity and in any state, only after the owner's answer: a gate of the task whose question names the key as a word (`gate add <T> --question "Move <K> to a follow-up task?" --options "move\|keep"`) and whose answer is its first option. Else it is fixed in a round or dismissed with a reason. |
| `verdict <T> --sha <sha> --kind <kind> [--cycle <n>] [--pr <n>] [--run <R>]` | Records a verdict on a head SHA. Give the full 40-character SHA (`git rev-parse <branch>`): a short one is refused, and capitals are the same SHA. A task without a build block records its verdicts without `--sha`. Kinds: checks-pass, review-clean, security-clean, ux-clean, qa-pass, evidence-clean, checks-fail, findings, qa-fail. Record the findings first: `findings` and `qa-fail` need an open medium or high finding, and their refusal says to record it first. On a task with a build, a review or QA verdict needs `--run`: a done run of the task, of the role that gives the kind, whose helper's report the hook kept at its stop (a helper whose name is its run's id). A clean report backs only a clean kind. A report with a medium or high finding backs `findings` or `qa-fail`, and a clean kind only after each of those findings is recorded with that `--run` and dismissed, moved or closed. One run backs one verdict, on the commit that its report names. The tool refuses any other, in every shell form. A `findings`, `qa-fail` or `checks-fail` verdict moves a verified or pr-ready task back to reviewing, prints that state and records the reason in the decision trail. |
| `gate add <T> --question "<q>" --options "<a\|b>" --recommend <a> [--default <a>] [--message <file>]` · `gate answer <G> --option <n> --via <place> --project <folder>` · `gate answer <G> --other-hex <hex> --via <place> --project <folder>` · `gate undo <G>` | Parks a question for the user, with your recommendation and the default. `--message` is the JSON file of the question's message: the gate keeps it as `gates/G<n>.json` after the message check, so that the board shows the whole question. `--via` is where the user answered: `claude-card`, `chat` (the default), `codex-card` or `board`. The first answer wins: a gate with an answer refuses, and names that answer, its place and its time; tell the user which answer counts. In a shared logbook, add `--chief C<n>` when this session is a chief of the gate's logbook (the hook names it): the gate records the chief that applied the answer. A board answer acts only when its chief's hook picks it up, and `gate undo` (the user's act, only when the user asks) takes it back before that. A breakdown gate keeps its own rule. The question is one line: each line break in it becomes a space. Only a breakdown gate's question has lines. The recommendation and the default are options, by text or number; options that differ only in case or hidden characters are refused. The answer is the number of an option as the board shows it (1, 2, …), never its text, so no agent-written text goes into a command. For the user's own words, use `--other-hex` with the UTF-8 bytes of the words in lower-case hex, so that the command holds only 0-9 and a-f; the gate keeps them as `other: <words>`. An option may not read as `other:`, also with other case, width, hidden characters or a space before the colon. Give the `--project` of the gate's own project: two projects can each have a G1. `init` and `task add` write the project's folder to `checkout.txt` in its logbook, so a session of another project can answer its gates. |
| `log <T\|-> "<decision>" --why "<reason>"` | Adds a line to the decision trail. Put the id that the decision is about first ("R1 stopped by hand"): only the first word counts as an id, so an id later in the text can come back. |
| `pages <T>` · `pages <T> record <file>` · `pages <T> record --run <R> --text <report>` | Makes (mode 700) and prints the folder where agents save the task's pages (research, designs, findings pages): `~/sage-worktrees/<project>-<hash>/pages/<T>/`, under the logbook's own folder name, so two projects with the same name never share it (`$SAGE_WORKTREES` overrides `~/sage-worktrees`). It is outside the logbook, so a sandboxed agent may write there. `record` adds the page's path and sha256 to the decision trail; the file must be a regular file of at most 16 MiB in that folder, not a link, a named pipe or a device, and its name has no control character (a tab or a line break). `--run` and `--text` save a run of the task's report as `<R>-report.md` in that folder (once) and record it, for a chief that cannot write the folder. Give that folder in the brief of each agent that saves a page. |
| `message <T> --file <json>` · `message <T> --json <json>` | Prints a message to the user from its JSON, in its kind's shape (the presentation skill lists the kinds, their parts and the blocks). A message with a picture, or a long message, also gets its page: one self-contained HTML file in the pages folder of `<T>`, named by its kind and a hash, and the text ends with its Page block. A Page block in the message names a page as `{ "t": "page", "title", "task", "file" }`, a file that exists in that task's pages folder. It refuses a message that is not in its kind's shape, with each problem. The JSON is at most 1 MiB; write it in your temp folder first. |
| `board [this\|all\|<project>\|<T>] [--view chat\|task\|status\|html]` · `board --name-hex <hex>` | Prints the board. `--view chat` (the default) is the chat board in Markdown: what needs the user, the agents at work, each task in its column, and Done for the last 7 days. `task` shows one task (`board T7 --view task`), `status` the short status lines, and `html` the board page as one HTML file. `this` (the default) is the session's project, `all` every project, and a name that project. `--name-hex` gives the name as the hex of its UTF-8 bytes. It reads every logbook, takes no lock and writes nothing. The hook's note for a board phrase gives the exact command. |
| `stats [--task <T>]` | Prints a guide line, a total line with the count of done review runs that have no tokens, and one table of the 50 tasks with the most review tokens, largest first: for each task, its review and QA runs, their tokens in thousands (done runs only), the tokens after round 0 (its runs of repair round 1 or later), its repair rounds, and its findings by role and by cycle (the cycle of the verdict of the finding's run in its task's ledger rows; none without one). A last line counts the tasks that the table does not show. With no review runs and no findings, it prints "No review runs yet." It reads only and takes no lock. |
| `worktrees` · `worktrees prune --yes` | Lists the git worktrees of the project's repository, one line each: the path, the branch (or `detached` and its short commit), the task, the task's state and one reason. The reason is `merged`, `concluded` or `abandoned` (the task of the worktree), `branch merged` (no task, and a merge brought the branch's own commits into origin/main), `open` (a task in any other state) or `unknown` (no task, and the branch is not in origin/main or adds no commit to it, or no branch). A branch on the first-parent line of origin/main, such as one at its tip, adds no commit: a new run starts there. A worktree matches a task only through the logbook: the `branch` of the task's row, or of a run of the task, never the number in a branch's name. It reads the local origin/main, prints its commit, and does not fetch. `prune --yes` removes each worktree whose reason is merged, concluded, abandoned or branch merged, with `git worktree remove` and no `--force`, and prints each path that it removes or keeps, with the reason. It keeps the primary checkout, the worktree of the current folder and of `--project`, a locked worktree, a worktree that holds another worktree (git would delete it with its ignored files), and one with uncommitted changes, untracked files, ignored files or folders (git would delete them, such as `.env` or `secrets/`; the reason names them) or unpushed commits. Only an ignored `node_modules` or `dist` folder, at any depth and also as a link, keeps no worktree (a regular file with that name keeps it): a package install or a build makes it again, so the prune deletes it and names it on the removed line (`also deleted ignored node_modules/`). A commit is pushed when a remote-tracking ref holds it, or when it is a verdict SHA of the task in the ledger or an ancestor of one (a squash merge leaves the task's commits out of origin/main). It runs `git worktree prune` for the entries whose folder is gone, and deletes no branch. Run the listing first and show its paths; only the chief runs either form. From pstack's worktree audit playbook. |
| `status` | Prints the status lines. Each change also writes them to `status.md`. End each report to the user with them. When an open task has no priority, a `priority` line names it (up to ten), for example `priority 12 open tasks have none: T3, T7, … · set them with task <T> set priority=<P0 to P3>`. Then one line for each release and one for each milestone: see `milestones.md`, which also has the release commands `release add`, `milestone <M> set release=` and `task <T> set release=`. |

## How an investigation ends

- An investigate task has no build block, so it ends at `concluded`, not at verified. Its last states are reviewing → verifying → concluded.
- `concluded` needs no open findings, and the task's latest verdict must be `evidence-clean`. Record it with `verdict <T> --kind evidence-clean --run <R>`, without `--sha`.
- A task with a build block cannot use `concluded`.
