# The sage state tool

The chief of staff keeps the work in the project's logbook, not in the conversation. Then a session on the phone or the desktop can continue it. Each command prints one line. A refused command prints the reason and exits with 1: do what the reason says, and do not work around it.

Run it as `node ${CLAUDE_SKILL_DIR}/sage.mjs <command> --project <path to the project>`: node and the absolute path, without quotes. In the sandbox, only this form runs outside it; a quoted path, a variable, a `cd … &&` or a pipe stays inside, and the logbook write fails.

Only the chief writes the logbook. The sage hook lets an agent run only `status`, `merge-check`, `logbook`, `standing` and `config` without `key=value`: `node <path>/sage.mjs <command> [--project <path>]`, with the copy of sage.mjs that the hook loads, also in a pipe or a chain. The hook judges the programs that a command line runs (T815): `node` or the script itself that runs `sage.mjs` or `sage-pr.mjs`. Any other program may read their files. The hook refuses an agent's file change under the sage root in any case or Unicode form, and an agent's shell write whose literal path is in the sage root or the shared root: a word of a program that is not a reader (`cat`, `grep`, `echo`, `jq` and the like), the value of a `key=value` or an `--option=value`, or a redirection's target, resolved from the program's folder (also after a literal `cd`, `pushd` or `popd`, and `~` as the home folder) as written, not through a link (so `rm` of a link to a root removes the link and passes), or a word whose text holds a root's path. A pattern counts by its literal part, the text before its first `$`, backtick or pattern character, so `rm dist/*` and `jq ... > config.json` pass in a project. A remove or a move (`rm`, `mv`, `rsync --delete`) of a folder that holds a root is refused too, also by a pattern in it (`rm -rf ~/.claude`, `rm -rf ~/*`). A refusal names the word that caused it, in the command's own capitals. When the hook cannot read a line, it refuses it only when its text names a merge, a push, the state tool, `gh`, `git stash` or a process program. When the hook cannot check an agent's call, it refuses it. A variable, a substitution, a path through a link, code (`node -e`, `python -c`), a script and text piped into a shell can still build a path or a command while the line runs: that is a limit of the hook, and the sandbox (tasks T94–T99) is the full guard.

Only sage.mjs changes the logbook, so that each change leaves its record. The hook refuses the chief's Write, Edit, MultiEdit and NotebookEdit under the sage root, in any mode. It also refuses the chief's shell write (a redirection to a file, `cp`, `mv`, `rm`, `sed -i` and the like) whose literal path is in the sage root or the shared root, by the rule above for an agent. A logbook file's name elsewhere (`tasks.tsv`, `config.json` in a project) passes. The state tool passes, and so does a read of the logbook, also in a pipe or a chain. The user's own `!` commands are not hook events, so the user can still change a logbook file by hand.

Each option takes a value: `--name value`, or `--name=value` for a value that starts with `--`. A command refuses an option that it does not take, and names the options that it takes. It refuses an option given twice.

In a shared logbook, each write names its actor: the chief adds `--chief C<n>`, and a lead adds `--lead R<n>`, its own lead run. The hook names the id at the first write and refuses another chief's id, also when a value is in quotes. It reads a write that is one command of its own: after `cd` or in a pipe, it names no id. A write on a task of another chief refuses and names that chief. So does `sage-pr create` or `merge`, as one command of its own: the hook checks the session's chief, because the script reads no session. A command with no chief only reads. A legacy logbook refuses both options, `claim`, `offer`, `cancel`, `accept`, `release` and `gate replace`.

## Commands

| Command | Does |
| --- | --- |
| `init` | Makes the project's logbook and its standing orders. A new logbook has each table with only its header line. `init` writes tasks.tsv last, so a folder with tasks.tsv has every table. On an existing logbook it makes no table: a lost one refuses (see "The logbook check"). It adds the logbook's folder to the known project list, `projects.tsv` in the sage root, under the root's lock; it never removes a line. It checks the list and takes the root's lock before it writes the logbook, so a refusal there (a busy lock, a damaged or missing list) makes nothing. |
| `link --to <folder>` · `link --separate` | Run it only after the user's answer in the chat. `--to` adds a row for this checkout to `bindings.tsv` in the shared root, for a logbook of that root. `--separate` makes a new shared logbook and a row. The folder name stays `<slug>-<6 hex>` and is saved in the row. A retry changes nothing. A project with a legacy logbook in either provider root refuses, because a link would hide its tasks: only the move takes it over. A logbook belongs to its oldest row with first commits whose checkout is still on the disk, or its oldest such row when all are gone. A checkout with no row and no logbook, with the first commit of a shared logbook (a moved checkout, a clone or a fork), refuses every command and `init` and names the link; only the first-commit call on the way to that refusal runs at a read. A `--to` to a logbook whose owner has no first commit in common with this checkout refuses; a shallow clone needs `git fetch --unshallow` first. A row that names a missing folder, or a row with no first commit in common with the owner, refuses every read and write of that checkout only, and link replaces that row. The first-commit call is the hardened local read. A timeout, or a repository that Git cannot read, refuses and makes no row. Only a HEAD with no commit yet, or a folder with no `.git` entry in it or above it, has no commits. An unwritable shared root, or a provider root that link cannot read, refuses and names the path. A damaged `bindings.tsv`, or a missing one that `bindings.made` says sage made, refuses every project, and sage never falls back to a legacy logbook. The shared root is the launcher's option, `SAGE_SHARED_HOME` (an absolute path), `<SAGE_HOME>/shared`, or `~/.sage`. For a shared project, `cycles.*` and `max_rounds` live in the shared root's `config.json`: the first shared write takes the largest value of the provider roots, and a later link leaves them. Model keys, `arena`, the caps and `.hooks` stay in the provider root. |
| `move --preview` · `move --plan <plan>` · `move --gate <G>` | The move of an existing project into one shared logbook, when the user asks for it. 1. `--preview` only reads: show its print to the user as it is. It refuses, with nothing changed, while a run runs, while a provider's plugin is below contract 2, or when a folder cannot be written. Then start no new run in the project, and tell the user what the refusal says. 2. `--plan <plan>` with the 8 hex of the preview's plan opens the move gate in this logbook and prints it: put it to the user word for word, with your recommendation. It refuses when the logbooks changed since the preview. 3. After the user's answer (`gate answer`), `--gate <G>` moves: it checks the plan again under the locks, then prints six steps, the end check by table and provider, the map page, the backup paths and the restore steps by hand. Give the user the end check, the map, the backups and the restore steps with the warning first. A plan that no longer matches moves nothing and says what changed: show a new preview and open a new gate. A move gate answers once; keep moves nothing. While a move's plan is saved, every command of the project in either provider refuses and names `sage move --gate <G>`: run it at once, from any checkout of the move (the user's answer covers it), and tell the user. An end check that does not match names no command: show the user the missing records and the steps to set the plan aside, start no work in the project, and wait for the user. The move takes the open tasks of the Claude and Codex logbooks of the repository, also of its clones, with new numbers (Claude's first) and an adoption record of version 2 that keeps each branch and PR. Each moved task starts unclaimed; one in verifying, verified or pr-ready returns to reviewing. Runs, verdicts and kept reports stay in the old logbooks, which become read-only. Writes the user's "unused" answer for a provider with no row in `plugins.tsv`: then the gate offers that answer in place of a plain move. |
| `claim <T> --version <version> --chief C<n>` | Shared logbook only. Gives a task with no owning chief to this chief. A write on such a task refuses and prints this command, with the version. A task that changed, or that another chief claimed first, refuses. A chief claims only a task that it released itself, or, after the move, a task that its own provider started: a task that another chief released last, or that the move brought from the other provider's logbook, refuses and names the takeover gate. Any chief abandons a task with no owning chief with no claim: `task <T> set state=abandoned --why "<reason>" --chief C<n>`, with that state alone. The task keeps no chief, and the decision row keeps the reason and the chief. |
| `offer <T> --to C<n> --chief C<n>` · `cancel <T> --offer <id> --chief C<n>` · `accept <T> --offer <id> --version <version> --chief C<n>` · `release <T> --chief C<n>` | Shared logbook only. `offer` names one other chief, and the owning chief stays until that chief accepts. A task has one open offer. `offer` and `task <T>` print the offer's id and the version. `cancel` clears the exact open offer, also while a run is active, and a cancelled offer never becomes valid. The chief that the offer names runs `cancel` to decline it: the line says that it declined, and the owning chief keeps the task. `accept` does not take the task: it opens a takeover gate from the owning chief to the named recipient, and the owner's answer approve gives the task, as for `gate replace`; the answer decline ends the offer. A second accept prints the open gate and opens no other. Its line ends with the next step: ask the owner to answer the gate. It needs the exact open offer, the current version and no active or unknown run. A run that ends changes no task, so the recipient still accepts, and a transfer changes no run. `release` clears the owning chief, and only that chief claims the task back; another chief takes it through the takeover gate. It needs no open offer and no active or unknown run. Its work and reports stay. |
| `gate replace <T> --to C<n> --chief C<n>` | Shared logbook only. The takeover gate: the owner gives a task to another chief, in either direction between Claude and Codex, and no chief takes a task from another chief without it. Any chief opens it for a task of another chief, for a task with no owning chief that it may not claim, for an owning chief that stopped, or for a session that `/clear` made a new chief. `accept` opens the same gate. A gate that is open already for the same task and chiefs is the one: no second one opens, and the line prints it. It has the options approve and decline (a gate of an older sage has replace and keep, and still answers). Its question asks "Hand <T> and PR <n> from <chief> to <chief>?": it names the task, its PR, the owning chief (or the chief that released the task, or the logbook that the move brought it from) and the new chief with their providers, each active or unknown run with its role, what each answer does, that the branch keeps its name, the PR its number and the verdicts stay, and, last, the task's title. When a Claude chief takes a task from a chief of another provider, the question says that it runs one fresh cycle before it merges, and the merge check and the board keep that rule: the cycle counts only the verdicts of review and QA runs that started after the owner's answer. It is the only way to take a task with no consent from its chief. Each line that opens it ends with the next step: ask the owner to answer it. The owner's answer goes through `gate answer`, as for every gate. A chief never answers a takeover gate by itself: only the owner's answer counts. This rule is an instruction, not a check. Option 1 sets the chief, clears an open offer and ends each of those runs as failed, in one write. It refuses when the owning chief changed, or when a new run started: answer decline, then open a new gate. Decline and the owner's own words change nothing, and the line says so: `nothing replaced`, the task keeps its chief, and the gate is spent. A decline of a gate that `accept` opened also ends that offer in the same write: its question and the line say so. Never report a replacement from that line. A takeover gate answers once. When another worktree of the repository holds the task's branch, the answer's line names it and the one safe command that frees it (`git -C '<worktree>' switch --detach`, the path quoted for a POSIX shell, never `--force`), then says that the new chief checks out the branch in its own worktree. A path with a control character gets no command: the line says to find the worktree with `git worktree list`. The replaced chief gets a refusal that names the new owning chief. A run that ended as blocked or failed keeps a late report once, with its arrival time, and `task <T>` prints its path. That report backs no verdict. |
| `projects rebuild --accept-listing yes` | The owner's act, so it names no chief, also on a shared logbook. Writes the known project list of this project's logbook root again: each folder of that root with tasks.tsv or ledger.tsv (`how` is `rebuild`), and prints each one. Run it only when the user asks for it, and show the user the listing: a folder that no project uses may be forged, so the user removes it and runs the rebuild again. A `projects.tsv` that is a folder refuses; a link is replaced by a regular file. |
| `logbook` · `logbook repair --accept-loss <table>[,<table>...]` · `logbook repair --accept-change-loss yes` | Prints the logbook's folder. `repair --accept-loss` starts each named table that fails the logbook check again, without rows. Run it only after the user accepts the loss of their rows. Name every damaged table in one command, joined by commas (`--accept-loss tasks,ledger`): a repair refuses when another table fails too, and names the command with both. The old file stays beside each as `<table>.tsv.lost-<n>`, and the decision trail records each repair before the table starts again. A named table that passes the check refuses the whole command. `repair --accept-change-loss yes` is the way past a saved change that cannot finish (see "A saved change that cannot finish"). After the owner accepts the loss, the chief runs it, or the owner runs it in a terminal when the chief cannot. In Codex, the chief cannot. On a shared logbook each form of `repair` names no chief, because it is the owner's act. |
| `standing` · `standing add "<order>"` | Prints the standing orders as written, or adds one. Every agent reads them before it starts: a brief's STANDING field points to this command, and does not copy the orders. Tabs stay, CRLF line ends print as plain lines, and hidden characters are removed (see "Hidden characters"). |
| `task add --title "<t>" --size tiny\|small\|large\|investigate [--risk auth,data,schema,money,secrets,input] [--add <blocks> --why "<reason>"] --priority P0\|P1\|P2\|P3 [--kind <kind>] [--waits <T,T>] [--program <PG>]` | Frames a task and its route. The size gives the least route. A risk adds the security review. `--add arena` on a tiny task also adds the code review, because a judge's graft is new code that nobody read. An investigation takes no build block: a build that it needs is its own task. Every task needs a priority, and `task add` refuses without one, with the scale: P0 the owner's current focus and what blocks it; P1 next: function or safety bugs, work in flight, pre-pilot items; P2 later: polish, hardening lows, follow-ups; P3 parked but kept. Give each task its priority on this scale. The kind is optional. The board shows both as tags on the task's card. A kind is one of: design, ui, orchestration, optimization, bug-fix, logbook, docs, security, providers, checks. Choose the task's main one. Another value refuses, with the list. |
| `task <T> set priority=P0\|P1\|P2\|P3` · `task <T> set kind=<kind>\|none` | Sets the task's priority, or sets or clears (`none`) its kind, from the lists of `task add`. An open task's priority does not clear: only a merged, concluded or abandoned task takes `priority=none`. An older task with no priority still works: `status` names the open ones, the board marks each card "no priority", and you set one. A follow-up task of `finding move` gets P2. |
| `task <T> set waits=<T,T>` · `waits=` (or `waits=none`) | Sets or clears the tasks that this task waits for: task ids of this logbook, separated by commas or spaces (`waits=T7,T9`). A wait is met when that task is merged or concluded; an abandoned task never meets it, so remove or change the wait, or ask the user. While a wait is unmet, the task takes no lead, implementer, investigate or arena-judge run and no `state=building` or `state=merged`, and the merge check refuses it; its designer and pe runs, and review and QA runs, go on. A wait on a task of the same pull request (`--pr`, or else the same recorded PR) is met at the merge check when that task passes too; a task of another pull request, or an abandoned one, never meets it. When the waiting task is not on that pull request, the refusal names the `pr=` to set. The tool refuses a word that is not a task id, a duplicate, the task itself, more than 20 tasks, a task that the logbook does not have, and a loop (it names the loop: T8, T9, T8). Each change writes a decision row (`waits <old> → <new>`). `task <T>` and `status` show each wait with its task's state, and which are unmet. |
| `program propose --name "<name>" --goal "<goal>" --pilot <T> --tasks <T,T>` · `program propose <PG> [--name "<name>"] [--goal "<goal>"] [--pilot <T>] [--tasks <T,T>\|none]` | Writes a program (`PG1`, `PG2`, …) for a request of two or more tasks with one goal. Frame every task first, then propose once: it puts the pilot and the other tasks (`--tasks`) in the program and opens the breakdown gate on the pilot task (options approve, change, drop; recommendation approve). The board shows it under "Needs you". The gate's question has one part on each line, with no quotes: the fixed first line `Approve program PG1? No task builds before you approve.`, then `Name: <name>`, `Goal: <goal>`, `Pilot, runs first:` with the pilot, and `Then, each after T1:` with each other task, one on each line as `  T2: <title>`. A task's waits other than the pilot, or an ended task's state, come in brackets after its id, before the colon, for example `  T3 [waits for T2]: <title>` or `  T4 [merged]: <title>`, so a title cannot pass for them. A title, name or goal prints as written, but each line break prints as a space, hidden characters are removed, and spaces are single; an empty title prints as `(no title)`. So no text adds a line. The `status` line of each program puts the name last, after `name:`. The `status` gates line shows a breakdown gate's first line and its count of tasks, only for the gate that the program's row names, on its pilot, with the options approve, change and drop (any other gate shows on one line, whatever its text), for example `G1 Approve program PG1? No task builds before you approve. (breakdown, 3 tasks)`; the board shows the whole question. The program's state comes from the answer of that gate, on the pilot task: proposed while it is open, active after approve, dropped after drop, changing after change or the user's own words (they say what to change). Any other gate reads as lost. A breakdown gate (each gate whose question starts with that first line, also one that a newer round replaced) answers once: `gate answer` refuses a second answer, so a change of mind is a new proposal. Only `program propose` writes that line: `gate add` refuses a question that starts with `Approve program`, also after blank, mark or symbol characters, and with Cyrillic or Greek letters that look like its Latin ones. Any other gate takes a new answer. `program propose <PG>` proposes it again after change, or for a new pilot: a new gate whose first line says its round, for example `Approve program PG1 (round 2)? No task builds before you approve.` The round counts the program's earlier breakdown gates. Tell the user in the chat what changed. Without `--tasks` the program keeps its tasks (the old pilot too); with it, the list is the new one, and a task that it leaves out leaves the program. An ended task (merged, concluded or abandoned) stays in the program either way: it counts, and the question lists it with its state. The name is 1 to 60 characters, unique in the logbook (case and width do not count) and not of the form `PG<n>`; the goal is 1 to 300; both have no space at an end or two together and no control, format or hidden character. It refuses a pilot or task that has ended (for a re-proposal whose pilot ended, it asks for a new one with `--pilot`) or is in another program, a task that has started (past briefed, or with a lead, implementer, investigate or arena-judge run that runs), an open breakdown gate, a dropped program, and a loop, which it names with the wait to clear. When a proposal stopped before it wrote its gate, the same command finishes it, and writes the decision row of each task that it put in the program. A drop holds also after a loss of `gates.tsv`: the decision row of the user's answer says it. |
| `task <T> set program=<PG>` · `program=none` (or `program=`) | Puts the task in a program, or takes it out, for a task that joins later. Until the user approves the breakdown, no task of the program takes a lead, implementer, investigate or arena-judge run or a move to building, merged or concluded, and the merge check refuses it. After the approval, each task but the pilot waits for the pilot in the same way, until the pilot is merged or concluded: a pilot wait never passes in the same merge. Its designer and pe runs, and its reviews and QA, go on. The refusal names the fix: ask the user to answer the gate, propose again after change, propose a new pilot for an abandoned one, or take the task out of a dropped program. No task leaves a program before the user approves or drops it; the pilot stays until a new pilot is proposed (it may leave a dropped one). It refuses an unknown or dropped program, an ended task (merged, concluded or abandoned: it neither joins nor leaves a program, so its program keeps it in its count), a task that joins while the breakdown gate is open (its question does not name the task: ask the user to answer change, then propose again with `--tasks`), a started task that joins before the user approves the breakdown and the pilot is merged or concluded, and a loop through a pilot, which it names. A task joins while the user asks for changes: the next proposal names it. No task of the program changes its `waits=` while the breakdown gate is open, as its question shows them: ask the user to answer change, then propose again. No task of a program has or had a pull request of its pilot before the pilot is merged or concluded, as that pull request could never merge: in every state but dropped, `pr=`, `verdict --pr`, `program=` and `program propose` refuse it from either side, also for a PR that a task had before, and name the way out (another PR, or the task out of the program). A task that joins or leaves after the approval does so with no new gate: the line ends with `joins PG1 after the owner approved its breakdown: no new gate, so tell the owner` (or `leaves PG1 …`), and you tell the user. Each change writes a decision row (`program <old> → <new>`). `status` shows each program on its own line, with its pilot and progress, and its name last, for example `program PG1 · pilot T1: 2 of 4 merged · T4 abandoned · name: Codex support`: the count keeps every task of the program, and names each abandoned task. A program is done when each task that is not abandoned is merged or concluded (`program PG1 · done, 3 of 4 merged · T4 abandoned · name: Codex support`), a dropped one names the next step for its tasks that have not ended (`program PG1 · dropped: 4 tasks still in it, take each out with program=none · name: Codex support`), and a program whose pilot was abandoned says `pilot T1 abandoned: choose a new pilot, or drop the program`. |
| `config name="<name>"` · `config archived=yes\|no` | Sets a key of the project's own logbook, in `config.json` of its logbook folder (not the config for all projects). `name` is the project's name on the board: 1 to 60 characters, with no space at an end or two together, and no control, format or hidden character (a tab, a line break, a zero-width space, a right-to-left mark). `name=` alone removes it. Without a name, the board shows the repository name of the checkout's `upstream` remote, then of `origin`, then the main checkout's folder. `archived=yes` folds the project into the board's Archived group: its tasks leave the columns. Set these keys in a config command of their own. Run it only when the user asks for the name or the archive. |
| `task <T> set state=<state> [branch=<b>] [pr=<n>]` | Moves the task. The tool refuses a move that the design does not allow, and "verifying" or "concluded" while a finding is open. A PR number is only digits, with no leading zero. A branch (here and in `run add --branch`) is letters, digits and `. _ / -`, such as `claude/t12` or `tool/t12-short-name`: not main, master, HEAD or `refs/…`, and not a name that starts with `-` or holds `..` or `@{`. In `task set` it must also be a branch of that task, `[<prefix>/]t12[-<words>]`, the rule that the PR script checks, or the branch that another task of the logbook names, so that two tasks share one pull request. `branch=` clears it. An investigation takes no PR number; `pr=` clears one. Each change of a build's PR writes a decision row (`PR <old> → <new>`, with `none` for no PR). `--why "<reason>"` goes only with `state=abandoned`, and the abandon's decision row keeps it. |
| `round <T> [--why "<reason>"]` | Starts a repair round on the open findings marked fix, also on low findings only, and names the roles to re-run on the repair's diff: the sources of those findings. After the last round, or when a round did not fix its findings, it holds or re-plans the task. With autopilot on, `--why` gives the chief one more round past `max_rounds`, up to 5 in all (below). |
| `run add <T> --role <role> [--branch <b>] [--candidate <k>]` · `run done <R> --status done\|blocked\|question\|failed [--tokens <n>] [--report <path>]` | Records an agent run. A done review, QA or evidence-review run needs `--tokens` with its tokens as a whole number. A run ends once: a later `run done` of an ended run, with the same `--status`, only adds the `--tokens` or the `--report` that it lacks (a Codex native finish and a re-plan end a run with neither); it never replaces a value, and any other call is refused. The role is one of lead, implementer, pe, designer, arena-judge, code-reviewer, security-reviewer, ux-reviewer, qa, investigate and evidence-review; it is read in lower case, without spaces or hidden characters at its ends (`Lead ` is lead), and any other role is refused. One writer (implementer, designer, arena-judge) per branch: finish the running one first, or use another branch. A branch name in another letter case is the same branch. An arena-judge run needs `--branch`, and its branch differs from each candidate run's branch for good, also after a run ends. A candidate's branch stays its own: no other run that writes takes it, not another candidate (also one with the same number on another task or role) and not a run with no number; only the same candidate of the same task and role may run on it again. While a task's arena step is open (its route has the arena block or it has a candidate run, and no arena-judge run of it ended done), an implementer or designer run needs `--candidate`, a whole number from 1. After that, a repair needs no number. An implementer is no candidate of a large task before briefed: its arena is a design arena. A build route with no code review takes no candidate: frame the task with `--add arena`. The refusal of an open step names the way out: finish a judge, or for a task that needs no arena, abandon it and frame it again. An abandoned task has no open step. A lead run (`--role lead`) needs a task with a build that is not concluded, merged or abandoned (the refusal names the state; a verified task takes one): a task has at most one running lead run, and the project at most `max_leads` (default 5), and each refusal names the running lead runs. A lead run of a task that waits (its waits, or its program's pilot) prints `upstream reports:` with the report of the last lead or investigate run of each such task, or `no report recorded`: put each report in full in the lead's CONTEXT. `run add` prints the model of the run (`R12 running · qa on T3 · model sonnet`) and records it in the runs column `model`: pass it as the `model` of the agent call. No model on the line means the agent's own model: pass none. An arena candidate `<k>` takes the k-th model of arena_models; any other run with a risk flag first takes `model.<role>.risk`, then `model.<role>.<size>` (the task's size), else `model.<role>`. |
| `finding add <T> --source <role> --severity high\|medium\|low --summary "<s>" [--key <K>] [--run <R>] [--class <class>]` | Records a finding. ## Cycles and merges

- A cycle is one full set of fresh reviews and QA on one head SHA. Record each verdict with `--cycle <n>`.
- A cycle is clean when no medium or high finding of the task is open. A review or QA that found only low findings records its clean verdict, not `findings` or `qa-fail`: the tool refuses those without an open medium or high finding. An open medium or high finding blocks the move to verifying and the merge. An open low finding never blocks a merge; it stays on the task's polish list.
- A `findings`, `qa-fail` or `checks-fail` verdict blocks its SHA: repair, then review the new SHA. Triage can clear a `findings` or `qa-fail` verdict on its SHA: the verdict's run must link to at least one finding, and each finding of that run must be moved, or dismissed below high; an open low finding of the run does not count. A closed finding does not clear it, because a new head confirms a fix, and a dismissed high finding does not either. A `findings` or `qa-fail` verdict needs each medium and high finding of its run's report on record for that run first, at its severity or above. A cleared verdict stops the refusal only: the SHA still needs its clean cycles.
- A merge needs the task's clean cycles on its head SHA: 1 for every task (`cycles.small`), 2 for a large task (`cycles.large`), and 2 for any task with a risk flag (`cycles.risk`); the largest count that applies wins. A task with no review or QA in its route needs only checks-pass: a tiny task without a risk flag or an added review. Verified needs 1 for every task.
- A clean merge of main keeps the cycles. The merge check counts the clean cycles of an earlier head H1 of the task for the head H2 when all of these hold: each commit from H1 to H2 on H2's first-parent line merges a commit of `origin/main` with no conflict and no other edit (its tree is the tree of `git merge-tree` of its parents); the pull request's own diff, from the merge base with `origin/main`, has the same `git patch-id --stable` on both heads; checks-pass is on H2; H2 has no review or QA verdict of its own; and no commit between H1 and H2 (`git rev-list H1..H2`, also on the main side of a merge) has a review or QA verdict of the task, so a findings verdict on a middle head is never skipped. git reads each commit's own parents: it ignores replace refs, `info/grafts` and the commit-graph of the clone. It uses the earlier head with the most clean cycles, and says so: `cycles from <H1> carried to <H2>: clean merge of main, same patch-id`. In any other case, or when git fails, H2 needs its own cycles, and the refusal says why. Fetch origin first, so that `origin/main` has the merged main commits. The board's merge check reads git in the project's folder too, so the board shows the same carried cycles.
- A repair round re-runs only the roles that `round` names, on the repair's diff. The re-check confirms each fix (`finding close`) or opens the finding again; it records no verdict. Then the task needs its clean cycles on the final SHA, with every role.
- A new medium or low finding that a round raises goes to a follow-up task with `finding move`, not to another round. A high finding always blocks.
- With autopilot on, merge with `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`. The sage hook runs `merge-check` first and refuses a SHA that is not ready. It refuses every merge by an agent.
- A new commit is a new SHA. Its verdicts start again from cycle 1.
- Every task with verdicts on a SHA counts, also an abandoned one. When two tasks share a pull request, give both the same `branch=` and `pr=`, and record each verdict under both: autopilot merges it when each task passes on its own verdicts. Only the chief puts a task on a shared branch or takes it off one: a branch that another task names by its `branch=` or ran work on. To leave an old task's verdicts behind, push a new commit.

## What the hook refuses an agent

- `git stash` in any form, also with `-C` or `--git-dir`: every worktree shares one stash list. Use `git worktree add --detach <scratch> <sha>` or `git show <sha>:<path>`.
- A program that lists or signals processes (`ps`, `pgrep`, `pkill`, `kill`, `killall`, `lsof`, `top`), unless it resolves to a fake in the temp folder. Put a fake `ps` first on PATH that prints a start time in the past, and run a fake `kill` by its path. The chief is not limited.

## How an investigation ends

- An investigate task has no build block, so it ends at `concluded`, not at verified. Its last states are reviewing → verifying → concluded.
- `concluded` needs no open findings, and the task's latest verdict must be `evidence-clean`. Record it with `verdict <T> --kind evidence-clean --run <R>`, without `--sha`.
- A task with a build block cannot use `concluded`.

## Several sessions on one project

- Several chief sessions may share one project's logbook. Each command that changes the logbook holds its lock while it runs.
- A command waits up to 3 s for the lock. Then it refuses with `the logbook is busy: pid <n> on <host> has held <path> for <n> s`, or with `<path> has no valid owner file`. Nothing changed: run the command again.
- The next command clears a lock that a crashed command left. A lock from another machine, a live process that is not sage, or an odd owner file stays. Remove the folder in the message only when no sage command runs.
- The next command also removes the temp folder (`.lock.<id>`) of a command that was killed while it waited.
- `status`, `logbook`, `standing` and `merge-check` take no lock. They work while another command runs.
- The sessions may run two versions of sage. A version refuses to change a logbook whose tables have columns that it does not know: its write would lose them. The refusal says to update the sage plugin and restart the session, and that `status`, `logbook`, `standing` and `merge-check` still work.
- A command refuses, before any change, when status.md or standing.md is not a regular file, also a link to nothing.

## The logbook check

One check guards the merge check and every write, `init` on an existing logbook too. Each of the seven tables must be:

- there (not deleted, and not a link to nothing);
- a regular file that the tool can read;
- not empty (not 0 bytes, and not only blank lines);
- with its header line: the first line names each of its columns. A BOM and CRLF line ends from an editor are read as a plain file.

A table that fails refuses every merge and every write, and the refusal names the file. No command makes a lost table again or repairs it in silence. The ways out:

- Restore the file from a copy.
- A table that cannot be read (EACCES): fix its permissions. Do not remove it: its rows are there.
- If no copy is left and the user accepts the loss: `logbook repair --accept-loss <table>`. Run the command that the refusal prints. When a second table fails too, the repair refuses and prints the command with both tables: run that one.

After a repair of tasks.tsv, the verdicts of its lost tasks stay in ledger.tsv. The merge check refuses their SHA, says that tasks.tsv was started again, and asks for a new commit with its verdicts under a task that the logbook has.

The programs table came after the others. A logbook made before it has no programs.tsv: that reads as a table with no rows while no task names a program, and `program propose` writes the file. When a task names a program and the file is missing, its rows are lost, as for any table.

Limit: a table cut to only its header line is a table without rows. The check cannot tell it from a new table.

A folder without tasks.tsv is no logbook: `init` has not finished it. `init` finishes it when its tables have no rows. When they have rows, its task list is lost, and `init` refuses: restore tasks.tsv, or repair it.

## A saved change that cannot finish

Each write starts by finishing or undoing a saved change that an earlier write left. Sage never drops a saved change by itself. When the change cannot finish, every write and merge of that project refuses with one line, and other projects go on. The line names two ways out:

1. **With a backup:** the owner restores the folder that `sage logbook` prints. Rows newer than the backup are lost.
2. **With no backup:** ask the owner in the chat to accept the loss of this saved change. After the answer, run `logbook repair --accept-change-loss yes`, or the owner runs it in a terminal when you cannot. This is the one step that passes a saved change, and it needs the owner's answer each time.

What the repair does:

- It works the same on a shared logbook, from any checkout with a row in `bindings.tsv`, also on a path through a link to that checkout.
- It refuses, and changes nothing, on a logbook with no saved change and on a saved change that can finish. Any write finishes that one.
- It also refuses, and changes nothing, when the change may still finish elsewhere, each time with the next step:
  - The logbook is reached through a link. The line names the real folder and the next step. When the logbook's path is the link itself, move the real folder there, in place of the link. When a folder above it is the link, set the setting that the line names, `SAGE_HOME` or, for a shared logbook, `SAGE_SHARED_HOME`.
  - A newer sage wrote the change: its schema is above the highest that this version knows, or a table has columns that this version does not know. Update the sage plugin.
- It writes a decision row first. The row names the kept file and says that the owner accepts the loss.
- It moves `review-pending.json` aside as `review-pending.json.lost-<n>`, and never deletes it. Each repair keeps its own file.
- It does not repair the tables, and it says so. A half-published update can leave mixed tables: some tables hold the change and others do not. Its output ends with the result of the logbook check.

Sage writes saved changes of two schemas only: 7 (usage) and 9 (Replace). Schemas 2 to 6 and 8 belonged to the Codex native runtime, which sage deleted (T732, T914). A saved change of one of them cannot finish, so it stops the writes of its logbook until the repair above. No readable logbook had one when sage deleted them.

When the check fails, the output prints the refusal, and the table repair above applies. The check reads each table alone, so tables that are each whole but do not agree pass it: read the rows of the last work.

When decisions.tsv fails the check, the repair cannot write its decision, and it prints the command that takes both losses: `logbook repair --accept-change-loss yes --accept-loss decisions`.

## Hidden characters

The tool keeps no hidden character in a cell, and removes them from the standing orders. Hidden characters are those that a person does not see but a terminal or an agent acts on:

- the control characters (C0, DEL and C1), except a tab and a line end in the standing orders;
- the bidi embeddings, overrides, isolates and marks (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, U+061C);
- the zero-width characters (U+200B to U+200D, U+2060, U+FEFF);
- the variation selectors (U+FE00 to U+FE0F, U+E0100 to U+E01EF);
- the tag characters (U+E0000 to U+E007F), text that only an agent reads.

Other text stays: each script, and emoji. A zero-width joiner or non-joiner between two letters stays: Persian and Indic text needs it. A zero-width joiner between two emoji stays, so a joined emoji stays whole, and the emoji selector (U+FE0F) stays after an emoji or a keycap base (`1️⃣`). A subdivision flag (England, Scotland, Wales) shows as a black flag.

The tool prints each hidden character in an id, a column or a path as `\xNN` or `\u{N}`. For a project path with a control character, it prints no command to paste.


### An approved repair after a round hold

A round hold needs an explicit answer from the owner. A default answer does not grant a repair.

For a task with four spent rounds and a current limit of three, open a gate on that task:

```text
sage gate add T1 --question "Approve one more repair round for T1 after 4 spent rounds and limit 3?" --options "approve|decline" --recommend approve
```

After the owner chooses approve, record that answer with `gate_answer`, then call `task_set` with `task: T1` and `fields: {"state":"building","approval":"G1"}`. Use the actual gate ID. Use `briefed` instead of `building` when a new brief is needed. The CLI form is `task T1 set state=building approval=G1`.

The limit is `max_rounds + extra`. One approval permits the next round above the greater of spent rounds and that limit. This example permits round five; round six holds again. The task keeps its cumulative rounds, PR, branch, earlier allowances and review minimum.

Missing, declined, wrong-task, stale, malformed or used approvals refuse before any changes. A repeated CLI or `task_set` call after success refuses and adds nothing. An exact native task-update retry returns its saved result. After an uncertain result, read the task before a new request. The allowance and used gate IDs share one task-row write.

### An extra round in autopilot

While autopilot is on for your session, you give the next round past `max_rounds` yourself, up to 5 rounds in all, with the reason: `sage round T1 --why "<reason>"`. It works from the round hold or before it, and writes a decision row with the reason. Without `--why`, with autopilot off, or for round 6 and later, the round hold and the owner's gate above stay. Only the chief gives such a round: a lead's `round` takes no `--why`.
