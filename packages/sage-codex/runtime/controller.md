# Owned controller wrapper

The wrapper runs the native owned controller of the Codex fork for one Sage task. It launches the controller, checks the effective policy before any model turn, binds one task to one root thread, and keeps every notification and an honest result for each turn. The terminal client puts the owner in front of it: each typed line is one turn.

## What it does

- **Launch.** `resolveControllerBinary` reads only `SAGE_CODEX_CONTROLLER_BIN`: no default, no PATH lookup and no other variable. It refuses an unset, relative, missing or non-executable path. It follows a link to the real path, and refuses the file, or a folder on that path, when its group or other users can write it, or when it belongs to a user other than the current user or root (a sticky folder such as `/tmp`, owned by root, is accepted). It returns the sha256 of the file, and refuses a different hash when `SAGE_CODEX_CONTROLLER_SHA256` is set. The process runs `app-server --stdio --owned-controller --strict-config` with one `-c` flag for each key of `OWNED_CONTROLLER_CONFIG`, in its own process group, with the real path of the project as its cwd. No other launch exists.
- **The launch profile.** The `-c` flags turn multi-agent v2 on, and multi-agent v1, goals, web search, plugins, apps and remote plugins off. The gated real test checks that the model gets no v1 tool (`send_input`, `resume_agent`) and no goal tool.
- **Policy binding.** `openThread` runs every check of the project before `thread/start`, because `thread/start` already starts the MCP servers. In order:
  1. `checkProjectFiles` refuses a rules file (`.codex/rules/*.rules`), a hooks file (`.codex/hooks.json`) or an agent role file (each `.toml` file in `.codex/agents/` or a folder below it) in the `.codex` folder of the project or of any folder above it, up to the filesystem root. Codex loads these files with no config key, so `config/read` never shows them: a rule can let a command run with no approval or outside the sandbox, a hook runs a command at its event, and a role sets the instructions, model, sandbox and MCP servers of each agent that starts with it. Codex loads them from the folders between the project root and the cwd, and the hooks of a linked Git worktree from the matching folder of its main checkout, so the check covers those folders too (a superset). The `.codex` folder that is `CODEX_HOME` (or `~/.codex` when `CODEX_HOME` is not set) holds the owner's own rules and hooks, and passes. The refusal says where the file is (in the project, in a folder above the project, or in the main checkout of the project worktree), and tells the owner to check the file: to move it to `CODEX_HOME/rules/`, `CODEX_HOME/hooks.json` or `CODEX_HOME/agents/` if they trust it, or to remove it. A folder that the check cannot read, also a link that points to itself or a loop of links in `.codex/agents`, refuses with the code `project-files` and says to make the folder readable or to remove it; a dead link is no role file and passes.
  2. `config/read` with `includeLayers`, then `checkConfig` on its reply: each owned key has its value from the session flags layer. Each layer that is not the owner's (the project layer, because an agent can write project files, and each other layer such as the packaged defaults) can set only the keys that `PROJECT_ALLOWED` names. `checkConfig` decides this from the layer's own config tree in the reply: each key path that the layer sets is checked, also a table or a list, empty or not, because a list replaces the owner's list. The origins of the merged config name only values and list items, so an empty list from the project (`shell_environment_policy.include_only = []`) cleared the owner's list with no project origin (R1575-1). An empty table on the way to an allowed key (`[tui]` with no keys) merges nothing and passes. The check of the origins (each key comes from the user layer, a managed layer or the session flags, unless `PROJECT_ALLOWED` names it) stays as a second check. A reply with no layers refuses. A disabled project layer (an untrusted project) is checked too, although Codex does not load it. The allowed keys: Each changes the model's text work only: none can run a program, change a path or the environment, add a tool or a role, or change approvals.
     - `model`: a model name for the owner's own provider (`model_provider` and `model_providers` are not on the list). `bindPolicy` shows it with its origin.
     - `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`: fixed words that the provider gets with each request.
     - `personality`: a fixed word that selects one of the built-in texts of the instructions.
     - `developer_instructions`: text only. The client gives its own developer instructions at `thread/start`, and those take its place. `model_instructions_file` is not on the list, because it names a path that Codex reads outside the sandbox.
     - `file_opener`: a fixed word for the scheme of the file links in the text (such as `vscode`). It opens nothing.
     - `history.persistence`, `history.max_bytes`: whether and how much Codex keeps of the typed lines in the history file of `CODEX_HOME`. Neither names a path.
     - `tui.*`: the display of the TUI. The client does not run the TUI, and no TUI key runs a program (`notify`, which runs a command, is a top-level key and is not on the list).

     So the project cannot set `shell_environment_policy.*`, `allow_login_shell`, `zsh_path`, `agents.*`, `mcp_servers.*`, `hooks.*`, `features.*`, `tools.*`, `notify`, `profile`, the sandbox, permission and approval keys, the URL and path keys, any `experimental_*` key, or a key that the client does not know. The approval policy and the sandbox must also be set: a key that no layer sets comes from `config/read` as null with no origin, and for these two that is one refusal that names each missing key, with an example value, and says to set it in `CODEX_HOME/config.toml`. A refusal of a key from the project tells the owner to check it: to move it to `CODEX_HOME/config.toml` if they trust it (an agent may have written it), or to remove it. Each message calls the owner's config "your Codex config".
  3. `thread/start` with the project cwd, `ephemeral` true and the developer instructions. `bindPolicy` then checks that the thread is a 0.160.0 ephemeral root in the project, and that the model, provider, approval policy and sandbox of the thread are the ones in the owner's config. A model or a provider that no layer sets is the default.

  `config/read` and `thread/start` each have a deadline. A refusal sends no later request (a file or config refusal sends no `thread/start`), stops the process and returns `refused` with a fixed code and a message that says what it found and what to change. The policy record and its binding hash go with every turn result.
- **The owner's selection.** The wrapper never sends a model, provider, approval policy, sandbox, permission profile, environment list, tool list, or a `turn/start` cwd or workspace root. The thread keeps the default environment, so the normal Codex tools run under the owner's own sandbox and approval setting. The owner's hooks stay on.
- **Server requests.** The transport answers no server request by itself. It keeps the id of each request that waits, and `answer(id, result)` or `refuse(id)` (an error reply, -32601, which the controller reads as a refusal) sends its one reply; a second reply, an unknown id, a request that `serverRequest/resolved` closed, or a closed connection sends nothing and returns false. A second request with the id of one that waits is a protocol fault. With an `onEvent` handler, the process gives each request to the handler (kind `server-request`), and the handler answers it by its id. With no handler, nobody can answer, so the process refuses it at once (kind `server-request-refused`).
- **Events.** Every notification and every server request goes to `onEvent` in arrival order, with a sequence number, as frozen data. `events()` keeps them too: with an `onEvent` handler, only the events of the current turn (the handler keeps what it needs, so a long session does not grow); with no handler, every event of the process. `maxEvents` and `maxEventBytes` count from the start of the current turn; past them the process fences: a lost event never passes silently. Three kinds of event can pass 64 MiB in one long valid turn: a delta (such as `item/agentMessage/delta` or `item/commandExecution/outputDelta`, one for each streamed piece), `turn/diff/updated` (the whole diff again after each patch) and each event of another thread than the bound root (a child agent). These do not count toward `maxEvents` or `maxEventBytes` (R1580-1), and with an `onEvent` handler `events()` does not keep them, so they cost no memory; `maxDeltaEvents` (1 000 000 in one turn) bounds their count. A throw from `onEvent` fences too. No stderr text is kept. One frame (one line of the protocol) can hold one whole agent message, so its bound (`maxFrameBytes`) is 64 MiB too; the reader counts the bytes of a frame and never copies its pieces.
- **MCP servers after the check.** `thread/start` reads the config again, so a project config that an agent writes between `config/read` and `thread/start` can start an MCP server that `checkConfig` did not see (R1581-1, proved on the real binary). As a second check, an `mcpServer/startupStatus/updated` event for a server that is not in the checked config (`mcp_servers`) and is not the built-in `codex_apps` fences the process with the reason `Unchecked MCP server`: no turn runs after it, and the client says that the controller started an MCP server that it did not check. The server process has started by then; the fence stops the session, not the start.
- **Turn result.** `turnOutcome` decides from `turn/completed` of the bound thread and turn only: `completed`, `interrupted` or `failed`; any other status, also a name such as `constructor`, gives `uncertain`. A terminal that comes before the `turn/start` reply waits for it. Two terminals in one read give `uncertain`; a terminal for a turn that already has its result fences the process. EOF, a crash, an invalid frame, a fence or the event limit before a terminal give `uncertain`, never `completed`. At the turn deadline, and on `stop()` during a turn, the wrapper sends `turn/interrupt` first; with no terminal within `interruptGraceMs` the result is `uncertain`. An uncertain turn fences the process. `fenced()` resolves with the first fence reason.

## The terminal client

Run it from the built plugin, because `commands.mjs` needs the bundled core:

```sh
SAGE_CODEX_CONTROLLER_BIN=/absolute/path/to/fork/codex \
  node plugins/sage-codex/runtime/controller-client.mjs --project <folder> --task T400 --run R1 --instructions <file>
```

- Before it starts the controller, it checks the options, the binary, the project folder, the instructions file and the task and run ids. A refusal says what it found and what to do. The instructions file must be a regular file: the client opens it with no wait and checks the type of the open file, so a named pipe, a device or a folder refuses at once and names its type (a read of a named pipe waits for a writer).
- It prints the binary path and its sha256, and a warning when `SAGE_CODEX_CONTROLLER_SHA256` is not set. Then it prints the task, the run, the model, approval and sandbox of the owner's config, each in quotes, and how to use the client. A model that no layer sets shows `(the Codex default)` after it.
- On a terminal, the client reads each key (raw mode) and keeps the line itself, because a terminal in line mode keeps at most 1024 bytes of one line on macOS (`MAX_CANON`): a longer pasted line never came through, and Enter, Ctrl-C and Ctrl-D then did nothing. So a line of up to 65536 bytes, typed or pasted, is one turn (a longer one is refused with the line limit message). Enter sends the line; Backspace removes the last character; Ctrl-C clears the line (below); Ctrl-D ends the input on an empty line. The client echoes printable text and tabs only: a key sequence such as an arrow, and each other control character, is ignored. A key sequence that comes in two reads (an ESC in one, `[A` in the next) is kept until its end and then ignored too, so it adds no text (R1575-4); an ESC alone at the end of a read with no sequence after it is the Escape key. Raw mode turns off the terminal's own Ctrl-S, Ctrl-Z and Ctrl-\\ keys while the client reads. Raw mode stays on until the client ends, also after Ctrl-D during a turn, so Ctrl-C still stops that turn and the terminal does not echo text that no line takes (R1577-3). The client gives the terminal its line mode back at the end.
- On a terminal, the client turns on bracketed paste mode (`ESC[?2004h`) before the Ready lines, and turns it off at the end (also after a crash, from the exit handler of the entry). The terminal then puts marks around a paste: the text between them, with its line ends kept as `\n`, goes into the line, and the paste becomes one turn when the owner presses Enter (R1577-1). A control character inside a paste is text of the paste and is dropped; Ctrl-C there does not act. The Ready lines say that a paste of several lines is one line. Node's readline in terminal mode was the other option, but it draws the line again at each wrap of the terminal width: a paste of 12000 bytes into 80 columns took minutes. Input from a pipe is read by lines, as before.
- Each non-empty line is one turn, one at a time, sent unchanged. A line typed during a turn waits, and the client says so. Input from a pipe gives a paste of several lines as several lines. `commands.mjs` classifies the line: the client says that a mode phrase goes to the chief, or that a near line changed no mode, with the phrase that it means ("this") or the phrases ("one of these").
- It prints the agent messages of the root thread, each with `chief> ` before each of its lines (the line ends at the end of a message give no empty line, R1578-1), and each controller warning, each of its lines with the warning prefix. A warning that comes again (the controller can give the same one at each turn) shows once in a session. Each turn result says what happened and what to do next; the fix for a refused line shows also when another typed line waits. The reasons of the controller process come in plain words (for example "the controller process ended by itself"), the same words for one event in each line.
- **Approvals (T431).** The client asks the owner yes or no for each approval request of the controller, from the chief or from a child agent, also while no turn runs. It shows the question as a block:

  ```text
  [Approval: agent /root/lead_t1/implementer asks to run a command.]
    command: "npm install"
    folder: "."
    reason: "needs network"
  Type y to allow it once, or n to refuse it.
  ```

  - Line 1 names the agent and the action: "run a command", "send input to a running command", "change files", "get file access", "connect to a host" or "use an MCP tool". The agent is `/root (the chief)` for the root thread, else the agent path of its thread. The pinned binary gives no `thread/started` for a child (R1598-K3), so the name comes from the `subAgentActivity` item on the root thread (`agentThreadId` to `agentPath`), and from `thread/started` when it comes. The first name of a thread stays, and no item renames the chief. A thread with no known name shows as `(unknown child <thread id>)`, never as the chief.
  - Then one field for each line, indented two spaces: `command`, `folder`, `reason`, `host`, `server`, `tool`, `message`, and `file` or `access` once for each item, all items. The last line says how to answer.
  - Each value is a JSON string, so a quote or a line end in it shows escaped (`\"`, `\n`): a value cannot draw a fake end of the question (R1596 spoof). Each shown line then goes through the control-character filter below. (The order is JSON first, then the filter, so that a line end shows as `\n` and not as U+FFFD.)
  - A folder or a file inside the project shows relative to it (`"."` for the project folder); one outside it, after its `..` parts resolve, shows as an absolute path. Symbolic links are not resolved.
  - A value over 2000 characters, or a request with over 50 files or access items, is not shown: the client refuses it at once with `[Agent <name> sent an approval request that is too long to show, so the client refused it.]`.

  | Request | The fields | y sends | n sends |
  | --- | --- | --- | --- |
  | `item/commandExecution/requestApproval` | `command`, `folder`, `reason`, one `access` for each extra permission | `{decision: "accept"}` | `{decision: "decline"}` |
  | the same, with `networkApprovalContext` (it has no command and no folder) | `host` (the host and the protocol; the protocol has no port), `reason` | `{decision: "accept"}` | `{decision: "decline"}` |
  | `item/fileChange/requestApproval` | one `file` for each path of the `fileChange` item of `item/started`, `reason` | `{decision: "accept"}` | `{decision: "decline"}` |
  | `item/permissions/requestApproval` | `folder`, `reason`, one `access` for each item | the asked permissions, `scope: "turn"` | no permissions, `scope: "turn"` |
  | `mcpServer/elicitation/request`, a form with `_meta.codex_approval_kind` `mcp_tool_call` and a `requestedSchema` with no properties and no required fields | `server`, `message` | `action: "accept"`, no content and no `_meta` | `action: "decline"` |
  | `item/tool/requestUserInput`, one question with the id `mcp_tool_call_approval_<itemId>`, where `itemId` is an `mcpToolCall` item that started in the same thread and has not ended, and an `Allow` option | `server` and `tool` (from that item), `message` | the answer `Allow` | the answer `Cancel` |

  An `access` item is `the network`, or a target and its access (read, write or deny): a path, `the files that match "<glob>"`, or for a special path a plain name (`the whole disk` for root, `your home folder` for home, else `the special path "<kind>"`, with its subpath). The client shows every `fileSystem.entries` item; a legacy `read` or `write` root that only repeats an entry shows once. y grants exactly the items that the block shows. An entry, an access or a path list that the client cannot read makes the request unreadable, so the client refuses it. In the fork, only the MCP tool approval code makes a question id with the prefix `mcp_tool_call_approval` (`core/src/mcp_tool_call.rs`: `mcp_tool_call_approval_<call id>`, after the `mcpToolCall` item of that call id starts; the request has that call id as its `itemId`), but the model's own `request_user_input` tool can choose any question id, so the client checks the item too (R1594-6).

  Input while a question shows:

  - Each show of a question clears the typed line and drops the rest of the current terminal read (only paste marks and Ctrl-C still act in it). If the typed line had text, the client says `[Your typed text was cleared, because an approval request came. Type it again after you answer.]`. So no text typed or pasted before the question, and no second y in the same read, can answer it (R1594-1, R1595-1).
  - Only a typed y, yes, n or no (any case, trimmed) and an Enter that is not part of a paste answer. Text from a paste never answers.
  - Any other line, also an empty one, is no turn: `[Your line did not go to the chief, because an approval request waits. Answer it, then type your line again.]`, then the question again (R1595-2).
  - After any other output while a question waits (a chief line, a child line, a notice, a turn result), the question block shows again, so the question is the last text on the screen (R1595-1).
  - Lines that waited before the question stay waiting as turns; they never answer it.
  - A line that is only y, yes, n or no when no question waits never goes to the chief: `[No approval request waits, so your line did not go to the chief.]` (R1595-4, R1596-2).

  Input from a pipe is read by lines: each line after the question shows can answer it, in order; the rules above apply, except the clear of the typed line and of the rest of a read, which are terminal rules.

  A question that is not a tool approval is refused with `[Agent <name> asked you a question: "<text>". The client cannot show questions, so it refused it. The agent goes on without your answer.]`, with the text escaped and cut at 2000 characters.

  The client never offers or sends a lasting choice: no `acceptForSession`, no amendment from `availableDecisions`, no session scope and no `persist` value. Several requests wait in order and show one at a time. Ctrl-C while a request waits refuses it (decline) and then acts as before (it stops the turn); the end of input and a stop refuse each request that waits; a request that comes after them shows no question, only the line that the client refused it (R1593-4). A `serverRequest/resolved` for a request that waits removes it, with a line, and the next one shows. After a fence the client drops the requests that wait, because no reply can go out. While a request waits, the 15 s note below does not show. Every other request is refused at once with an error reply, with a line that says so: an approval request that the client cannot read (for example a command with no command text), an MCP form that is not a tool approval, a question that is not a tool approval, and any other method.
- When a turn gets no controller event for 15 s (`WAIT_MS`), the client shows `[Waiting for the model. Press Ctrl-C to stop the turn.]`, once for each turn.
- Controller text never reaches the terminal raw. Each character of these classes becomes U+FFFD: the controls (`\p{Cc}`: C0, C1 and the newline in a client line too), the format characters (`\p{Cf}`: bidi controls, zero-width characters, the soft hyphen, tags, U+0600 to U+0605, U+180E, U+206A to U+206F), the line and paragraph separators (`\p{Zl}`, `\p{Zp}`), and every default-ignorable character (`\p{Default_Ignorable_Code_Point}`: variation selectors, Hangul fillers). So model text cannot move the cursor, write the clipboard, hide or reorder what the owner sees or print a line that looks like the client's. A config value on the Ready line goes through the same filter, in quotes.
- The client writes to its terminal without blocking, so a terminal that takes no output (Ctrl-S, or a stopped terminal) never stops it. When more than 8 MiB of output waits for the terminal (`TERMINAL_QUEUE_BYTES`), the client says so once, stops the turn, and drops output until the terminal takes output again (with input from a pipe, the message also says to press Ctrl-Q after Ctrl-S; in raw mode the terminal's own Ctrl-S is off, so it does not); the result of that turn says that the client stopped it. The client's result lines (each turn result, and the end of the session) wait while the terminal takes no output, and show when the stream says `drain`, so each turn shows how it ended, also when the terminal is still paused at its end. A turn that ran while output was dropped says that some of its output did not show.
- Ctrl-C (the key in raw mode, or SIGINT from a pipe session) clears the typed line and drops the lines that wait, and says how many it dropped; the first one also stops the active turn at once with a message (R1575-2, R1577-1). A line typed after that Ctrl-C runs when the turn ends, and the client says that it starts now, with the count when more than one waits (R1577-2). A second Ctrl-C on an empty line stops the controller, also before the chief is ready; a Ctrl-C that clears a typed line never stops the controller. SIGTERM stops the controller. The end of the input (Ctrl-D) stops the controller after the lines already typed; during a turn the client says that Ctrl-C stops it now. After the end of the input or a stop, the result of a turn says that the controller stops now.
- A lost terminal (SIGHUP, or an EIO or EPIPE on the terminal) stops the controller at any time, idle or in a turn, and the client writes nothing more. The client writes to its terminal without blocking and opens stderr at its start: after a terminal closes (macOS), a blocking write and the first open of stderr wait for ever.
- The controller runs in its own process group, so a terminal Ctrl-C reaches the client only. The controller still ends with the client: the client stops it on every path, and a killed client closes its stdin, which ends the controller by itself (the gated real test checks this).
- The exit code is 0 only after a stop that the owner asked for (Ctrl-C, Ctrl-D or SIGTERM). A refusal, a crash, a fence, an unknown turn result or a lost terminal gives 1.
- The controller gets the client's environment, so it uses the owner's `CODEX_HOME`, config, hooks and login.

## What it refuses

- A second `openThread`, an `openThread` before the start, a second turn while one is active, and any turn after a fence or a stop.
- With no `onEvent` handler, every server request, with error -32601. The client refuses every request that is not an approval it can read (see Approvals above).
- A task id, run id, project, instructions or turn text that fails the checks in `bindTask` and `bindTurnText`.

## What it does not prove

- That the binary that runs is the one that was hashed: a swap between the hash and the launch is not detected.
- That no agent writes a project config file (`.codex/config.toml`), a rules, hooks or agent role file during the session. The check runs before `thread/start` only. The Codex sandbox keeps each `.codex` folder read-only in its writable roots (read in the fork source, not tested here); with `danger-full-access` nothing keeps it.
- A project config file, rules, hooks or agent role file added between the check and `thread/start`. For the project config, the MCP startup check above stops the session when such a file adds an MCP server, after that server has started; another key from such a file is not detected.
- That the native tool policy is safe for children (T391). The wrapper checks the launch profile and the root's tool names, not the children's tools.
- Real-model behaviour. The gated test in `controller-owned.test.mjs` uses a loopback synthetic provider. Three gated cases run the client with the approval policy `on-request` and a read-only sandbox: the synthetic model asks for an escalated `touch` of a marker outside the project; n leaves the marker out and y creates it. In the third, the command draws a fake end of the question (R1596 spoof): it shows escaped inside its `command` field, and n leaves the marker out. The file change, permission, host and MCP kinds, and the terminal input rules, are tested on the fake controller only.
- A bound on memory for a long session with no `onEvent` handler: then `events()` keeps every event of the process. The client gives a handler.

## Checks

Run each test file alone with `node --test`, with fake `ps`, `pgrep` and `kill` first on PATH. `controller-owned.test.mjs` replays `controller-fixture.json`, which comes from the labelled synthetic U3 transcript and the `config/read` format of the real fork binary. Its signal cases run the built client as its own process on a fake controller script, and send SIGINT to the process group of that client only. Its pty cases run the built client on a pseudo terminal (Python `pty.fork`, skipped when `python3` is missing) and close that terminal; one of them stops reading the terminal during a large chief message and checks that the client still runs the next line. Its ten real cases run only when `SAGE_CODEX_CONTROLLER_BIN` names the built fork binary; `SAGE_CODEX_CONTROLLER_EVIDENCE` names a folder for their JSON evidence.
