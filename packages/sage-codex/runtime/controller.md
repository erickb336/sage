# Owned controller wrapper

The wrapper runs the native owned controller of the Codex fork for one Sage task. It launches the controller, checks the effective policy before any model turn, binds one task to one root thread, and keeps every notification and an honest result for each turn. The terminal client puts the owner in front of it: each typed line is one turn.

## What it does

- **Launch.** `resolveControllerBinary` reads only `SAGE_CODEX_CONTROLLER_BIN`: no default, no PATH lookup and no other variable. It refuses an unset, relative, missing or non-executable path. It follows a link to the real path, and refuses the file, or a folder on that path, when its group or other users can write it, or when it belongs to a user other than the current user or root (a sticky folder such as `/tmp`, owned by root, is accepted). It returns the sha256 of the file, and refuses a different hash when `SAGE_CODEX_CONTROLLER_SHA256` is set. The process runs `app-server --stdio --owned-controller --strict-config` with one `-c` flag for each key of `OWNED_CONTROLLER_CONFIG` and the trust flag of the project (below), in its own process group, with the real path of the project as its cwd. No other launch exists.
- **The launch profile.** The `-c` flags turn multi-agent v2 on, and multi-agent v1, goals, web search, plugins, apps and remote plugins off. The gated real test checks that the model gets no v1 tool (`send_input`, `resume_agent`) and no goal tool.
- **Project settings.** The launch flag `projectTrustFlags` marks the project folder and each folder above it, up to `/`, as untrusted: `-c projects={ "<folder>"={ trust_level="untrusted" }, ... }`. So Codex disables each project layer (each `.codex` folder from the project root to the cwd) at each config load: at `config/read`, at `thread/start` and later. A file that an agent writes in a `.codex` folder at any time has no effect, so no check of the project files and no race window remain (R1588-1, R1588-2). The reasons for the form of the flag (proved on the pinned binary, R1591):
  - A session flag is above the owner's own config, so it wins over a trust entry that the Codex TUI wrote there.
  - Codex gives each folder from the project root to the cwd its own trust decision. A flag for the project only leaves a trusted folder above it loaded: its MCP server started.
  - A dotted key (`-c projects.<path>.trust_level=...`) splits the path at each dot, and the controller stops at startup for a path such as `my.project`. The inline table keeps each path one key. Each key is a JSON string, which is a TOML basic string; DEL is written as `\u007f`, and a path that is not valid Unicode refuses with the code `project-path`.
  - Codex looks up the trust of the canonical spelling of the cwd: the one that `realpath(3)` gives, with the letter case and the Unicode form of the disk. So the process takes the canonical folder of its cwd with `realpathSync.native`, runs the controller there (also `config/read`, `thread/start` and the binding record), and the flag names that spelling first. When the spelling that the owner typed differs (for example `myproj` for `MyProj`, or NFC for an NFD name), the flag names it too, each folder up to `/`. Before this, a trust entry of the owner under the canonical spelling still applied, and a project MCP server that an agent wrote at `thread/start` ran (R1600-1, R1601-1).
  - Each trust entry of the owner. An agent can move or rename the project at `thread/start` into a folder that the owner trusts, and Codex then looks up that folder: a case-only rename (`MyProj` to `MYPROJ`, R1611-1), a move into a trusted folder or Git repository with a link at the old path (R1620-1, R1622-1), or a case-only rename of the folder above a linked worktree, which gives the trust of its main checkout (R1620-2). In each case the owner's entry applied and a project MCP server ran. So after `config/read`, `unflaggedTrustKeys` takes each key of the owner's `projects` tables (the user config, its profile and the managed configs, as written) that the flag does not name. When there is one, `openThread` stops the controller and starts it once more with those keys in the flag too, as untrusted (`trustFlags`); only the second controller gets `thread/start`. So no trust entry of the owner applies during the session: one rule for every move, rename and link. If the `config/read` of the second controller shows another such key (the owner config changed in between), the start refuses with the code `project-spelling`: `Your Codex config changed while the client started: it has a new trust entry for "<key>". Start the client again.` A restart, not a read of the owner config before the launch: the client has no TOML reader, and Codex itself merges the owner layers for `config/read`. The restart costs one more start of the controller (47 to 75 ms in QA, with no line), and only for an owner with a trust entry outside the project and the folders above it. When the first controller does not stop, or the second does not start, the start refuses with the code `restart` and a fix: `the controller did not stop for its restart, so the client did not start it again.` or `the controller did not start again after its restart.`, then `Check that SAGE_CODEX_CONTROLLER_BIN is the fork binary and that your Codex config file loads, then start the client again.` (R1619-4, R1621-2).

  What does not load: the project config (`.codex/config.toml`: MCP servers, hooks, features, the model and text settings too), the rules, hooks and agent role files, of the project and of each folder above it, and the hooks of a linked worktree from its main checkout. What still loads: the skills of the project (`.codex/skills`), as Codex says in its own warning; a skill is text and files, and a script in it runs only through the shell tool, under the owner's sandbox and approval setting. Codex does not load the project `AGENTS.md` of an untrusted project, so the wrapper adds the project files (below). An untrusted project with an owner config that sets neither the approval policy nor the sandbox gets other defaults; the client refuses that config anyway (`selection-missing`).
- **Policy binding.** `openThread` runs the check of the config before `thread/start`, because `thread/start` already starts the MCP servers. In order:
  1. `config/read` with `includeLayers`, then `checkConfig` on its reply. Each owned key has its value from the session flags layer. Each project layer must be disabled: an enabled one refuses with the code `project-trusted`. The message names a managed config (`/etc/codex/managed_config.toml`, or one from the organization), which is above the launch flags, and ends: `Remove that trust entry (if the file belongs to your organization, ask its administrator), then start the client again.` An owner trust entry cannot cause it: the flag marks each one untrusted (R1612-1, R1621-1). Each key of the merged config comes from the user layer, a managed layer or the session flags; a key from another layer refuses with `selection-origin` and its name. A reply with no layers refuses. The approval policy and the sandbox must also be set: a key that no layer sets comes from `config/read` as null with no origin, and for these two that is one refusal that names each missing key, with an example value, and says to set it in `CODEX_HOME/config.toml`. Each message calls the owner's config "your Codex config".
  2. The project files (`projectInstructions`, below), with the owner's limits from the checked `config/read` reply.
  3. `thread/start` with the project cwd, `ephemeral` true and the developer instructions (the chief instructions and the project files). `bindPolicy` then checks that the thread is a 0.160.0 ephemeral root in the project, and that the model, provider, approval policy and sandbox of the thread are the ones in the owner's config. A model or a provider that no layer sets is the default. A thread in another cwd after the real path of the project changed (a move or a rename during the start) refuses with the code `cwd`, and the client says `[The client did not start the chief: the project folder changed while the client started. Start the client again.]`; with no such change it is a fork mismatch (R1622-2). The policy record keeps the launch arguments (with the trust flag) and the `.codex` folders of the disabled project layers (`projectFolders`).

  `config/read` and `thread/start` each have a deadline. A refusal sends no later request (a config refusal sends no `thread/start`), stops the process and returns `refused` with a fixed code and a message that says what it found and what to change. The policy record and its binding hash go with every turn result.
- **The owner's selection.** The wrapper never sends a model, provider, approval policy, sandbox, permission profile, environment list, tool list, or a `turn/start` cwd or workspace root. The thread keeps the default environment, so the normal Codex tools run under the owner's own sandbox and approval setting. The owner's hooks stay on.
- **Events.** Every notification and every refused server request goes to `onEvent` in arrival order, with a sequence number, as frozen data. `events()` keeps them too: with an `onEvent` handler, only the events of the current turn (the handler keeps what it needs, so a long session does not grow); with no handler, every event of the process. `maxEvents` and `maxEventBytes` count from the start of the current turn; past them the process fences: a lost event never passes silently. Three kinds of event can pass 64 MiB in one long valid turn: a delta (such as `item/agentMessage/delta` or `item/commandExecution/outputDelta`, one for each streamed piece), `turn/diff/updated` (the whole diff again after each patch) and each event of another thread than the bound root (a child agent). These do not count toward `maxEvents` or `maxEventBytes` (R1580-1), and with an `onEvent` handler `events()` does not keep them, so they cost no memory; `maxDeltaEvents` (1 000 000 in one turn) bounds their count. A throw from `onEvent` fences too. No stderr text is kept. One frame (one line of the protocol) can hold one whole agent message, so its bound (`maxFrameBytes`) is 64 MiB too; the reader counts the bytes of a frame and never copies its pieces.
- **Turn result.** `turnOutcome` decides from `turn/completed` of the bound thread and turn only: `completed`, `interrupted` or `failed`; any other status, also a name such as `constructor`, gives `uncertain`. A terminal that comes before the `turn/start` reply waits for it. Two terminals in one read give `uncertain`; a terminal for a turn that already has its result fences the process. EOF, a crash, an invalid frame, a fence or the event limit before a terminal give `uncertain`, never `completed`. At the turn deadline, and on `stop()` during a turn, the wrapper sends `turn/interrupt` first; with no terminal within `interruptGraceMs` the result is `uncertain`. An uncertain turn fences the process. `fenced()` resolves with the first fence reason.

## The terminal client

Run it from the built plugin, because `commands.mjs` needs the bundled core:

```sh
SAGE_CODEX_CONTROLLER_BIN=/absolute/path/to/fork/codex \
  node plugins/sage-codex/runtime/controller-client.mjs --project <folder> --task T400 --run R1 --instructions <file>
```

- Before it starts the controller, it checks the options, the binary, the project folder, the instructions file and the task and run ids. A refusal says what it found and what to do. The instructions file must be a regular file: the client opens it with no wait and checks the type of the open file, so a named pipe, a device or a folder refuses at once and names its type (a read of a named pipe waits for a writer).
- The project files. `openThread` reads them once, after the check of `config/read` and before `thread/start`, with the rules of plain Codex:
  - The folders: from the project root down to the project folder. The project root is the nearest folder, from the project folder up, with one of the owner's `project_root_markers` (the default is `.git`; a `.git` file of a linked worktree counts). A marker counts only when it is there, with links followed, so a dead link is no marker. With no such folder, or with an empty marker list, only the project folder (R1610-2).
  - The file in each folder: the first of these names that is a regular file, with links followed: `AGENTS.override.md`, `AGENTS.md`, then each name of the owner's `project_doc_fallback_filenames`, as written (no trim). So a dead link, a folder or a named pipe named `AGENTS.override.md` gives `AGENTS.md`, with no notice, as in Codex (R1610-1). A fallback name `.` or `..`, or one with `/` or NUL, is skipped, and one line before the Ready lines says so for each one: `[The client ignores the name "../outside.md" in project_doc_fallback_filenames: it is not a file name. In your Codex config (<CODEX_HOME>/config.toml), remove it or give a file name with no folder, then start the client again.]` (R1610-3, R1621-3).
  - The limit: the owner's `project_doc_max_bytes` (the Codex default is 32 KiB) for all files together, and 0 turns the files off. The wrapper reads each file to the limit and one byte more, and checks the count of bytes before it decodes the text. The chief instructions with the files must stay within 256 KiB.
  - Each file must have no NUL, and must still be a regular file when the wrapper opens it (the open does not wait, so a named pipe that took its place is refused at once). A missing file and an empty file add nothing.
  - A file that breaks a rule is left out, and one line before the Ready lines says that the session starts without it and how to fix it, for example `[The session starts without the project file <path>: it has a NUL character. To give it to the chief, remove the NUL character, then start the client again.]` A file that the owner cannot read gives `you have no permission to read it` and `give yourself read permission (for example chmod u+r <path>)`; another read error gives its code after plain words, for example `the client cannot read it (error EIO)` (R1602-3). A file that makes the chief instructions pass 256 KiB says to shorten it, or the file that `--instructions` names (R1612-5). These two rules (a file over a limit and a file with NUL are left out, not cut) are decided differences from plain Codex.
  - Your own `AGENTS.md` in `CODEX_HOME` loads as in plain Codex, before the project files; the wrapper does not read it (R1602-4).
  - The form: the files, in order, between `# AGENTS.md instructions for <project>` and `<INSTRUCTIONS>` ... `</INSTRUCTIONS>`, as Codex gives them. Codex sends this text in the user role, but `thread/start` has no field for it (the fork's schema has `baseInstructions` and `developerInstructions` only), so it goes in a marked section of the developer instructions. Each `<` in a file and in the project path of the heading becomes `&lt;`, so the only `<` of the section are its own two marks: no text can open or close a mark and write text that looks like the sage instructions (R1601-2, R1611-2). One rule, with no list of the forms of an end mark, so a `<` before a look-alike slash is escaped too (R1620-6). A look-alike of `<` itself (such as U+2039 or the full-width U+FF1C) has no `<` and stays as it is. The heading path loses its line ends, tabs and each other hidden character (each becomes U+FFFD), so the heading stays one line (R1620-5).
  - The text keeps its line ends and tabs; each other character that the terminal filter (below) changes becomes U+FFFD, so no hidden text reaches the chief. A child agent gets the text only when the chief puts it in a brief. An agent can change a file, as with Codex itself; the chief gets the text of the start.
- It prints the binary path and its sha256, and a warning when `SAGE_CODEX_CONTROLLER_SHA256` is not set. When the project or a folder above it has a `.codex` folder (the disabled project layers) with more than skills in it, one line before the Ready lines says so: `[This project has Codex settings in <folder>/.codex. They do not load under sage: the project config, rules, hooks and agent roles. Skills still load.]` A `.codex` folder with only skills (and dot files) gets no line, because its skills load (R1602-1). The controller's own warning about these folders ("Project-local config, hooks, and exec policies are disabled ... until the project is trusted") does not show, because under sage a trust entry changes nothing. Then it prints the task, the run, the model, approval and sandbox of the owner's config, each in quotes, and how to use the client. A model that no layer sets shows `(the Codex default)` after it.
- On a terminal, the client reads each key (raw mode) and keeps the line itself, because a terminal in line mode keeps at most 1024 bytes of one line on macOS (`MAX_CANON`): a longer pasted line never came through, and Enter, Ctrl-C and Ctrl-D then did nothing. So a line of up to 65536 bytes, typed or pasted, is one turn (a longer one is refused with the line limit message). Enter sends the line; Backspace removes the last character; Ctrl-C clears the line (below); Ctrl-D ends the input on an empty line. The client echoes printable text and tabs only: a key sequence such as an arrow, and each other control character, is ignored. A key sequence that comes in two reads (an ESC in one, `[A` in the next) is kept until its end and then ignored too, so it adds no text (R1575-4); an ESC alone at the end of a read with no sequence after it is the Escape key. Raw mode turns off the terminal's own Ctrl-S, Ctrl-Z and Ctrl-\\ keys while the client reads. Raw mode stays on until the client ends, also after Ctrl-D during a turn, so Ctrl-C still stops that turn and the terminal does not echo text that no line takes (R1577-3). The client gives the terminal its line mode back at the end.
- On a terminal, the client turns on bracketed paste mode (`ESC[?2004h`) before the Ready lines, and turns it off at the end (also after a crash, from the exit handler of the entry). The terminal then puts marks around a paste: the text between them, with its line ends kept as `\n`, goes into the line, and the paste becomes one turn when the owner presses Enter (R1577-1). A control character inside a paste is text of the paste and is dropped; Ctrl-C there does not act. The Ready lines say that a paste of several lines is one line. Node's readline in terminal mode was the other option, but it draws the line again at each wrap of the terminal width: a paste of 12000 bytes into 80 columns took minutes. Input from a pipe is read by lines, as before.
- Each non-empty line is one turn, one at a time, sent unchanged. A line typed during a turn waits, and the client says so. Input from a pipe gives a paste of several lines as several lines. `commands.mjs` classifies the line: the client says that a mode phrase goes to the chief, or that a near line changed no mode, with the phrase that it means ("this") or the phrases ("one of these").
- It prints the agent messages of the root thread, each with `chief> ` before each of its lines (the line ends at the end of a message give no empty line, R1578-1), and each controller warning, each of its lines with the warning prefix. A warning that comes again (the controller can give the same one at each turn) shows once in a session. An approval request names the command and says that it did not run. Each turn result says what happened and what to do next; the fix for a refused line shows also when another typed line waits. The reasons of the controller process come in plain words (for example "the controller process ended by itself"), the same words for one event in each line.
- When a turn gets no controller event for 15 s (`WAIT_MS`), the client shows `[Waiting for the model. Press Ctrl-C to stop the turn.]`, once for each turn.
- Controller text never reaches the terminal raw. Each character of these classes becomes U+FFFD: the controls (`\p{Cc}`: C0, C1 and the newline in a client line too), the format characters (`\p{Cf}`: bidi controls, zero-width characters, the soft hyphen, tags, U+0600 to U+0605, U+180E, U+206A to U+206F), the line and paragraph separators (`\p{Zl}`, `\p{Zp}`), and every default-ignorable character (`\p{Default_Ignorable_Code_Point}`: variation selectors, Hangul fillers). So model text cannot move the cursor, write the clipboard, hide or reorder what the owner sees or print a line that looks like the client's. A config value on the Ready line goes through the same filter, in quotes.
- The client writes to its terminal without blocking, so a terminal that takes no output (Ctrl-S, or a stopped terminal) never stops it. When more than 8 MiB of output waits for the terminal (`TERMINAL_QUEUE_BYTES`), the client says so once, stops the turn, and drops output until the terminal takes output again (with input from a pipe, the message also says to press Ctrl-Q after Ctrl-S; in raw mode the terminal's own Ctrl-S is off, so it does not); the result of that turn says that the client stopped it. The client's result lines (each turn result, and the end of the session) wait while the terminal takes no output, and show when the stream says `drain`, so each turn shows how it ended, also when the terminal is still paused at its end. A turn that ran while output was dropped says that some of its output did not show.
- Ctrl-C (the key in raw mode, or SIGINT from a pipe session) clears the typed line and drops the lines that wait, and says how many it dropped; the first one also stops the active turn at once with a message (R1575-2, R1577-1). A line typed after that Ctrl-C runs when the turn ends, and the client says that it starts now, with the count when more than one waits (R1577-2). A second Ctrl-C on an empty line stops the controller, also before the chief is ready; a Ctrl-C that clears a typed line never stops the controller. SIGTERM stops the controller. The end of the input (Ctrl-D) stops the controller after the lines already typed; during a turn the client says that Ctrl-C stops it now. After the end of the input or a stop, the result of a turn says that the controller stops now.
- A lost terminal (SIGHUP, or an EIO or EPIPE on the terminal) stops the controller at any time, idle or in a turn, and the client writes nothing more. The client writes to its terminal without blocking and opens stderr at its start: after a terminal closes (macOS), a blocking write and the first open of stderr wait for ever.
- The controller runs in its own process group, so a terminal Ctrl-C reaches the client only. The controller still ends with the client: the client stops it on every path, and a killed client closes its stdin, which ends the controller by itself (the gated real test checks this).
- The exit code is 0 only after a stop that the owner asked for (Ctrl-C, Ctrl-D or SIGTERM). A refusal, a crash, a fence, an unknown turn result or a lost terminal gives 1.
- The controller gets the client's environment, so it uses the owner's `CODEX_HOME`, config, hooks and login.

## What it refuses

- A second `openThread`, an `openThread` before the start, a second turn while one is active, and any turn after a fence or a stop.
- Every server request, with error -32601. So an approval request is a refusal: with an approval policy that asks, the command does not run.
- A task id, run id, project, instructions or turn text that fails the checks in `bindTask` and `bindTurnText`.

## What it does not prove

- That the binary that runs is the one that was hashed: a swap between the hash and the launch is not detected.
- A managed config that marks the project as trusted. It wins over the launch flag; the `project-trusted` refusal covers it at `config/read` (fakes only, not run on the real binary).
- A child agent under the flag. The pinned binary started no child in the probe; in the source, a child keeps the disabled layers of its parent.
- Project rules and hooks at run time: the source reads them from enabled layers only. The real cases check that a rules file and a hooks file of the project change nothing, and that a project config written at `thread/start` loads no MCP server, feature or role.
- An owner trust entry that the owner adds after the `config/read` of the second controller and before its `thread/start`. The flag of that controller does not name it.
- That Codex treats a folder that no trust entry names as not trusted. QA saw it on the pinned binary (R1622 rsMove: a move into a folder below a trusted folder that is not a Git root loaded nothing, also before this change), but no test of the wrapper proves it from the source.
- That an agent cannot change `CODEX_HOME` (the owner's config). The Codex sandbox keeps it out of the writable roots; with `danger-full-access` nothing keeps it.
- That the native tool policy is safe for children (T391). The wrapper checks the launch profile and the root's tool names, not the children's tools.
- Real-model behaviour. The gated test in `controller-owned.test.mjs` uses a loopback synthetic provider.
- A bound on memory for a long session with no `onEvent` handler: then `events()` keeps every event of the process. The client gives a handler.

## Checks

Run each test file alone with `node --test`, with fake `ps`, `pgrep` and `kill` first on PATH. `controller-owned.test.mjs` replays `controller-fixture.json`, which comes from the labelled synthetic U3 transcript and the `config/read` format of the real fork binary. Its signal cases run the built client as its own process on a fake controller script, and send SIGINT to the process group of that client only. Its pty cases run the built client on a pseudo terminal (Python `pty.fork`, skipped when `python3` is missing) and close that terminal; one of them stops reading the terminal during a large chief message and checks that the client still runs the next line. Its ten real cases (the two case races and the linked worktree race need a file system that ignores letter case, such as APFS; the worktree race runs git with no user or system git config) run only when `SAGE_CODEX_CONTROLLER_BIN` names the built fork binary; `SAGE_CODEX_CONTROLLER_EVIDENCE` names a folder for their JSON evidence.
