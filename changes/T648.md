- **The last two move fixes before any real move (T648).** Fixes from the reviews of T647.
  - A command that waited on an old logbook's lock refuses while a move plan names that logbook, also when its root is another path to the same folder: through a link, or in another letter case on a volume that ignores case. Before, it wrote into the unmarked old logbook, and the move could not finish.
    - The path rule: two folders that exist compare by device and inode (`sameDir`), which every path to a folder shares. A folder that is gone compares by its path, as before.
    - Why not a realpath: Node's `realpathSync` resolves links but keeps the letter case that it was given. `realpathSync.native` gives the case on disk on macOS, but that depends on the system, and a case fold would need a test of the volume. The inode needs neither.
    - Why not the folder name: the new shared logbook has the same folder name as the old logbook that holds the move gate, so a match by name would also refuse the new logbook.
    - The same rule now also covers the move's own check for a stopped plan and the resolver's check before the lock.
    - A path in a plan that is missing or is no valid name (a NUL byte, a name too long) names no folder, so it is not this logbook. Before, it gave a raw error to every writer of every project.
    - A path in a plan that the system cannot read for any other reason (no right to search a folder on the way, a link loop, a disk error) may be another path to this logbook. So the command refuses, names the path and the error, and changes nothing. This also stops the writers of other projects until the owner fixes the rights or the plan.
  - A move that stopped finishes from the other provider also when that provider's roots are other paths to the same folders. Before, the finish refused and told the owner to check the plan file.
  - A round key whose finding closed before the move keeps its new key also after the next round. The move writes one decision row for each such key, with the key as its first word, so the key counter counts it. Before, the next round dropped the key, and a new finding of the task took it again, so the decision trail had one key for two findings.
    - A repair that accepts the loss of the decisions writes one row again for each round key with no finding (`F-T4-2 is a round key of T4 with no finding`), so the key stays taken after that repair too.
