- **Linked clones show as one project on the board, and the chief asks before each link (T633, PR 6b of the shared logbook).** A shared logbook with two or more linked checkouts is one project. A project with one checkout, and a legacy logbook, do not change.
  - The project picker's second line names the live checkouts in link order, for example `sample-owner/lantern · 2 checkouts: lantern, lantern-b`. A gone checkout does not count.
  - Two checkouts with one folder name show `lantern #1` and `lantern #2`, by link order, in the picker and on their runs. A number never moves to another folder. No page shows a checkout's path.
  - A row of `bindings.tsv` that links a folder to another project's logbook is one line in the board's Logbook notes, by its folder name.
  - "Show board" in a clone with no row no longer shows a shared project of the same folder name as if it were linked.
  - When a command stops in a new clone or in a folder with a wrong link, the chief asks you one choice, link or start separate, with a recommendation, and runs [`sage link`](docs/guide/using-sage.md#shared-logbooks) only after your answer.
  - The state tool's refusal holds the whole prompt, so the chief asks it word for word in both providers: the warning that no sage command can change the answer later, the numbered choices with the command of each, and the recommendation by GitHub remote (the same remote: link; another remote, a fork: separate; no remote: link). A row that names a missing logbook offers to restore it first.
  - The guide says that a shallow clone, or a clone whose first commit Git cannot read, gets a legacy logbook at `init`, which a later link refuses (T610).
