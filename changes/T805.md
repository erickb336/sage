- **A clean merge of main keeps a pull request's clean cycles (T805).** Before, a merge of main into the branch (or GitHub's update branch) made a new head, and the merge check wanted every cycle again, although the pull request's own change did not move.
  - The merge check counts the clean cycles of an earlier head H1 for the new head H2 only when each commit from H1 to H2 merges a commit of `origin/main` with no conflict and no other edit, the pull request's own diff has the same `git patch-id --stable`, checks-pass is on H2, H2 has no review or QA verdict of its own, and no commit between H1 and H2 has a review or QA verdict of the task (so a findings verdict on a middle head is never skipped).
  - The check reads each merge with the merge attributes of main, never with those of the pull request, so a `merge=union` in the pull request cannot hide a conflict. A Git without `--attr-source` refuses the carry.
  - sage's local git reads each commit's own parents: it ignores `info/grafts` and the commit-graph of the clone, as it already ignored replace refs, so a forged parent cannot put an unreviewed commit on `origin/main`.
  - Its line names both heads: `cycles from <H1> carried to <H2>: clean merge of main, same patch-id`. A refusal says why the cycles did not carry. Any git error refuses; when git does not know a commit, the refusal says to fetch origin.
  - The carry is all or nothing: a review or QA verdict on H2 replaces the carried cycles, and the refusal says so.
  - The board's merge check carries the cycles in the project's folder too, so the board and the merge check agree.
