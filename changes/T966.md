- **Codex's trust-once hooks: the install asks you first, and a few edge cases are fixed (T966).** The entry list does not change, so no entry needs your trust again. The launcher's version goes to 2: the start status asks for `hooks install` once, to copy the new launcher.
  - The gate's "not running" line and the start status no longer tell the chief to run `hooks install`. They say that you run the command, or say yes and then the chief runs it, and they give the exact command (F-T957-19).
  - `hooks install`, `uninstall` and `status` work on the Codex home that holds the plugin, also when `CODEX_HOME` is not set. They refuse when `CODEX_HOME` names another home (F-T957-25). The Codex guide says to use your `CODEX_HOME` in place of `~/.codex` (F-T957-24).
  - A hook that you put inside a sage group stays at install and at uninstall (F-T957-2, F-T957-10). A 0-byte or blank hooks file counts as empty (F-T957-20). The install says "1 sage hook", not "1 sage hooks" (F-T957-26).
  - When the newest version folder has no `hooks/dispatch.mjs` (for example an empty folder), the launcher refuses a shell merge or push, as for a broken install, and does not stay silent (F-T957-14, F-T957-15). Its backup refusal also reads the `gh api` forms of a merge and of a ref write (F-T957-18).
  - The trust count no longer counts a changed entry or a hook that you turned off in `/hooks` (F-T957-4). The status line now says how many sage hooks "are trusted".
  - The launcher reads no setting inside a TOML multi-line string (F-T957-13), and it orders build metadata of version folders as Codex does (F-T957-22). New tests check that `local` wins first and that a trust record keyed by the plain `~/.codex` path counts (F-T957-17).
  - The guide names a documented limit: the launcher reads only your Codex config file to see that the plugin is off, not a `-c` option, a profile or a managed policy (F-T957-16).
