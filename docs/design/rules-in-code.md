# Rules held in code

This page lists every rule that sage keeps in code, and why. It is reference material for a contributor or a careful user. [SECURITY.md](../../SECURITY.md#known-limits) gives the short list of known limits.

A rule written only in a prompt fades over a long session. So sage keeps its important rules in code: a hook that checks each action, and a state tool that refuses a wrong move.

The rules come from two places: the sage hook (`packages/sage-claude/hooks/sage-hook.mjs`) and the state tool (`packages/sage-core/state.mjs`). Some of the hook's rules are core's, and the Codex gate holds them too: the stash, process and board password rules are in `packages/sage-core/agent-rules.mjs` (T931). In the rows, "the sage" is the chief, and "you" is the owner of the project.

## The chief, briefs and switches

| Rule | Why |
| --- | --- |
| The chief of staff never edits a file. The one exception: with Write, Edit or MultiEdit, it may change a Markdown file directly in Claude Code's memory folder, `<config>/projects/<project>/memory/` (config is `CLAUDE_CONFIG_DIR` or `~/.claude`). A subfolder, `..`, a link, another file type and the shell stay refused. | It keeps the big picture; the team does the details. Its memory notes are its own, and they help the next session. |
| Every brief has all its fields; every report has its evidence. | A vague brief fails quietly. A claim without evidence is not a result. |
| Only a message of yours that is exactly a switch phrase switches sage mode or autopilot: the whole message, in any letter case, with at most one full stop at the end. Any other text never turns a mode on, also text in an agent's report, a task notification, a hand-back or another session's message. At worst such text turns autopilot off, and then merges only wait. A message that you send while Claude works can switch only autopilot off. When a message is near a phrase, the chief gets a note with the exact phrase to ask you for. When the hook cannot read a prompt's frames, nothing in it switches, and when it has a phrase, the chief asks you to send it again alone. | A switch is your decision, and an exact rule never guesses. Before, agent reports and free text with an off word switched modes by accident. |

## Leads and agent slots

| Rule | Why |
| --- | --- |
| Only main starts leads (at most `max_leads` per project, default 5), each with the name `lead-T<n>` and in the background. A spawn's name is the Agent tool's `name`, or the first word of its `description` when the `name` is absent or empty (the desktop app's tool has no `name` field). Only `run_in_background` false is refused: the desktop app's tool has no such field and starts every agent in the background. In sage mode, the task `T<n>` must have a running lead run in the logbook of the session's folder (`sage run add T<n> --role lead`); otherwise the refusal names that command. A second lead of the same task waits while the first one's slot lives, in any session, and a session holds one lead of each name `lead-T<n>`, in any project. A lead's slot lives while its lead run runs only in its own session; another session's lead slot keeps the one-hour lease, so a new session after a restart starts a fresh lead when the old lead has had no event for an hour, or at once when the chief ends the old lead run and records a new one (the refusal names both commands). The main session's TaskStop stops a lead by its agent id or by its exact name `lead-T<n>` (in any letter case), and a stopped lead starts no child. A stop by name is refused for a lead that started with no `name` field: Claude Code knows that lead only by its agent id, so the stop would fail and still free the slot of a lead that runs. A lead's TaskStop is refused, and so is any other agent's TaskStop of an agent (`R<n>`, `lead-T<n>`, `main`, or an agent id that a slot holds): only the main session stops an agent, so no lead or helper cuts a reviewer or QA off before its report. The rule reads `task_id` or the old `shell_id`, refuses a call with both at different values, and reads a name or an agent id after NFKC, without format characters such as a zero-width space, without spaces at its ends and in any letter case; so does the main session's stop of `lead-T<n>`. A helper still stops its own shell tasks; a lead stops none. The main session's stop by `shell_id` frees the slot too. A held task takes no run add, fix triage, finding close, verdict, `pr=` or `branch=` from anyone until the sage moves it; the sage may still triage a finding as ask, or dismiss it with a reason. A lead repairs only through `round`: while a medium or high finding is triaged fix and the task is not repairing, it closes no finding and records no verdict on a new commit. A lead's run counts only with a real child: the lead starts the child under the run's id as its name (`R<n>`; the hook refuses any other name), a child of the run's role, and the run ends (`run done`) only after that child stopped. Each lead verdict names such a run of its task, finished, of the task's current round and in no other verdict, whose role gives that kind (`--run`); a checks verdict is the sage's, and the hook refuses a lead's. The verdict must say what that child's report says, on the commit that it saw: at the child's stop, the hook keeps the first word of its RESULT, the severity of each finding in its FINDINGS, and the head of the task's branch if the branch did not move since the child started. The stop gate and the lead rules read a report with one reader. A field starts a line that is not indented, and Markdown around its name is fine (`**FINDINGS**`, `FINDINGS:`, a table row). Each line break ends a line, also U+2028 and U+2029. FINDINGS is `none` alone, or one line per finding in the form `- <key> <severity> <summary>`, where the key has a digit, with any detail on indented lines under it. The reader never lowers a severity and never reads a finding as none. A field given twice (also FINDINGS as an indented line or a list item), any other line under FINDINGS, a line there over 4,096 characters, a detail line whose first or second word is a severity word or that has a severity label (`high:`), or RESULT FINDINGS or FAIL with `none` makes the report unreadable, and the stop gate stops the agent once to fix it. A code block counts only from a fence indented by at most three spaces. A clean verdict (review-clean, security-clean, ux-clean, qa-pass) needs a clean report (CLEAN or PASS, or FINDINGS or FAIL with only low findings); `findings` and `qa-fail` need a report that is not clean, and `--sha` must be the commit that the child saw. The findings that the lead run recorded itself (the hook sees its own `finding add` print the key) must hold each medium and high finding of every stopped child of that role's runs, in any round, at its severity or above: one recorded finding for each finding of each run. A lead started again on the same lead run keeps them. A finding that the sage added never counts, also on an old key; the sage's dismissal, close or move of the lead's finding (once or more, by the move's own decision) still counts. Until they do, the lead adds no run of that role, records no verdict of that role (clean, findings or qa-fail) and makes no state move. A lead records no verdict on a run whose child gave no report, or a report that the hook cannot read: the sage reads it. A review or QA run whose report was not clean ends only after the lead records its medium and high findings, or after its findings or qa-fail verdict; the sage ends a run whose report it cannot read. A lead uses only the runs that it added itself: the hook sees its own `run add` print the id, of the role that the command asked for. A new lead never helps with, ends or uses an old lead's runs, nor the runs that the sage added, and the sage ends them. One run has one child, in any session and also after its slot's lease ends. A run whose child gave no report (it never started, it left with no stop when its slot's lease ended, or the main session stopped it) ends only as failed or blocked, and backs no verdict. While the child's lease is live, the refusal says to wait for its stop, with the minutes left, or to ask the sage. The merge check refuses while a review or QA run of a task still runs. A new lead's start removes the child notes of the logbook's ended lead runs. The state tool refuses a review or QA verdict whose `--run` already backs one of the task. While repairing, a lead closes only the round's fix findings (never one triaged ask), and only when the head of the task's branch is not a commit on which one of its review or QA children of an earlier round found problems (a re-review of the repair that finds a new problem does not count); it leaves repairing only after them; a new finding of the round waits for the next round. `round` also starts from repairing, for a fix key that a re-check did not confirm, with the same limit, hold and replan. A lead never changes the triage of a finding triaged ask. A move out of a hold that `round` set gives the task one more repair round, once per such hold; a hold for a question gives none. A retry whose last round's findings are still open goes to replan, as does any round that fixed none of the last round's findings. Leaving replan clears the old round's keys, so its findings no longer replan the task; the round number goes on, so the total stays capped by `max_rounds` plus the extra rounds. A move from held or replan back to briefed ends the task's running lead run, so the old lead writes nothing more and starts no child; the sage starts a new lead with the new brief. A lead with no bound lead slot starts no child, nor does a lead whose task is held, in replan, merged, concluded or abandoned, or whose lead run ended. A lead that is started outside sage mode gets no slot, so it starts no children: this is intended. The hook reads that logbook with the 4 MiB limit per table, and refuses when it cannot read it. In sage mode, and for a sage agent in any mode, an agent never names a spawn `main` or `lead-T<n>`. A sage type counts in any letter case. A lead starts at most 9 permitted children; other agents start none. A lead's stop is blocked, also a second one, while a helper of its lead run started, did not stop and holds its slot's lease; the block names the wait command, `node <plugin>/hooks/wait.mjs <T>`, which reads only the logbook and the hook's helper notes, and returns when such a helper stopped (with its kept RESULT, severities and commit), when none runs, or after 9 minutes. Only the sage ends a review or QA run whose report the hook cannot read, so its stop does not end the wait: the wait names that run once (a note in the helper notes) and lists each such run when no helper runs. In sage mode, the main session's SendMessage to `lead-T<n>` with no live lead slot of that task in the session, or to the agent id of a lead that ended or lost its slot, is refused: a message would wake it with no slot. The state tool holds the verdict rule (next section); the hook holds no copy of it (T815). While a task has a running lead run, the hook checks that the lead recorded its helpers' findings before the main session's review or QA verdict, in the verdict command's plain form. These rules hold in any mode for an agent's spawn of a sage agent. In sage mode, and for a sage agent in any mode, an agent sends SendMessage only to main, because a message can wake a stopped agent. Every sage spawn needs a full brief and shares the project cap (`cap.<project>`, otherwise `max_agents`, default 10, so one lead and its 9 children fit). `cap_total` (default 20, two full lead teams) remains a temporary fuse across projects. A slot stays until its own agent stops, the main session stops it, or the one-hour lease ends; a child's events renew its lead's lease, and a lead keeps its slot while a child runs or while its lead run runs in its logbook. The main session's `run done` of a lead's helper run frees that helper's slot at once and notes its stop. A spawn that fails, or that shows no start after 10 minutes, frees its slot. | Cost, focus and bounded nesting. |
| The logbook records a lead as a run with the role `lead` (`sage run add <T> --role lead`). A task has at most one running lead run, and a project at most `max_leads` (default 5); each refusal names the running lead runs. An investigation takes no lead run, because it has no build, and neither does a task that has ended (concluded, merged or abandoned); a verified task does, for its remaining cycles. A lead run counts in `status` and shows on the board with its role, as any run does. | The logbook agrees with the hook's limits, so a second lead for one pull request never starts from a stale record. |

## Waits and programs

| Rule | Why |
| --- | --- |
| Before you use waits, run `claude plugin update sage@sage` (see To update sage), then restart every session that was already open: an older session still merges a waiting task. A task can wait for other tasks of the same logbook (`sage task add ... --waits T7,T9`, or `sage task <T> set waits=T7`; `waits=` clears it). A wait is met when that task is merged or concluded. An abandoned task never meets it, and the refusal says to remove or change the wait, or to ask you. While a wait is unmet, the task takes no lead, implementer, investigate or arena-judge run and no move to building or to merged, and the merge check refuses it with each unmet task and its state. Its designer and PE runs, and its reviews and QA, go on. A wait on a task of the same pull request is met when that task passes the same merge check; a task of another pull request, or an abandoned one, does not meet it. To merge two tasks on one pull request, build both under the first task. The waiting task takes the same `pr=` and records its own verdicts with `--pr`, and gets its wait after its build. It moves to merged after the first one. The chief gives the waiting task the first task's `branch=` too, and autopilot merges the pull request when each task passes on its own verdicts. The state tool refuses a word that is not a task id, a duplicate, the task itself, more than 20 tasks, a task that the logbook does not have, and a loop, which it names (T8, T9, T8). Each change writes a decision row with the old and new list. `sage task <T>` and `status` show the waits and which are unmet. | Work that needs another task's result does not start, or merge, before that result is there. A loop never ends, so it is refused when it is written. |
| Before you use programs, run `claude plugin update sage@sage` (see To update sage), then restart every session that was already open: an older session still merges a task of a program that you did not approve. A program groups the tasks of one goal, with one pilot task. The sage frames every task first, then proposes once (`sage program propose --name <name> --goal <goal> --pilot <T> --tasks <T,T>`): that opens one gate on the pilot task. Its question names each task and what it waits for, one on each line, with no quotes. You approve, change or drop the breakdown; an answer in your own words says what to change. A breakdown gate answers once, also after a newer round replaced it, so a change of mind is a new proposal. Until you approve, no task of the program takes a lead, implementer, investigate or arena-judge run, a move to building or merged, or a merge. No task leaves the program before you approve or drop it. No task joins it while its gate is open, and no task of it changes its waits then: the sage asks you to answer change, then proposes again. No task of the program has or had the pilot's pull request before the pilot is merged or concluded, as that pull request could never merge: the state tool refuses it at `pr=`, `verdict --pr`, `program=` and `sage program propose`, from either side, in every state but dropped. A task that has started its build joins only after you approve and the pilot is merged. After you approve, each task but the pilot waits for the pilot in the same way, until the pilot is merged or concluded; the same-PR rule does not meet that wait. The designer and PE runs, and the reviews and QA, go on. After change, the sage proposes again (`sage program propose PG1`, with a new name, goal, pilot or task list), and the new gate says its round, for example "(round 2)"; the sage tells you in the chat what changed. A task that has ended stays in the program and its count. After drop, the program takes no new task, and the sage takes out each task that has not ended (`program=none`). The pilot stays in its program until a new pilot is proposed. A task that joins or leaves after your approval needs no new gate, and the sage tells you. The program's state comes from the answer of its breakdown gate on the pilot task: it is never stored, and any other gate reads as lost. The state tool refuses a bad or used name, a name of the form PG1, an empty goal or one over 300 characters, a pilot or task that has ended or is in another program, and a loop through a pilot, which it names with the wait to clear. `status` shows each program with its pilot and progress, also when it is done or dropped, and when its pilot was abandoned. A logbook made before programs has no programs file, and works as before. | Your approval of the breakdown comes before any build of it, and the pilot runs end to end before the other tasks build. |

## Git: pushes, merges and branches

| Rule | Why |
| --- | --- |
| One writer (implementer, designer or arena judge) per branch, in any letter case. Nobody force-pushes or pushes to the default branch. A push is only `git push [-u] <remote> <branch>`, to a remote of the checkout, with the branch's own name (T536). A push inside another command (`sh -c`, `eval`, `$( )`) or beside other commands meets the same push form (T909). | Parallel writers conflict. Work reaches main only through a pull request. A project's remote can have any name, so the rule reads the default branch, not the name origin. |
| An agent never merges. The merge rule and the push rule hold for every command tool: Bash, Monitor, PowerShell and the terminal tool. | An agent that reports a ready pull request leaves the merge to the chief or to you. A second tool must not be a way around the rule. |
| An agent never runs `git stash`, in any form. To test old code, it uses `git worktree add --detach <scratch> <sha>` or `git show <sha>:<path>`. | Every worktree of a repo shares one stash list, so another agent can pop or drop the work. |
| In sage mode, a code reviewer, security reviewer, UX reviewer, QA, PE, lead, investigate or evidence-review agent changes no files from the shell either: the hook refuses a command with a write form (core's `commandWrites`, by the role rule of core's `roleEditDenied`, as in the Codex gate), such as `sed -i`, a redirection to a file, `tee`, `cp`, `mv`, `rm` or `node -e`. A redirection into the temp folder, outside the project, passes, so the agent keeps its output and probes in its scratch folder. A sage role that core does not know counts as read-only. The implementer, the designer and the arena judge are not affected (T933). Their file tools write only there too, and the investigate agent may also write in the pages folder of its project's logbook, for its research page (T932). | Their agent files take away the file tools, but a shell write would change the code under review without a writer run. |
| An agent never lists or signals the real processes (`ps`, `pgrep`, `pkill`, `kill`, `killall`, `lsof`, `top`, `htop`, `fuser`, `pidof`, `launchctl`, and `kill-port` or `fkill` through `npx`, `npm exec`, `pnpm dlx` or `bunx`). Such a program passes only as a fake in the temp folder, found through PATH and links. A bare `kill` is the shell's builtin, so it never passes. The hook finds the program after shell keywords (`while`, `if`, `do`, `!`, `{`), redirections (`2>/dev/null ps`), wrappers and their options, inside a shell's `-c` text or stdin, and in the arms of a `case`. The arguments of a script (`bash ./x.sh kill`) and a `case` pattern are not programs. To stop its own server or background job, an agent uses TaskStop, or runs it as a background task. | An agent that reads or signals the real process list can stop your own programs. A `process.kill` inside a script is not visible to the hook. |
| A task's branch, and the branch of a writer run, is a plain task branch such as `claude/t12`: letters, digits and `. _ / -`. It is never main, master or HEAD in any case, and never a name under `refs/`, `heads/`, `remotes/` or `origin/`. | Git reads those names as main or as another ref, so a writer could reach main without a pull request. |
| An arena judge's run needs `--branch`, and it works on that new branch. While a task's arena step is open (its route has the arena block or it has a candidate run, and no arena-judge run of it ended done), an implementer or designer run needs `--candidate`, a whole number from 1. An implementer is no candidate of a large task before briefed: its arena is a design arena. `--add arena` on a tiny task also adds the code review, and a build route with no code review takes no candidate, because a graft is new code that nobody read. The state tool refuses a judge on a candidate's branch, a candidate on a judge's branch, and any other writer on a candidate's branch: only the same candidate of the same task and role runs there again. It refuses in both orders, in any letter case, also after a run ended. The move to verified, the move to concluded, the merge check and `sage-pr create` refuse an open arena step, and each refusal names the way out: finish a judge, or for a task that needs no arena, abandon it and frame it again. An abandoned task has no open step, so that way out does not end in a second refusal. All but the move to concluded also refuse a candidate's branch, also of an abandoned task, as the pull request's head branch or, with no `--head`, as the task's `branch=`, and a task with candidate runs and no branch named. A new command takes these rules; a replay of a saved update keeps the rules of its writer. They read the branch, not the SHA, so a judge with no graft lands the candidate's commit from its own branch. The chief names the judge's branch at `run add`. The judge makes it from the chosen candidate's head and stops if it exists; that step and "a candidate opens no pull request" are role rules, not code rules. A commit under a new branch name that no run records is a documented limit. | A candidate's branch is evidence, so no other run that writes takes it, and it never lands. A design arena goes on to a separate build, so the rule names what never lands, not what lands. |

## Pages, findings and repair rounds

| Rule | Why |
| --- | --- |
| Agents save their pages (research, designs, findings pages) in the task's pages folder, outside the logbook. The chief makes the folder with the state tool (only you can open it) and prints its path, and logs each page in it with its sha256. The state tool logs only a regular file of at most 16 MiB inside that folder, with no control character in its name. | A sandboxed agent cannot write the logbook, and the sha256 shows later that the page did not change. |
| Every finding is triaged: fix, dismiss with a reason, or ask you. | No finding is dropped. |
| A review or QA verdict on a task with a build needs `--run`: a done run of the task, of the role that gives the kind, with a kept report. The hook keeps a helper's report in the logbook (`kept/<run>.json`) when the helper stops: in Claude Code for each helper of a lead, and for each review or QA agent that the chief starts itself, whose brief starts with `Run R<n> · task T<n>`; and in Codex for each review or QA child whose task name carries its run. No command keeps a report. A clean report backs only a clean kind. A report with a medium or high finding backs `findings` or `qa-fail`, and a clean kind only after each of its medium and high findings is recorded for the run (by `--run`, or a key that starts with the run's id) and dismissed, moved or closed. The report's commit, as the hook saw it or as its BRANCH names it (the one full SHA, or the one after the word head when BRANCH names more), is the verdict's `--sha`. One run backs one verdict. The state tool refuses every other review or QA verdict, so the rule holds in every shell form. The hook refuses early only a command in which node runs a `sage.mjs` (in any letter case), or a path with a pattern or a variable, that it cannot read; a read of the file, such as `cat` or `git log`, passes. It reads `--project` as the state tool does, and refuses the verdict when it cannot read that logbook. | A text check of shell commands can never be complete, so the boundary is in the state tool. A verdict says what a review found, never what the sage relays. |
| At most 3 repair rounds (max_rounds); in autopilot the chief gives more with a reason, up to 5 in all. A round of low fix findings only starts too. | Loops must end. The chief judges a low fix and a near-done repair (owner, 2026-11-07, T804). |
| A repair round re-checks only the repair's diff, with the roles that found the problems. A new medium or low finding goes to a follow-up task; a high one blocks. | A round that re-reviews the whole branch finds new scope, not the fix. |

## The merge check and the logbook

| Rule | Why |
| --- | --- |
| An open medium or high finding blocks the move to verifying or concluded, the move to verified and the merge check. An open low finding never blocks a merge; it stays on the task's polish list, which the board shows. | A low finding is polish. Before this rule, the chief spent many steps to move or dismiss lows before each merge (owner, 2026-11-07, T671). |
| A `findings` or `qa-fail` verdict stops refusing its SHA only when triage clears it: the verdict's run links it to at least one finding (by the finding's run, or by the decision of its move), and each of those findings is moved, or dismissed below high with the triage dismiss. A row back on the task under a moved key counts as that finding, and an open low finding of the run does not count. A closed finding does not clear it, because a new head confirms a fix; a dismissed high finding does not either, and a closed finding is not dismissed. The verdict itself is refused until each medium and high finding of its run's report is on record for that run, at its severity or above, so a part of a bad report cannot clear it. With no link, the verdict keeps blocking, and a `checks-fail` verdict always does. A cleared verdict never counts as clean: the SHA still needs its clean cycles. | A moved or dismissed finding asks for no repair, so an empty commit must not be the only way past its verdict. A real failure must still block. |
| A merge needs the exact checked commit, with its clean cycles in the ledger. The hook reads the pull request's head branch from GitHub (`gh pr view`, at most 5 seconds) and refuses the merge unless each task that is or was on the pull request owns that branch, and each task of the logbook that owns that branch is on the pull request (`merge-check --head <branch>` runs the same check by hand). A task owns a branch by its `branch=`, by its name, or by a run of it on that branch, also after it moves to another branch. Two tasks share a pull request when both have its `branch=` and `pr=`: only the chief puts a task on a shared branch or takes it off one. A branch is shared when another task names it by its `branch=` or ran work on it, also a branch named for the task. A failed or slow read, or a pull request from a fork, refuses. Only a task in the logbook of the project being merged (the merge's folder) approves its pull request; a task of another project's logbook with verdicts on the commit must still pass. | A new commit is not checked until it is reviewed again. |
| Only the chief writes the logbook, except a lead on its own task (next row). An agent runs only the state tool's read commands (`status`, `merge-check`, `logbook`, `standing`, `config` with no `key=value`), with the copy of the tool that the hook loads, from Bash or any other tool that runs a command, also in a pipe or a chain. The hook judges the programs that a command line runs, as core's command reader sees them (T815): `node` (whatever its options) or the script itself that runs `sage.mjs` or `sage-pr.mjs`, Code that loads one of them (`node -e`, `-r`, `--import`) is a limit of the hook (below). Any other program may read their files. An agent never runs the PR script, never writes under the sage root with its own tools (in any case or Unicode form, also through a link), and never runs outside the sandbox. It never runs a shell write whose literal path is in the sage root or the shared root (core's `logbookWrite`): in a line with a write form, each word of a program that is not a reader, the value of a `key=value` or an `--option=value`, and each redirection's target. A reader is `echo`, `printf`, `cat`, `grep`, `rg`, `head`, `tail`, `wc`, `jq`, `ls`, `diff`, `cut`, `stat`, `file`, `cd`, `pushd`, `popd`, `tr`, `test`, `git`, `gh`, `node`, `sed`, `awk`, `sort` and `uniq`, by its bare name, and not with an option that writes or runs a program (`node -e`, `sed -i`, `awk -i inplace`, `sort -o`, `uniq IN OUT`, `rg --pre`, `file -C`, `diff -l`, `git diff --output`) or, for `git`, a subcommand that changes a checkout (`clean`, `checkout`, `reset` and the like). A word counts by its literal part, the text before its first `$`, backtick or pattern character, resolved from the program's folder (after a literal `cd`, `pushd` or `popd`, and `~` as the home folder), as written: only the roots are resolved through links. A word whose text holds a root's path counts too. zsh's clobber form (`>!`) makes every word count. In any line, a remove or a move of a folder that holds a root is refused too: a word of `rm`, `rmdir`, `unlink` or `shred`, of `mv` but its last word, or of `rsync` with a delete option, that names a root or a folder above one; for a pattern or a variable, the folder of its literal part counts (`rm -rf ~/*`). In any line, a word of `chmod`, `chown`, `chgrp` or `chflags` with `-R` is refused when it names a root or a path in one (`chmod -R 000 ~/.sage`), not when it names only a folder above one (`chmod -R u+w ~`). A `find` with `-delete` counts as a write: only a word that names a path in a root. `command -v` and `command -V` only look a name up, so they run nothing. A refusal names the word that caused it, in the command's own capitals. When the hook cannot read a line, it refuses it only when its text names a merge, a push, the state tool, `gh`, `git stash` or a process program. When the hook cannot check an agent's call, it refuses it. ## The PR script

| Rule | Why |
| --- | --- |
| The PR script, `sage-pr.mjs import\|create\|view\|merge <task>`, imports a task's commit for review, pushes the reviewed commit and opens, shows or merges its pull request. It takes exactly those two words. `import` copies the agent's bundle into the logbook's mirror (with fsck, so each object's hash is checked) and writes a review copy that agents cannot write: `review/<task>-<sha>/` in the logbook folder holds the commit's files, and `review/<task>-<sha>.diff` its change from main. The reviewers read only this copy, because git in the agent's own clone does not check the hashes, so an agent can make it show harmless text at the right SHA. `create` and `merge` refuse a commit whose review copy is not older than its first verdict: run `import`, and review again. It reads the branch and the reviewed commit only from the logbook, and the commit only from the bundle file that the agent wrote: a link, a second hard link, a file over 10 MiB or a file that is not a git bundle refuses, and so does a bundle whose tip is not the reviewed commit, the base branch, a branch of another task and a commit that is already on main. It refuses a project folder that is not the logbook's own checkout (`checkout.txt`) or that is in the worktree root, an origin that is not exactly `https://github.com/<owner>/<name>`, `ssh://git@github.com/<owner>/<name>` or `git@github.com:<owner>/<name>` (with an optional `.git`; a user or token, a port, a `#`, a `?`, another host or an upper-case host refuses), and a `SAGE_REPO` that is not the origin's repository. A `mirror.git` in the logbook that is not a bare repository (a file, a link, an empty or other folder) refuses: remove it, and the next call makes a new mirror. When GitHub lists 100 or more pull requests of the branch into main (forks' pull requests with the same branch name count too), it refuses, because the task's own can be missing from the list. It pushes fast-forward only and never a tag, opens a pull request only when the repository itself has none open from the branch into main (GitHub allows one), and records its number in the logbook (it replaces a closed one, or a number that GitHub does not have). It refuses a task with a merged pull request of its branch, also when the logbook has no PR number ("already merged as PR #n: nothing to create"), because after a squash merge the commit is not on main. It merges only that pull request, only when the task is verified or pr-ready (else it names `sage task <T> set state=verified`) and GitHub has the reviewed commit (else it names `sage-pr create`), only after the merge check, with `--match-head-commit`. Then it reads the pull request again: a merge queue that leaves it open is no success, and an error after GitHub merged (such as a branch deletion that gets 403) is still a merge. A pull request that is already merged gives "already merged" and exit 0 only when GitHub merged the reviewed commit; a merge of another commit refuses ("pull request #n merged <sha>, not the reviewed head <sha>: ask the user"). No message prints the origin, `SAGE_REPO`, a URL's user and password (also with punctuation), an `Authorization` header (also quoted or as key=value) or the value of a gh token variable. git and gh get only an allow-list of the environment's variables (no `GIT_CONFIG_*`, `GIT_SSH_COMMAND`, `GH_HOST` or proxy), no global git config, and a folder that agents cannot write; the script refuses to run with `NODE_OPTIONS` set. The whole call holds the logbook's lock, so two calls on one project never share the mirror. Exit 1 is a refusal of the script's own checks (or git's own answer that the mirror or the bundle is not one), and exit 2 a failed git or gh call (also a lock or disk error, or a call on the bundle that takes over 120 s) or a logbook that stays busy: run it again. A folder that the script cannot remove gives a warning, not another exit code. Exit 3 means that the merge happened but the mirror refresh failed: run merge again later, and it says "already merged" and refreshes the mirror. It is built but not in the route yet: agents still push, and the chief still runs `gh pr merge`. | In the coming sandbox, agents never push or call gh. One small script with a closed grammar is easier to check than every form of `git push` and `gh`. |

## The limits of the hook

The hook catches mistakes and the normal habits of an agent, such as a quoted branch name or a short ref like `heads/main`. It does three things:

1. **It refuses.** The merge rule and the push rule are allow-lists: a command that merges or pushes passes only in its one form, and each refusal names that form. The rules judge the programs that a command line runs, as core's command reader sees them (also in `env`, `command`, `sh -c`, `eval`, `$( )`, `xargs` and `find -exec`), never free text such as a commit message, a pull request body or a tool call's description (T815).
   - A merge is `gh pr merge` (after gh's own options), at any depth that the reader sees. Only the one merge form, as a command of its own, goes on to the merge check.
   - Each `git push` that the reader finds, also inside another command (a shell's `-c` text, `eval`, `$( )`, a known wrapper), must be the push form. A push beside other commands in the same line passes.
   - A push names a remote of the checkout (any name, never a URL) and the literal name of a branch that is not the default branch. `HEAD`, `@`, a pattern, a variable or a refspec with `:` or `+` is refused, and so are `--force`, `+ref`, `--mirror`, `--all` and a push with no branch.
   - The default branch is main, master, and the branch that GitHub names for the remote's repository. The hook reads it with a GET (`gh api repos/<owner>/<name> --jq .default_branch`, with `GH_HOST` and `GH_REPO` cleared), for each URL the push goes to (`pushurl`, else `url`). When GitHub does not answer, or the remote is not a GitHub URL, the hook refuses the push.
   - The hook reads the branch of the checkout where the push runs (the `-C` folder, a `cd` before it, or the session's folder), and refuses a push from the default branch.
   - `git subtree push`, `gh repo sync` and `gh repo edit --default-branch` are refused.
   - The command reader resolves a literal `cd ~`, `cd ~/<path>` and `pushd` of them to the home folder. After a `cd` that it cannot follow (`cd -`, `cd $X`), the folder of the later commands is unknown: only an absolute path counts, and a push there is refused unless `git -C` names its checkout. When the hook cannot read a command at all, it refuses the command when its text names a merge, a push or the state tool (for an agent, also `gh`, `git stash` or a process program). Every such refusal starts with the same words: the cause, the way forward (close each quote, substitution and heredoc, or run a nested command as a command of its own), then what the text names and that rule's form.
2. **It asks you in one case.** For a blank project, the chief creates main or master on GitHub for the first time. Only this whole command, from the main session, asks you: `gh api --hostname github.com -X POST repos/<owner>/<repo>/git/refs -f ref=refs/heads/main -f sha=<full commit id>`. An agent never gets this exception. The hook checks on GitHub, not in the local repo, that the branch is absent and that the commit has no parent. Then Claude Code's permission prompt shows you the repository, the commit, its number of files and its top-level names.
   - That commit reaches GitHub on a task's branch, and the first push to a blank repository makes that branch the default branch. The push rule then refuses the branch. So one more whole command, from the main session, asks you (T621): `gh repo edit github.com/<owner>/<repo> --default-branch main` (or `master`). The hook checks on GitHub that the default branch is not main or master, that the named branch is one root commit, and that the repository is nearly empty: at most 20 commits on the default branch, 5 branches and 3 open pull requests. So a repository past these counts never gets this exception, and a check that cannot read GitHub refuses. A root commit alone proves nothing, because any repository can have one on main. So the prompt shows the three counts, and you decide for a small repository that is not blank. An agent never gets this exception, and no agent pushes to main.
3. **The lock is GitHub branch protection.** After the first main or master, sage tries to turn it on, so that the branch changes only through pull requests. GitHub offers it for public repos, and for private repos on paid plans.

In sage mode, every app, MCP and dynamic tool other than sage's own runs with no sage rule, by the owner's choice, in Claude Code and in Codex. The hook checks only the tools that its matcher names: the file tools, the agent tools, the shell (`Bash`, `Monitor`, `PowerShell`, the terminal tools) and, in Codex, the sage logbook tools. For example, the Sites publish tool publishes a page with no sage check. In Codex, a `js` call of the desktop app's REPL runs too, also when its code runs a shell command ([the Codex guide](../guide/codex.md#the-rules-in-codex) gives the Codex rules). In Codex, in every mode, no thread runs `codex` from the shell except `codex --version` and `codex --help`, because Codex records the prompt of a resumed, forked or queued turn (`codex queue`) as the owner's typed message, also `autopilot on` (R1981-1).

The limits, said once: the hook and the lock stop mistakes, not an agent that acts on purpose. The hooks guard ordinary commands against honest mistakes (standing order 70, the owner's decision of 2026-11-08). A disguised form is a documented limit by default: GitHub's protection of main, the merge check, the sandbox and the owner's phrases are the guards against deliberate tricks. T815 and T909 cut the checks that existed only to stop a trick. These forms pass the hooks:

- A variable or a substitution in a program word or a path, and a pattern in a path or a plain argument. The literal part before the first expansion still counts: `rm <root>/p/*` is refused, `rm $ROOT/p` is not.
- A wrapper program that the reader does not know (`arch -arm64`, `op run --`, `script -q /dev/null`), an alias, an unusual option order (`gh pr -b view merge 12`), and a known wrapper inside `find -exec`.
- A merge or a branch write through GitHub's API (`gh api`, GraphQL, `curl`, `wget`). GitHub's protection of main is the guard. An agent's `gh api` still runs only with GET.
- A git alias, a `git-<name>` program, a gh alias, a gh extension, and a renamed copy of gh or of Codex.
- A git setting that redirects a push (`remote.<remote>.push`, `remote.<remote>.mirror`, `url.<base>.insteadOf`, `push.default` upstream), a symbolic branch, a local `refs/remotes/<remote>/HEAD` that disagrees with GitHub, and a command beside a push that changes them. A git hook, `core.hooksPath` and a write under a `.git` folder (T909 Q1: that rule also refused honest setups such as husky). The hook does not read the git settings that run a program either: `include.path`, `core.sshCommand`, `credential.helper`, `core.pager` and filter drivers.
- Code that pushes, merges or builds a logbook path, or that loads the state tool: a script, `node -e`, `node -r` or `--import`, `python -c`, `awk` and the like, and a file that a later command runs.
- Text piped into a shell or an interpreter (`echo '…' | sh`, `cat <<EOF | python`) or given to a remote host (`ssh`), and a program that `find -exec` runs through a shell (`-exec sh -c '…'`).
- A path through a link. The hooks judge a word as written and resolve only the roots, so `rm` of a link to a root removes the link and passes (F-T903-10), and a write through such a link passes too. The board rule reads a path as written in the same way. A folder known only at run time: a `cd` to a variable, or a relative `Set-Location`.
- A PowerShell command is read as shell text: `Start-Process`, backtick escapes and PowerShell's own quoting are limits.
- A severity word in look-alike letters of another script (Cyrillic, Greek) in a report. A gate question that starts with look-alike letters or a filler letter (U+115F, U+3164, U+FFA0) before "Approve program" is not read as a breakdown gate (F-T909-4). Full-width letters and zero-width characters still count.
- A `find` with `-delete` and no name filter over a folder that holds a root (`find ~ -delete`, `find / -delete`) passes: the rule cannot tell it from a `find` that deletes only matched files (F-T903-7, F-T909-6). A word that names a root or a path in one still counts (`find ~/.sage -delete`).
- Text that only a trick hands to a shell (T910): the shell text of `watch` (`watch 'gh pr merge 1'`), the split string of `env -S`, a shell function's call (the reader reads the function's body where it is defined, not at the call), and a `CDPATH` or a `HOME` that the line itself changes (`export`, `unset`, `HOME=… cd`): the reader resolves `cd` from the folder alone and `~` from the hook's own home.
- The Codex gate's state tool rule does not find `sage.mjs` after a `node` option that takes a value in the next word and that the rule does not know (`node --env-file .env sage.mjs`), so that run passes the rule (F-T909-10).
- `chmod -R u+w` of a sage root itself, or of a path in one, is refused like any recursive mode change of a root, although it only adds a right (F-T909-11). Run it on a folder above the root, or ask the chief.
- gh settings that run another program (a pager, an editor, a browser) and gh's config folder.
- The Codex gate follows the same rule (T903, T909). A child's gh meets core's agent list, as in the Claude hook; the chief's gh meets the merge and push rules. Its config file rule reads `config.toml` by a literal path. Its logbook rule is core's `logbookWrite`, with the Codex sage folder and the shared root as the roots, in every mode: a write whose literal path is in a root, a patch of a file there, and a remove or a move of a folder that holds one are refused. A read of a root passes. A `find` with `-delete`, and `chmod`, `chown`, `chgrp` or `chflags` with `-R`, count only when a word names a root or a path in one (F-T903-7, F-T909-5). A logbook file's name in another folder (`../tasks.tsv`) and a write target with a variable or a pattern (`> $DEST`, `> out*`) pass. A patch into a `.git` folder still meets the patch's checkout rule of `managed-worktree.mjs`.
- The main session's verdict command in a wrapped form (`env node <tool> verdict …`) skips the hook's gap rule for a running lead; the state tool still refuses a verdict that no kept report backs. An agent that holds your GitHub token can remove the protection or merge a pull request. The guard against that is identity: agents get a GitHub identity that cannot merge or change main. That identity is planned and not built yet.

A round hold resumes only with an unused, explicit owner approval for that task, spent round count and current limit. `task set state=building approval=<G>` (or `state=briefed`) grants one round above the greater of spent rounds and the limit. The task records the used gate with its allowance in one row. Retries grant nothing more; earlier allowances and clean-cycle requirements remain.
