# The merge check and the config

Each row gives a command of the sage state tool and its full rules. Run each as the sage skill says: node, the state tool's absolute path and the command, without quotes.

| Command | Does |
| --- | --- |
| `merge-check --sha <sha> [--pr <n> [--head <branch>]] [--cycles <n>] [--chief C<n>]` | Says if the full SHA may merge. With `--chief` on a shared logbook, it judges for that chief, as the hook does for its session: a live task of another chief refuses. A task that a Claude chief took from a Codex chief through a takeover gate needs one Claude cycle on this SHA after the owner's answer: run one cycle of its reviews and QA on this SHA, record each verdict, then merge with `gh pr merge`. The cycles of both providers count together, in one ledger. Each task that has verdicts on it, in every project's logbook, must pass on its own verdicts: no open findings, no review or QA run that still runs (end it first, with its report's findings recorded), checks-pass, and its route's verdicts in the clean cycles of its size and risk (see "Cycles and merges"). In the project's folder, the clean cycles of an earlier head count after clean merges of main, and the line names that head. `--cycles` raises the count of every task to at least that number; it never lowers a task's own count. A logbook that is a link to a folder counts too. With `--pr`, each task of that pull request must pass too, and the pull request must have one in the logbook of the project being merged (`--project`, `SAGE_PROJECT` or the current folder; for the hook, the merge's folder): a task of another project's logbook never approves the pull request, but its verdicts on the SHA must still pass. With `--head` (not empty), the pull request's head branch on GitHub (`gh pr view <n> --json headRefName`), each task that is or was on the pull request must own that branch: its `branch=`, a branch of the task such as `sage/t12-x`, or the `--branch` of a run of the task, also after the task moved to another branch. Each task of the logbook that owns that branch must be on the pull request too, so a task on another task's branch never merges that task's work on its own verdicts. An arena candidate's branch never merges: the check refuses it as the head branch or, with no `--head`, as the task's `branch=`, and it refuses a task with candidate runs and neither. It also refuses a task whose arena step is open; an abandoned task has none. `task <T> set state=verified` refuses the same cases, so no candidate reaches the user as ready. `task <T> set state=concluded` refuses an open step too. The sage hook reads the head branch from GitHub for each merge and passes it; when it cannot read it in 5 seconds, or the pull request comes from a fork, it refuses the merge. A refusal lists every task that fails and its way out. The tasks of a pull request are each task that was ever on it: by its `pr`, by a `PR <old> → <new>` decision row, or by a verdict on a commit with that `--pr`. A cleared or changed `pr=` does not take a task out: it stays in the merge check until the user merges. A logbook (a folder with tasks.tsv) that fails the logbook check refuses every merge and names the file. A folder outside the known project list (`projects.tsv`) that has verdicts on the SHA refuses the merge and is named. `init` adds only a project's own folder, so for a renamed folder or a link the user gives the folder back its name, runs `projects rebuild`, or removes the folder. The first command of this version, the merge check too, finds neither `projects.tsv` nor `projects.made` and lists each folder with tasks.tsv or ledger.tsv once (`how` is `migration`); it writes `projects.made` first. After that, a missing `projects.tsv` refuses every merge and every `init` until the user restores it or runs `projects rebuild`. A `projects.tsv` that is a link, not a regular file, or has no header line refuses every merge and names the rebuild. |
| `lint <T> --sha <sha>` | Lints the head with the rules of the tip of `origin/main`, which must have `sgconfig.yml` at its root, else lint records nothing and the merge check needs no lint verdict. It scans only the lines that the head adds since its merge base with `origin/main` (moved and edited lines too, and every line of a renamed file, under the rules of its new path), with ast-grep 0.51.1 and the rules, `sgconfig.yml` and `.gitattributes` of `origin/main`, so a change to them at the head does not count. With no `origin/main` and a root `sgconfig.yml` in the checkout, lint and the merge check refuse. It records lint-pass, or lint-fail with each problem: a match on an added line (file, line, the rule's message), a changed file that holds ast-grep's suppression comment (the whole file fails), a file that ast-grep skipped (not UTF-8), or a file of more than 10 MiB. It lists the files that it did not check: a symbolic link, a submodule, a file marked linguist-generated or linguist-vendored in `origin/main`, a file with no ast-grep language or no rule. `verdict` refuses both kinds. A lead may run it on its own task. When ast-grep 0.51.1 is not in the project's `node_modules/.bin` or in sage's tools folder, it refuses and prints the command that installs it. |
| `config [key=n ...]` | Prints or sets max_agents, max_leads, cycles.small, cycles.large, cycles.risk, max_rounds, arena and cap_total for all projects, and `cap.<project>=n` for one project's agent cap (the project's name is its main checkout's folder name, as a slug: `cap.sage=5`). Each is a whole number of 1 or more; cycles.large and cycles.risk are 2 or more (the owner's floor: only a code change lowers it). The limit is 10 for the cycles and max_rounds, and 50 for the others, so that a typo cannot block every merge or start too many agents. One rule reads every count in `config.json`. The count is a number, or a string of a number with spaces or leading zeros allowed (`2.5`, `"03"`, `" 3"`). A cycles count rounds up, and any other count rounds down (`2.5` reads as 3 cycles, but as 2 agents). Below its floor a count reads as the floor (`0` or `-1` reads as 1, and cycles.large of 1 as 2). Above its limit, a cycles count keeps its value (a merge never gets easier), and the merge check's reason names the key and its value in `config.json`; any other count reads as the limit. So a count in `config.json` never starts more agents or rounds, or asks fewer cycles, than written. A cycles key with no number (`"abc"`, `true`, `[3]`, `1e400`) refuses every merge: `config` prints it as `invalid`, and the merge check names the key; set it with `config` or remove it. Any other count that is missing or has no number (`"3x"`) gives its default. max_agents (default 10: one lead and its 9 children) is the cap of a project without its own; max_leads (default 5) is the most running leads of each project, read by `run add` and the hook, and a value below the running count ends no lead, it only refuses the next one; cap_total (default 20) caps the agents of all projects together, and it wins. It refuses a `key=value` with a second `=` (`cycles.large=3=4`). A change keeps the other keys in `config.json`, also those of a newer version; it refuses when `config.json` is a link or not a regular file. An older sage's `autopilot_cycles` in `config.json` counts as cycles.large when cycles.large is absent, never below the floor; one with no number is an invalid cycles.large. When autopilot turns on, its note names a cycles key with no number instead of the counts. It also sets an agent role's model: `model.<role>.<size>=<model>` for one size of task, or `model.<role>=<model>` for every size. A role is pe, designer, implementer, code-reviewer, security-reviewer, ux-reviewer, qa or arena-judge; a size is tiny, small, large or investigate; a model is opus, sonnet, haiku or fable. The Balanced defaults use sonnet for UX review, QA of tiny and small tasks, and code review and implementation of tiny tasks. Other configurable roles and sizes use opus. `model.<role>.risk=<model>` overrides the size choice for a task with a risk flag. `model.qa.small=inherit` clears a key: then `model.qa` counts, else the agent's own model. A bad model, or one in `config.json`, gives the default. The model keys print after the numbers. |
