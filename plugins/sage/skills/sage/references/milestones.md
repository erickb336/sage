# Milestones and releases

Each row gives a command of the sage state tool and its full rules. Run each as the sage skill says: node, the state tool's absolute path and the command, without quotes.

| Command | Does |
| --- | --- |
| `milestone propose --name "<name>" --goal "<goal>" --pilot <T> --tasks <T,T>` · `milestone propose <M> [--name "<name>"] [--goal "<goal>"] [--pilot <T>] [--tasks <T,T>\|none]` | Writes a milestone (`M1`, `M2`, …) for a request of two or more tasks with one goal. Frame every task first, then propose once: it puts the pilot and the other tasks (`--tasks`) in the milestone and opens the breakdown gate on the pilot task (options approve, change, drop; recommendation approve). The board shows it under "Needs you". The gate's question has one part on each line, with no quotes: the fixed first line `Approve milestone M1? No task builds before you approve.`, then `Name: <name>`, `Goal: <goal>`, `Pilot, runs first:` with the pilot, and `Then, each after T1:` with each other task, one on each line as `  T2: <title>`. A task's waits other than the pilot, or an ended task's state, come in brackets after its id, before the colon, for example `  T3 [waits for T2]: <title>` or `  T4 [merged]: <title>`, so a title cannot pass for them. A title, name or goal prints as written, but each line break prints as a space, hidden characters are removed, and spaces are single; an empty title prints as `(no title)`. So no text adds a line. The `status` line of each milestone puts the name last, after `name:`. The `status` gates line shows a breakdown gate's first line and its count of tasks, only for the gate that the milestone's row names, on its pilot, with the options approve, change and drop (any other gate shows on one line, whatever its text), for example `G1 Approve milestone M1? No task builds before you approve. (breakdown, 3 tasks)`; the board shows the whole question. The milestone's state comes from the answer of that gate, on the pilot task: proposed while it is open, active after approve, dropped after drop, changing after change or the user's own words (they say what to change). Any other gate reads as lost. A breakdown gate (each gate whose question starts with that first line, also one that a newer round replaced) answers once: `gate answer` refuses a second answer, so a change of mind is a new proposal. Only `milestone propose` writes that line: `gate add` refuses a question that starts with `Approve milestone` or the old `Approve program`, in any letter case, also after blank, mark or symbol characters. Letters of another script that look like the Latin ones (Cyrillic, Greek) and filler letters are a limit: `gate add` does not read them (F-T909-4). Any other gate takes a new answer. `milestone propose <M>` proposes it again after change, or for a new pilot: a new gate whose first line says its round, for example `Approve milestone M1 (round 2)? No task builds before you approve.` The round counts the milestone's earlier breakdown gates. Tell the user in the chat what changed. Without `--tasks` the milestone keeps its tasks (the old pilot too); with it, the list is the new one, and a task that it leaves out leaves the milestone. An ended task (merged, concluded or abandoned) stays in the milestone either way: it counts, and the question lists it with its state. The name is 1 to 60 characters, unique in the logbook (case and width do not count) and not of the form `M<n>`; the goal is 1 to 300; both have no space at an end or two together and no control, format or hidden character. It refuses a pilot or task that has ended (for a re-proposal whose pilot ended, it asks for a new one with `--pilot`) or is in another milestone, a task that has started (past briefed, or with a lead, implementer, investigate or arena-judge run that runs), an open breakdown gate, a dropped milestone, and a loop, which it names with the wait to clear. When a proposal stopped before it wrote its gate, the same command finishes it, and writes the decision row of each task that it put in the milestone. A drop holds also after a loss of `gates.tsv`: the decision row of the user's answer says it. |
| `task <T> set milestone=<M>` · `milestone=none` (or `milestone=`) | Puts the task in a milestone, or takes it out, for a task that joins later. Until the user approves the breakdown, no task of the milestone takes a lead, implementer, investigate or arena-judge run or a move to building, merged or concluded, and the merge check refuses it. After the approval, each task but the pilot waits for the pilot in the same way, until the pilot is merged or concluded: a pilot wait never passes in the same merge. Its designer and pe runs, and its reviews and QA, go on. The refusal names the fix: ask the user to answer the gate, propose again after change, propose a new pilot for an abandoned one, or take the task out of a dropped milestone. No task leaves a milestone before the user approves or drops it; the pilot stays until a new pilot is proposed (it may leave a dropped one). It refuses an unknown or dropped milestone, an ended task (merged, concluded or abandoned: it neither joins nor leaves a milestone, so its milestone keeps it in its count), a task that joins while the breakdown gate is open (its question does not name the task: ask the user to answer change, then propose again with `--tasks`), a started task that joins before the user approves the breakdown and the pilot is merged or concluded, and a loop through a pilot, which it names. A task joins while the user asks for changes: the next proposal names it. No task of the milestone changes its `waits=` while the breakdown gate is open, as its question shows them: ask the user to answer change, then propose again. No task of a milestone has or had a pull request of its pilot before the pilot is merged or concluded, as that pull request could never merge: in every state but dropped, `pr=`, `verdict --pr`, `milestone=` and `milestone propose` refuse it from either side, also for a PR that a task had before, and name the way out (another PR, or the task out of the milestone). A task that joins or leaves after the approval does so with no new gate: the line ends with `joins M1 after the owner approved its breakdown: no new gate, so tell the owner` (or `leaves M1 …`), and you tell the user. Each change writes a decision row (`milestone <old> → <new>`). `status` shows each milestone on its own line, with its pilot and progress, and its name last, for example `milestone M1 · pilot T1: 2 of 4 merged · T4 abandoned · name: Codex support`: the count keeps every task of the milestone, and names each abandoned task. A milestone is done when each task that is not abandoned is merged or concluded (`milestone M1 · done, 3 of 4 merged · T4 abandoned · name: Codex support`), a dropped one names the next step for its tasks that have not ended (`milestone M1 · dropped: 4 tasks still in it, take each out with milestone=none · name: Codex support`), and a milestone whose pilot was abandoned says `pilot T1 abandoned: choose a new pilot, or drop the milestone`. |

| `release add --name "<name>" [--goal "<goal>"]` | Adds a release (T1003): a version that the owner ships, such as 1.0. A release holds milestones and single tasks (tasks outside a milestone), and it is optional: a logbook with no release reads and writes as before. The releases keep the order in which you add them, so the next release is the next one that you added: a name such as Beta does not sort. The name is 1 to 60 characters, with the rules of a milestone's name, unique in the logbook (case and width do not count), not in the form of an id (`T12`, `M5`, `G3`, `R7`, `C2`, `PG1`), not `none`, and with no comma or middle dot (`·`). The goal is 1 to 300 characters. Shipping a release (a tag, a publish) is the owner's action: sage records no ship. |
| `milestone <M> set release=<name>` · `release=none` (or `release=`) | Puts a milestone in a release, moves it to another one, or takes it out. A milestone is in at most one release, and each of its tasks is in that release. Nothing moves a milestone by itself: when the owner says that a release ships, move each open item to the next release with one command each. The value names the release in any case or width, and the cell keeps the release's own name. It refuses a release that the logbook does not have (add it first), two names (`release=1.0,1.1`, or `release=` twice) and any other key. Each change writes a decision row: `M5 release 1.0 → 1.1`. |
| `task <T> set release=<name>` · `release=none` (or `release=`) | Puts a single task (a task outside a milestone) in a release, moves it, or takes it out, with a decision row `release none → 1.0`. A task of a milestone is in its milestone's release, so the command refuses it, and names the two ways out: set the milestone's release, or take the task out of the milestone first. A task that joins a milestone (`milestone=` or `milestone propose`) leaves its own release, with a decision row `release 1.0 → none`, and the line says so. `status` shows one line for each release, in the order of the releases, before the milestone lines: its state, the count of its tasks (the tasks of its milestones and its single tasks), its milestones, its single tasks and its goal last, for example `release 1.0 · in progress · 1 of 10 tasks done · 1 stopped · milestones M5 · single tasks T993, T996 · goal: <goal>`. The state is not started (no item, or no item started), in progress, done (each item is done or stopped, and one is done) or stopped (each item is stopped). A dropped milestone counts as stopped. The line of a milestone in a release names it: `milestone M5 · release 1.0 · pilot T984: …`. A release cell that names a release which the logbook does not have keeps its items in a line that says `not in the logbook`. |

**The update window (T1003).** An older sage reads a logbook with releases. A release alone adds only `releases.tsv`, which an older sage does not read, so it still writes the logbook. Once a milestone or a task has a release, the table has a release column that an older sage does not know: it refuses every write, says that a newer sage wrote the logbook, and changes nothing. Update sage in each Claude Code and Codex session before you put items in releases.

**The rename (T995).** Milestones were called programs (`PG1`, …) before. The first write of this version renames a logbook's programs to milestones, with the next free ids after the id floor, and writes a decision row for each one, such as `M5 was PG1`. A read before that write shows the same milestones. An answered gate and the old decision rows keep their words. The old words `program propose`, `--program`, `program=` and `release <T>` (now `unclaim`) work for one more version, and each prints a note with the new word. An old id such as `PG1` names its milestone through those decision rows there, and the line names the new id. A damaged programs.tsv refuses the first write, which changes nothing: restore it, or run the repair that the refusal names.
