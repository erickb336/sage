# The arena

The chief runs an arena with these steps.

For a design with no clear answer, or when the user says "arena" or "arena N": frame the task with `--add arena --why "<reason>"`. You run the arena yourself, before any lead.

**A large task's arena is a design arena.** It stands for the route's design block, so start no other designer, and its order is arena, PE, the user's approval, build. A build arena runs only on a tiny or small task, or on a briefed task after an approved design.

**The arena step is open** while the route has the arena block or the task has a candidate run, and no judge of the task ended done. While it is open, the state tool refuses an implementer or designer run with no `--candidate`. It also refuses `task set state=verified`, `task set state=concluded` and the merge check. To close the step, finish a judge. For a task that needs no arena, abandon it and frame it again: `--candidate` on a build's run marks the build's branch as a candidate's. An abandoned task has no open step, but its candidate's branch still never merges.

**A tiny arena has the code review,** because a judge's graft is new code that nobody read: `--add arena` adds it to the route. It has no QA, and its cycles follow from its route.

1. **Write the rubric:** 3 to 6 criteria from the acceptance that a judge can grade. Log it with `sage log <T> "<rubric>" --why "arena rubric"`. The candidates do not see it.
2. **Start N candidates** (3 by default) in one message: designers or implementers, with the same brief and a different angle each. A large task before briefed takes only designers: move a framed task first with `sage task <T> set state=designing`. A large task at briefed, after an approved design, may take implementers. A candidate run opens the step on a task with no arena block, but the state tool refuses a candidate on a route with no code review, such as a tiny task framed with no arena. For candidate k, run `sage run add <T> --role <role> --branch sage/t<n>-c<k> --candidate <k>`. Mix the models as `sage config` says (arena_models, by default opus, sonnet, sonnet): pass the model that `run add` prints in the agent call. Each brief names its branch, a worktree, the folder of `sage pages <T>` and its page name: `<R>-artifact.html` for a designer, `<R>-artifact.diff` for an implementer. A candidate opens no pull request.
3. **Record each candidate:** `sage run done <R> --status <its STATUS> --tokens <n>`, then `sage pages <T> record <folder>/<page name>`. An artifact that is not committed does not count. A candidate that ends blocked keeps its report, branch, head and partial files: decide if its evidence meets the brief, and tell the judge. To correct a candidate, add a new run on a new branch, such as `sage/t<n>-c<k>-2`. The old run stays.
4. **Start `sage:arena-judge`.** For a build, first run `sage task <T> set branch=sage/t<n>-judge`. Then run `sage run add <T> --role arena-judge --branch sage/t<n>-judge`: the state tool refuses a candidate's branch. Give the judge the rubric, the brief, each candidate's branch, worktree and report, its own branch, and whether the arena is a design or a build. For a design, also give the folder of `sage pages <T>` and the page name `<R>-final.html`, with the judge's run id as `<R>`. The judge makes its branch from the chosen candidate's head, and it stops if the branch exists. It scores each candidate, picks the base, grafts the best parts of the others into it on its own branch, and checks the result. When all candidates converge, it keeps the shared shape.
5. **Record the judge's report** with `sage run done`, then go on from its STATUS:
   - done: the arena step is closed. Show the user the judge's scores, base, grafts, rejections and empty candidates in one short message, from its RESULT. Then go to step 6 for a build, or step 7 for a design.
   - question: the candidates diverge on the product. The report gives both choices with a recommendation. Ask the user with `sage gate add`, then add a new judge run on the same branch, with the resolved brief.
   - blocked, with no usable candidate: there is no winner and no result. Resolve the brief: start new candidates on new branches, or abandon the task.
   - blocked, because its branch exists: take a new name, such as `sage/t<n>-judge-2`, set it with `task set branch=` for a build, and add a new judge run.
   - failed: there is no result, and the arena step stays open. Do the same: a new judge run on a new name, set with `task set branch=` for a build.
6. **A build goes on from the judge's draft pull request.** Move the task one state at a time to briefed, building and reviewing, with `pr=<n>` on the last move, where `<n>` is the PR in the judge's report. Then record a lead run and start one `sage:lead`, as **Run the route** says, with the judge's branch and PR in CONTEXT. It starts at reviewing. The reviews and QA of the route check the branch like any build, and a repair needs no `--candidate`. At verified, run `gh pr ready <n>`, then merge or tell the user as usual.
7. **A design goes to the PE.** The judge opens no pull request. It saves the final design in the pages folder, and its RESULT gives the page's path. Record the page: `sage pages <T> record <path>`. Run the PE on the judge's branch and that page. Move the task to awaiting-you, through designing when it is framed. Then ask the user to approve the design with `sage gate add`, and name the page in the question: the user reviews the page, not a branch. After the approval, move the task to briefed. The build starts as for any approved design: one lead, on a new branch from main (`sage/t<n>`), not on the judge's branch, so that the prototype and its sample data stay out of main. The lead's brief names the judge's branch as the design to build.
8. **A candidate's branch never merges,** also for an abandoned task: `task set state=verified` and the merge check refuse it, and a candidate opens no pull request: the judge of a build pushes its own branch and opens it (step 6).
9. **Keep the evidence.** Candidate branches and pages stay until the user deletes them, and so does the judge's branch of a design. A merge deletes the branch that it lands: its commits are in main. Worktrees go at the end of the task.
