# The sage state tool

The chief of staff keeps the work in the project's logbook, not in the conversation. Then a session on the phone or the desktop can continue it. Each command prints one line. A refused command prints the reason and exits with 1: do what the reason says, and do not work around it.

Run it as `node ${CLAUDE_SKILL_DIR}/sage.mjs <command> --project <path to the project>`: node and the absolute path, without quotes. In the sandbox, only this form runs outside it; a quoted path, a variable, a `cd … &&` or a pipe stays inside, and the logbook write fails.

Only the chief writes the logbook. The sage hook lets an agent run only `status`, `merge-check`, `logbook`, `standing` and `config` without `key=value`, as one plain command with no quotes: `node <path>/sage.mjs <command> [--project <path>]`, with the copy of sage.mjs that the hook loads. A command that names `sage.mjs` or `sage-pr.mjs` (in any case, also in quotes) may run only plain readers: `cat`, `grep`, `rg`, `head`, `tail`, `wc`, `ls`, `diff`, `shasum`, `jq`, `awk` and `sed` without `-i`, and `git show`, `log`, `diff`, `status`, `blame`, `grep`, `ls-files`, `add` or `commit`. Any other program in it is refused and named: `node`, `python`, a shell, `eval`, `echo`, `env` or `xargs` with it, whatever their options, also behind a shell keyword such as `for`, `while`, `if`, `{` or `!`. The one exception is the plain read command above. The hook does not look for the script among a program's options. The hook refuses an agent's file change under the sage root in any case or Unicode form, and an agent's shell write near the logbook: a write form (a redirection to a file other than `/dev/null` or a `&N` duplicate, `tee`, `cp`, `mv`, `rm`, `ln`, `sed -i`, `sort -o`, `uniq`, `less`, a PowerShell write and the like) with the sage root, `SAGE_HOME` or `CLAUDE_CONFIG_DIR` (except an assignment in the command to a plain path outside the sage root, such as a scratch folder for tests; a `$SAGE_HOME` or `$CLAUDE_CONFIG_DIR` in a write is always refused), `.claude` (except a plain worktree path), a variable by the home folder, a path that leads into the sage root or holds it through a link or `..`, or a link (`ln`) to the sage root or to a target that the hook cannot read. A pattern or a logbook file's name is refused only in a command that can leave the project: one with `cd`, `pushd`, `..`, `~`, `$`, a backtick or an absolute path. So `rm dist/*` and `jq ... > config.json` pass in a project. The hook does not expand variables, so the `?` of `$?` is a pattern character: after a redirect to a file, show the exit code with `|| echo FAIL` or `; echo done`, not with `echo exit=$?`. A refusal names the word that caused it, in the command's own capitals, and the plain way where one exists. Reads such as `grep T2 tasks.tsv 2>/dev/null` pass. When the hook cannot check an agent's call, it refuses it. A pattern with a link on its path (a link before the first wildcard, or a link that the first pattern part names, also a dangling one) is refused everywhere. The hook stops agents' mistakes and the common forgery forms. Deliberate shell forgery (scripts, variables, links made at run time) is the sandbox's job (tasks T94–T99).

Only sage.mjs changes the logbook, so that each change leaves its record. The hook refuses the chief's Write, Edit, MultiEdit and NotebookEdit under the sage root, in any mode. It also refuses a shell write (a redirection to a file, `cp`, `mv`, `rm`, `sed -i` and the like) that names the sage root, or, in sage mode, a logbook file, in any case or as a pattern (`tasks.tsv`, `runs.tsv`, `findings.tsv`, `gates.tsv`, `ledger.tsv`, `decisions.tsv`, `config.json`, `standing.md`, `status.md`). A command that is only `node <path>/sage.mjs ...`, with no redirection, pipe or chain, passes. The user's own `!` commands are not hook events, so the user can still change a logbook file by hand.

Each option takes a value: `--name value`, or `--name=value` for a value that starts with `--`. A command refuses an option that it does not take, and names the options that it takes. It refuses an option given twice.

## Commands

| Command | Does |
| --- | --- |
| `init` | Makes the project's logbook and its standing orders. A new logbook has each table with only its header line. `init` writes tasks.tsv last, so a folder with tasks.tsv has every table. On an existing logbook it makes no table: a lost one refuses (see "The logbook check"). It adds the logbook's folder to the known project list, `projects.tsv` in the sage root, under the root's lock; it never removes a line. It checks the list and takes the root's lock before it writes the logbook, so a refusal there (a busy lock, a damaged or missing list) makes nothing. |
| `projects rebuild --accept-listing yes` | Writes the known project list again: each folder of the sage root with tasks.tsv or ledger.tsv (`how` is `rebuild`), and prints each one. Run it only when the user asks for it, and show the user the listing: a folder that no project uses may be forged, so the user removes it and runs the rebuild again. A `projects.tsv` that is a folder refuses; a link is replaced by a regular file. |
| `logbook` · `logbook repair --accept-loss <table>[,<table>...]` | Prints the logbook's folder. `repair` starts each named table that fails the logbook check again, without rows. Run it only after the user accepts the loss of their rows. Name every damaged table in one command, joined by commas (`--accept-loss tasks,ledger`): a repair refuses when another table fails too, and names the command with both. The old file stays beside each as `<table>.tsv.lost-<n>`, and the decision trail records each repair before the table starts again. A named table that passes the check refuses the whole command. |
| `standing` · `standing add "<order>"` | Prints the standing orders as written, or adds one. Paste them into every brief. Tabs stay, CRLF line ends print as plain lines, and hidden characters are removed (see "Hidden characters"). |
| `task add --title "<t>" --size tiny\|small\|large\|investigate [--risk auth,data,schema,money,secrets,input] [--add <blocks> --why "<reason>"] --priority P0\|P1\|P2\|P3 [--kind <kind>] [--waits <T,T>] [--program <PG>]` | Frames a task and its route. The size gives the least route. A risk adds the security review. An investigation takes no build block: a build that it needs is its own task. Every task needs a priority, and `task add` refuses without one, with the scale: P0 the owner's current focus and what blocks it; P1 next: function or safety bugs, work in flight, pre-pilot items; P2 later: polish, hardening lows, follow-ups; P3 parked but kept. Give each task its priority on this scale. The kind is optional. The board shows both as tags on the task's card. A kind is one of: design, ui, orchestration, optimization, bug-fix, logbook, docs, security, providers, checks. Choose the task's main one. Another value refuses, with the list. |
| `task <T> set priority=P0\|P1\|P2\|P3` · `task <T> set kind=<kind>\|none` | Sets the task's priority, or sets or clears (`none`) its kind, from the lists of `task add`. An open task's priority does not clear: only a merged, concluded or abandoned task takes `priority=none`. An older task with no priority still works: `status` names the open ones, the board marks each card "no priority", and you set one. A follow-up task of `finding move` gets P2. |
| `task <T> set waits=<T,T>` · `waits=` (or `waits=none`) | Sets or clears the tasks that this task waits for: task ids of this logbook, separated by commas or spaces (`waits=T7,T9`). A wait is met when that task is merged or concluded; an abandoned task never meets it, so remove or change the wait, or ask the user. While a wait is unmet, the task takes no lead, implementer, investigate or arena-judge run and no `state=building` or `state=merged`, and the merge check refuses it; its designer and pe runs, and review and QA runs, go on. A wait on a task of the same pull request (`--pr`, or else the same recorded PR) is met at the merge check when that task passes too; a task of another pull request, or an abandoned one, never meets it. When the waiting task is not on that pull request, the refusal names the `pr=` to set. The tool refuses a word that is not a task id, a duplicate, the task itself, more than 20 tasks, a task that the logbook does not have, and a loop (it names the loop: T8, T9, T8). Each change writes a decision row (`waits <old> → <new>`). `task <T>` and `status` show each wait with its task's state, and which are unmet. |
| `program propose --name "<name>" --goal "<goal>" --pilot <T> --tasks <T,T>` · `program propose <PG> [--name "<name>"] [--goal "<goal>"] [--pilot <T>] [--tasks <T,T>\|none]` | Writes a program (`PG1`, `PG2`, …) for a request of two or more tasks with one goal. Frame every task first, then propose once: it puts the pilot and the other tasks (`--tasks`) in the program and opens the breakdown gate on the pilot task (options approve, change, drop; recommendation approve). The board shows it under "Needs you". The gate's question has one part on each line, with no quotes: the fixed first line `Approve program PG1? No task builds before you approve.`, then `Name: <name>`, `Goal: <goal>`, `Pilot, runs first:` with the pilot, and `Then, each after T1:` with each other task, one on each line as `  T2: <title>`. A task's waits other than the pilot, or an ended task's state, come in brackets after its id, before the colon, for example `  T3 [waits for T2]: <title>` or `  T4 [merged]: <title>`, so a title cannot pass for them. A title, name or goal prints as written, but each line break prints as a space, hidden characters are removed, and spaces are single; an empty title prints as `(no title)`. So no text adds a line. The `status` line of each program puts the name last, after `name:`. The `status` gates line shows a breakdown gate's first line and its count of tasks, only for the gate that the program's row names, on its pilot, with the options approve, change and drop (any other gate shows on one line, whatever its text), for example `G1 Approve program PG1? No task builds before you approve. (breakdown, 3 tasks)`; the board shows the whole question. The program's state comes from the answer of that gate, on the pilot task: proposed while it is open, active after approve, dropped after drop, changing after change or the user's own words (they say what to change). Any other gate reads as lost. A breakdown gate (each gate whose question starts with that first line, also one that a newer round replaced) answers once: `gate answer` refuses a second answer, so a change of mind is a new proposal. Only `program propose` writes that line: `gate add` refuses a question that starts with `Approve program`, also after blank, mark or symbol characters, and with Cyrillic or Greek letters that look like its Latin ones. Any other gate takes a new answer. `program propose <PG>` proposes it again after change, or for a new pilot: a new gate whose first line says its round, for example `Approve program PG1 (round 2)? No task builds before you approve.` The round counts the program's earlier breakdown gates. Tell the user in the chat what changed. Without `--tasks` the program keeps its tasks (the old pilot too); with it, the list is the new one, and a task that it leaves out leaves the program. An ended task (merged, concluded or abandoned) stays in the program either way: it counts, and the question lists it with its state. The name is 1 to 60 characters, unique in the logbook (case and width do not count) and not of the form `PG<n>`; the goal is 1 to 300; both have no space at an end or two together and no control, format or hidden character. It refuses a pilot or task that has ended (for a re-proposal whose pilot ended, it asks for a new one with `--pilot`) or is in another program, a task that has started (past briefed, or with a lead, implementer, investigate or arena-judge run that runs), an open breakdown gate, a dropped program, and a loop, which it names with the wait to clear. When a proposal stopped before it wrote its gate, the same command finishes it, and writes the decision row of each task that it put in the program. A drop holds also after a loss of `gates.tsv`: the decision row of the user's answer says it. |
| `task <T> set program=<PG>` · `program=none` (or `program=`) | Puts the task in a program, or takes it out, for a task that joins later. Until the user approves the breakdown, no task of the program takes a lead, implementer, investigate or arena-judge run or a move to building, merged or concluded, and the merge check refuses it. After the approval, each task but the pilot waits for the pilot in the same way, until the pilot is merged or concluded: a pilot wait never passes in the same merge. Its designer and pe runs, and its reviews and QA, go on. The refusal names the fix: ask the user to answer the gate, propose again after change, propose a new pilot for an abandoned one, or take the task out of a dropped program. No task leaves a program before the user approves or drops it; the pilot stays until a new pilot is proposed (it may leave a dropped one). It refuses an unknown or dropped program, an ended task (merged, concluded or abandoned: it neither joins nor leaves a program, so its program keeps it in its count), a task that joins while the breakdown gate is open (its question does not name the task: ask the user to answer change, then propose again with `--tasks`), a started task that joins before the user approves the breakdown and the pilot is merged or concluded, and a loop through a pilot, which it names. A task joins while the user asks for changes: the next proposal names it. No task of the program changes its `waits=` while the breakdown gate is open, as its question shows them: ask the user to answer change, then propose again. No task of a program has or had a pull request of its pilot before the pilot is merged or concluded, as that pull request could never merge: in every state but dropped, `pr=`, `verdict --pr`, `program=` and `program propose` refuse it from either side, also for a PR that a task had before, and name the way out (another PR, or the task out of the program). A task that joins or leaves after the approval does so with no new gate: the line ends with `joins PG1 after the owner approved its breakdown: no new gate, so tell the owner` (or `leaves PG1 …`), and you tell the user. Each change writes a decision row (`program <old> → <new>`). `status` shows each program on its own line, with its pilot and progress, and its name last, for example `program PG1 · pilot T1: 2 of 4 merged · T4 abandoned · name: Codex support`: the count keeps every task of the program, and names each abandoned task. A program is done when each task that is not abandoned is merged or concluded (`program PG1 · done, 3 of 4 merged · T4 abandoned · name: Codex support`), a dropped one names the next step for its tasks that have not ended (`program PG1 · dropped: 4 tasks still in it, take each out with program=none · name: Codex support`), and a program whose pilot was abandoned says `pilot T1 abandoned: choose a new pilot, or drop the program`. |
| `config name="<name>"` · `config archived=yes\|no` | Sets a key of the project's own logbook, in `config.json` of its logbook folder (not the config for all projects). `name` is the project's name on the board: 1 to 60 characters, with no space at an end or two together, and no control, format or hidden character (a tab, a line break, a zero-width space, a right-to-left mark). `name=` alone removes it. Without a name, the board shows the repository name of the checkout's `upstream` remote, then of `origin`, then the main checkout's folder. `archived=yes` folds the project into the board's Archived group: its tasks leave the columns. Set these keys in a config command of their own. Run it only when the user asks for the name or the archive. |
| `task <T> set state=<state> [branch=<b>] [pr=<n>]` | Moves the task. The tool refuses a move that the design does not allow, and "verifying" or "concluded" while a finding is open. A PR number is only digits, with no leading zero. A branch (here and in `run add --branch`) is letters, digits and `. _ / -`, such as `claude/t12` or `tool/t12-short-name`: not main, master, HEAD or `refs/…`, and not a name that starts with `-` or holds `..` or `@{`. In `task set` it must also be a branch of that task, `[<prefix>/]t12[-<words>]`, the rule that the PR script checks, or the branch that another task of the logbook names, so that two tasks share one pull request. `branch=` clears it. An investigation takes no PR number; `pr=` clears one. Each change of a build's PR writes a decision row (`PR <old> → <new>`, with `none` for no PR). |
| `round <T>` | Starts a repair round on the open findings marked fix, and names the roles to re-run on the repair's diff: the sources of those findings. After the last round, or when a round did not fix its findings, it holds or re-plans the task. |
| `run add <T> --role <role> [--branch <b>] [--candidate <k>]` · `run done <R> --status done\|blocked\|question\|failed [--tokens <n>] [--report <path>]` | Records an agent run. A done review, QA or evidence-review run needs `--tokens` with its tokens as a whole number. A run ends once: a later `run done` of an ended run, with the same `--status`, only adds the `--tokens` or the `--report` that it lacks (a Codex native finish and a re-plan end a run with neither); it never replaces a value, and any other call is refused. The role is one of lead, implementer, pe, designer, arena-judge, code-reviewer, security-reviewer, ux-reviewer, qa, investigate and evidence-review; it is read in lower case, without spaces or hidden characters at its ends (`Lead ` is lead), and any other role is refused. One writer (implementer, designer) per branch: finish the running one first, or use another branch. A lead run (`--role lead`) needs a task with a build that is not concluded, merged or abandoned (the refusal names the state; a verified task takes one): a task has at most one running lead run, and the project at most 3, and each refusal names the running lead runs. A lead run of a task that waits (its waits, or its program's pilot) prints `upstream reports:` with the report of the last lead or investigate run of each such task, or `no report recorded`: put each report in full in the lead's CONTEXT. `run add` prints the model of the run (`R12 running · qa on T3 · model sonnet`) and records it in the runs column `model`: pass it as the `model` of the agent call. No model on the line means the agent's own model: pass none. An arena candidate `<k>` takes the k-th model of arena_models; any other run with a risk flag first takes `model.<role>.risk`, then `model.<role>.<size>` (the task's size), else `model.<role>`. |
| `finding add <T> --source <role> --severity high\|medium\|low --summary "<s>" [--key <K>] [--run <R>] [--class <class>]` | Records a finding. A known key opens it again, with the new severity, source and summary; the decision trail keeps the old summary. Without `--summary`, a known key keeps its summary; an empty one is refused. Without `--key`, the finding gets a new key. `--run` is the run whose report holds the finding: a run of the same task. `--class` is the problem class: state-edge, speed, copy, layout, security or other. A finding whose source is a review or QA role (code-reviewer, security-reviewer, ux-reviewer, qa or evidence-review) needs both, given or kept by its known key; the refusal names the classes. Another source, such as the sage's own note, may leave them out. A lead's `--run` must be a run that it added. |
| `finding triage <T> <K> fix\|dismiss\|ask [--reason "<r>"]` · `finding close <T> <K>` | Triage every finding. A dismissal needs its reason. A low fix key of the current round is not dismissed while a medium or high finding of the task is open, in any triage and any state: it joins the next round with it. Close a fix after a review confirms it. |
| `finding move <T> <K> --to "<title>" [--size tiny\|small\|large]` | Moves an open medium or low finding to a new follow-up task (small by default), which it frames. The finding gets the new task's key, and the decision trail records the move. A high finding cannot move: it blocks its task until it is fixed. A fix key of the task's current round moves, at any severity and in any state, only after the owner's answer: a gate of the task whose question names the key as a word (`gate add <T> --question "Move <K> to a follow-up task?" --options "move\|keep"`) and whose answer is its first option. Else it is fixed in a round or dismissed with a reason. |
| `verdict <T> --sha <sha> --kind <kind> [--cycle <n>] [--pr <n>] [--run <R>]` | Records a verdict on a head SHA. Give the full 40-character SHA (`git rev-parse <branch>`): a short one is refused, and capitals are the same SHA. A task without a build block records its verdicts without `--sha`. Kinds: checks-pass, review-clean, security-clean, ux-clean, qa-pass, evidence-clean, checks-fail, findings, qa-fail. Record the findings first: `findings` and `qa-fail` need an open medium or high finding, and their refusal says to record it first. On a task with a build, a review or QA verdict needs `--run`: a done run of the task, of the role that gives the kind, whose helper's report the hook kept at its stop (a helper whose name is its run's id). A clean report backs only a clean kind. A report with a medium or high finding backs `findings` or `qa-fail`, and a clean kind only after each of those findings is recorded with that `--run` and dismissed, moved or closed. One run backs one verdict, on the commit that its report names. The tool refuses any other, in every shell form. A `findings`, `qa-fail` or `checks-fail` verdict moves a verified or pr-ready task back to reviewing, prints that state and records the reason in the decision trail. |
| `gate add <T> --question "<q>" --options "<a\|b>" --recommend <a> [--default <a>]` · `gate answer <G> --option <n> --project <folder>` · `gate answer <G> --other-hex <hex> --project <folder>` | Parks a question for the user, with your recommendation and the default. The question is one line: each line break in it becomes a space. Only a breakdown gate's question has lines. The recommendation and the default are options, by text or number; options that differ only in case or hidden characters are refused. The answer is the number of an option as the board shows it (1, 2, …), never its text, so no agent-written text goes into a command. For the user's own words, use `--other-hex` with the UTF-8 bytes of the words in lower-case hex, so that the command holds only 0-9 and a-f; the gate keeps them as `other: <words>`. An option may not read as `other:`, also with other case, width, hidden characters or a space before the colon. Give the `--project` of the gate's own project: two projects can each have a G1. `init` and `task add` write the project's folder to `checkout.txt` in its logbook, so a session of another project can answer its gates. |
| `log <T\|-> "<decision>" --why "<reason>"` | Adds a line to the decision trail. Put the id that the decision is about first ("R1 stopped by hand"): only the first word counts as an id, so an id later in the text can come back. |
| `pages <T>` · `pages <T> record <file>` · `pages <T> record --run <R> --text <report>` | Makes (mode 700) and prints the folder where agents save the task's pages (research, designs, findings pages): `~/sage-worktrees/<project>-<hash>/pages/<T>/`, under the logbook's own folder name, so two projects with the same name never share it (`$SAGE_WORKTREES` overrides `~/sage-worktrees`). It is outside the logbook, so a sandboxed agent may write there. `record` adds the page's path and sha256 to the decision trail; the file must be a regular file of at most 16 MiB in that folder, not a link, a named pipe or a device, and its name has no control character (a tab or a line break). `--run` and `--text` save a run of the task's report as `<R>-report.md` in that folder (once) and record it, for a chief that cannot write the folder. Give that folder in the brief of each agent that saves a page. |
| `board [this\|all\|<project>]` · `board --name-hex <hex>` · `[--remember yes\|no]` | Prints the board as Markdown: `this` (the default) shows the session's project and one line for each other project with something waiting, `all` shows every project, and a name shows that project. `--name-hex` gives the name as the hex of its UTF-8 bytes. It reads every logbook and changes none, and takes no lock on them. `board.json` at the sage root keeps when each project was last shown, so the next board lists only what merged since; `--remember no` leaves it as it is. |
| `stats [--task <T>]` | Prints a guide line, a total line with the count of done review runs that have no tokens, and one table of the 50 tasks with the most review tokens, largest first: for each task, its review and QA runs, their tokens in thousands (done runs only), the tokens after round 0 (its runs of repair round 1 or later), its repair rounds, and its findings by role and by cycle (the cycle of the verdict of the finding's run in its task's ledger rows; none without one). A last line counts the tasks that the table does not show. With no review runs and no findings, it prints "No review runs yet." It reads only and takes no lock. |
| `status` | Prints the status lines. Each change also writes them to `status.md`. End each report to the user with them. When an open task has no priority, a `priority` line names it (up to ten), for example `priority 12 open tasks have none: T3, T7, … · set them with task <T> set priority=<P0 to P3>`. |
| `node ${CLAUDE_SKILL_DIR}/sage-pr.mjs import\|create\|view\|merge <T>` | The PR script (not yet in the route): it imports the task's bundle for review, pushes the task's reviewed commit and opens, shows or merges its pull request, so that agents never push or call gh. It takes exactly a verb and a task id, and refuses any other word. `import` runs after the build and before the reviews: it reads the bundle as `create` does (the same checks, the same fetch with fsck into `refs/sage/<T>` of the mirror) and writes a review copy that agents cannot write, in the logbook folder: `review/<T>-<full sha>/` (the files of the bundle's tip, by `git archive`) and `review/<T>-<full sha>.diff` (`git diff` from the merge base with main). The mirror's own attributes override the commit's `.gitattributes`, so `export-ignore`, `export-subst`, `-diff` and line-end or encoding conversions hide or change nothing in the copy. It writes both in its own folder and moves them in, the diff last; it prints `imported <sha>: review the files in <folder> and the change in <file>`. An import of a tip that has a review copy prints the same line and changes nothing. The reviewers read only the review copy: `git diff`, `show` and `log` in the agent's clone do not check the objects' hashes, so an agent can make them show other text at the same SHA. `create` and `merge` refuse a reviewed head whose review copy is missing or not older than the first verdict on that SHA in the ledger (the ledger holds times to the second, so a verdict in the same second refuses too): `<sha> has no review copy from before its first verdict ...: run sage-pr import <T>, have the reviewers read the review copy that it names, and record their verdicts again`. The branch comes from tasks.tsv and the reviewed head from the task's latest verdict with a SHA; the repository from the GitHub origin of the project's main checkout (`$SAGE_PROJECT`, else the current folder). That folder must be the one that the logbook's `checkout.txt` names (the logbook key is short, so another folder can have the same one), and not in the worktree root. An origin that is not exactly `https://github.com/<owner>/<name>`, `ssh://git@github.com/<owner>/<name>` or `git@github.com:<owner>/<name>` (each with an optional `.git` and `/`) refuses: a user or token, a port, a `#`, a `?`, another host and an upper-case host do not pass, and `$SAGE_REPO` must be unset or name the origin's repository. The branch must be a task branch of that task (`[<prefix>/]t12[-<words>]`, the same rule as `task set branch=`), never main. `create` reads `<worktree root>/<logbook folder>/<T>.bundle` (`git bundle create <file> main..<branch>`) once, not through a link, a plain file with one link and at most 10 MiB that starts with `# v2 git bundle` or `# v3 git bundle`, and copies it; it fetches the copy into its mirror (`mirror.git` in the logbook), with fsck and without tags. git always names the mirror with `--git-dir`, so it never uses a repository in a folder above it; a new mirror is made in the script's folder and moved in whole, and a `mirror.git` that is not a bare repository (a file, a link, an empty or other folder) refuses: `<mirror> is not a bare git repository: ask the user to remove it`. It refuses a bundle tip that is not the reviewed head and a head that is already on main, pushes fast-forward only and never a tag, and opens a pull request only when the repository itself has none open from the branch into main (a fork's pull request does not count, by `isCrossRepository` only, so a renamed owner still finds its own; GitHub allows one open). ## Cycles and merges

- A cycle is one full set of fresh reviews and QA on one head SHA. Record each verdict with `--cycle <n>`.
- A cycle is clean when no medium or high finding of the task is open. A review or QA that found only low findings records its clean verdict, not `findings` or `qa-fail`: the tool refuses those without an open medium or high finding. Before the merge, fix, move or dismiss each low finding with a reason: an open finding blocks the merge.
- A `findings`, `qa-fail` or `checks-fail` verdict blocks its SHA: repair, then review the new SHA.
- A merge needs the task's clean cycles on its head SHA: 1 for every task (`cycles.small`), 2 for a large task (`cycles.large`), and 2 for any task with a risk flag (`cycles.risk`); the largest count that applies wins. A task with no review or QA in its route needs only checks-pass: a tiny task without a risk flag or an added review. Verified needs 1 for every task.
- A repair round re-runs only the roles that `round` names, on the repair's diff. The re-check confirms each fix (`finding close`) or opens the finding again; it records no verdict. Then the task needs its clean cycles on the final SHA, with every role.
- A new medium or low finding that a round raises goes to a follow-up task with `finding move`, not to another round. A high finding always blocks.
- With autopilot on, merge with `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`. The sage hook runs `merge-check` first and refuses a SHA that is not ready. It refuses every merge by an agent.
- A new commit is a new SHA. Its verdicts start again from cycle 1.
- Every task with verdicts on a SHA counts, also an abandoned one. When two tasks share a pull request, give both the same `branch=` and `pr=`, and record each verdict under both: autopilot merges it when each task passes on its own verdicts. Only the chief puts a task on a shared branch or takes it off one: a branch that another task names by its `branch=` or ran work on. To leave an old task's verdicts behind, push a new commit.

## What the hook refuses an agent

- `git stash` in any form, also with `-C` or `--git-dir`: every worktree shares one stash list. Use `git worktree add --detach <scratch> <sha>` or `git show <sha>:<path>`.
- A program that lists or signals processes (`ps`, `pgrep`, `pkill`, `kill`, `killall`, `lsof`, `top`), unless it resolves to a fake in the temp folder. Put a fake `ps` first on PATH that prints a start time in the past, and run a fake `kill` by its path. The chief is not limited.

## How an investigation ends

- An investigate task has no build block, so it ends at `concluded`, not at verified. Its last states are reviewing → verifying → concluded.
- `concluded` needs no open findings, and the task's latest verdict must be `evidence-clean`. Record it with `verdict <T> --kind evidence-clean --run <R>`, without `--sha`.
- A task with a build block cannot use `concluded`.

## Several sessions on one project

- Several chief sessions may share one project's logbook. Each command that changes the logbook holds its lock while it runs.
- A command waits up to 3 s for the lock. Then it refuses with `the logbook is busy: pid <n> on <host> has held <path> for <n> s`, or with `<path> has no valid owner file`. Nothing changed: run the command again.
- The next command clears a lock that a crashed command left. A lock from another machine, a live process that is not sage, or an odd owner file stays. Remove the folder in the message only when no sage command runs.
- The next command also removes the temp folder (`.lock.<id>`) of a command that was killed while it waited.
- `status`, `logbook`, `standing` and `merge-check` take no lock. They work while another command runs.
- The sessions may run two versions of sage. A version refuses to change a logbook whose tables have columns that it does not know: its write would lose them. The refusal says to update the sage plugin and restart the session, and that `status`, `logbook`, `standing` and `merge-check` still work.
- A command refuses, before any change, when status.md or standing.md is not a regular file, also a link to nothing.

## The logbook check

One check guards the merge check and every write, `init` on an existing logbook too. Each of the seven tables must be:

- there (not deleted, and not a link to nothing);
- a regular file that the tool can read;
- not empty (not 0 bytes, and not only blank lines);
- with its header line: the first line names each of its columns. A BOM and CRLF line ends from an editor are read as a plain file.

A table that fails refuses every merge and every write, and the refusal names the file. No command makes a lost table again or repairs it in silence. The ways out:

- Restore the file from a copy.
- A table that cannot be read (EACCES): fix its permissions. Do not remove it: its rows are there.
- If no copy is left and the user accepts the loss: `logbook repair --accept-loss <table>`. Run the command that the refusal prints. When a second table fails too, the repair refuses and prints the command with both tables: run that one.

After a repair of tasks.tsv, the verdicts of its lost tasks stay in ledger.tsv. The merge check refuses their SHA, says that tasks.tsv was started again, and asks for a new commit with its verdicts under a task that the logbook has.

The programs table came after the others. A logbook made before it has no programs.tsv: that reads as a table with no rows while no task names a program, and `program propose` writes the file. When a task names a program and the file is missing, its rows are lost, as for any table.

Limit: a table cut to only its header line is a table without rows. The check cannot tell it from a new table.

A folder without tasks.tsv is no logbook: `init` has not finished it. `init` finishes it when its tables have no rows. When they have rows, its task list is lost, and `init` refuses: restore tasks.tsv, or repair it.

## Hidden characters

The tool keeps no hidden character in a cell, and removes them from the standing orders. Hidden characters are those that a person does not see but a terminal or an agent acts on:

- the control characters (C0, DEL and C1), except a tab and a line end in the standing orders;
- the bidi embeddings, overrides, isolates and marks (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, U+061C);
- the zero-width characters (U+200B to U+200D, U+2060, U+FEFF);
- the variation selectors (U+FE00 to U+FE0F, U+E0100 to U+E01EF);
- the tag characters (U+E0000 to U+E007F), text that only an agent reads.

Other text stays: each script, and emoji. A zero-width joiner or non-joiner between two letters stays: Persian and Indic text needs it. A zero-width joiner between two emoji stays, so a joined emoji stays whole, and the emoji selector (U+FE0F) stays after an emoji or a keycap base (`1️⃣`). A subdivision flag (England, Scotland, Wales) shows as a black flag.

The tool prints each hidden character in an id, a column or a path as `\xNN` or `\u{N}`. For a project path with a control character, it prints no command to paste.
