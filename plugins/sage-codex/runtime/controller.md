# Owned controller wrapper

The wrapper runs the native owned controller of the Codex fork for one Sage task. It launches the controller, checks the effective policy before any model turn, binds one task to one root thread, and keeps every notification and an honest result for each turn. The terminal client puts the owner in front of it: each typed line is one turn.

## What it does

- **Launch.** `resolveControllerBinary` reads only `SAGE_CODEX_CONTROLLER_BIN`: no default, no PATH lookup and no other variable. It refuses an unset, relative, missing or non-executable path. It follows a link to the real path, and refuses the file, or a folder on that path, when its group or other users can write it, or when it belongs to a user other than the current user or root (a sticky folder such as `/tmp`, owned by root, is accepted). It returns the sha256 of the file, and refuses a different hash when `SAGE_CODEX_CONTROLLER_SHA256` is set. The process runs `app-server --stdio --owned-controller --strict-config` with one `-c` flag for each key of `OWNED_CONTROLLER_CONFIG`, in its own process group, with the real path of the project as its cwd. No other launch exists.
- **The launch profile.** The `-c` flags turn multi-agent v2 on, and multi-agent v1, goals, web search, plugins, apps and remote plugins off. The gated real test checks that the model gets no v1 tool (`send_input`, `resume_agent`) and no goal tool.
- **Policy binding.** `openThread` runs every check of the project before `thread/start`, because `thread/start` already starts the MCP servers. In order:
  1. `checkProjectFiles` refuses a rules file (`.codex/rules/*.rules`) or a hooks file (`.codex/hooks.json`) in the `.codex` folder of the project or of any folder above it, up to the filesystem root. Codex loads these files with no config key, so `config/read` never shows them: a rule can let a command run with no approval or outside the sandbox, and a hook runs a command at its event. Codex loads them from the folders between the project root and the cwd, and the hooks of a linked Git worktree from the matching folder of its main checkout, so the check covers those folders too (a superset). The `.codex` folder that is `CODEX_HOME` (or `~/.codex` when `CODEX_HOME` is not set) holds the owner's own rules and hooks, and passes.
  2. `config/read`, then `checkConfig` on its reply: each owned key has its value from the session flags layer, and each owner-only key comes from the user layer, a managed layer or the session flags, never from the project layer (an agent can write project files). The owner-only keys change the sandbox or where an approval goes, or start a program: `sandbox_mode`, `sandbox_workspace_write.*`, `permissions.*`, `default_permissions`, `approval_policy`, `approvals_reviewer`, `auto_review.*`, `mcp_servers.*`, `hooks.*`, `features.request_permissions_tool`, `features.exec_permission_approvals` and `features.write_stdin_approval`. The approval policy and the sandbox must also be set: a key that no layer sets comes from `config/read` as null with no origin, and for these two that is a refusal that says to set it in the user config.
  3. `thread/start` with the project cwd, `ephemeral` true and the developer instructions. `bindPolicy` then checks that the thread is a 0.160.0 ephemeral root in the project, and that the model, provider, approval policy and sandbox of the thread are the ones in the owner's config. A model or a provider that no layer sets is the default.

  `config/read` and `thread/start` each have a deadline. A refusal sends no later request (a file or config refusal sends no `thread/start`), stops the process and returns `refused` with a fixed code and a message that says what it found and what to change. The policy record and its binding hash go with every turn result.
- **The owner's selection.** The wrapper never sends a model, provider, approval policy, sandbox, permission profile, environment list, tool list, or a `turn/start` cwd or workspace root. The thread keeps the default environment, so the normal Codex tools run under the owner's own sandbox and approval setting. The owner's hooks stay on.
- **Events.** Every notification and every refused server request goes to `onEvent` in arrival order, with a sequence number, as frozen data. `events()` keeps them too: with an `onEvent` handler, only the events of the current turn (the handler keeps what it needs, so a long session does not grow); with no handler, every event of the process. `maxEvents` and `maxEventBytes` count from the start of the current turn; past them the process fences: a lost event never passes silently. A delta notification (such as `item/agentMessage/delta`, one for each streamed piece of text) does not count toward `maxEvents`, so a long valid turn runs on; `maxEventBytes` (64 MiB) and `maxDeltaEvents` (1 000 000 deltas in one turn) still bound them. A throw from `onEvent` fences too. No stderr text is kept.
- **Turn result.** `turnOutcome` decides from `turn/completed` of the bound thread and turn only: `completed`, `interrupted` or `failed`; any other status, also a name such as `constructor`, gives `uncertain`. A terminal that comes before the `turn/start` reply waits for it. Two terminals in one read give `uncertain`; a terminal for a turn that already has its result fences the process. EOF, a crash, an invalid frame, a fence or the event limit before a terminal give `uncertain`, never `completed`. At the turn deadline, and on `stop()` during a turn, the wrapper sends `turn/interrupt` first; with no terminal within `interruptGraceMs` the result is `uncertain`. An uncertain turn fences the process. `fenced()` resolves with the first fence reason.

## The terminal client

Run it from the built plugin, because `commands.mjs` needs the bundled core:

```sh
SAGE_CODEX_CONTROLLER_BIN=/absolute/path/to/fork/codex \
  node plugins/sage-codex/runtime/controller-client.mjs --project <folder> --task T400 --run R1 --instructions <file>
```

- Before it starts the controller, it checks the options, the binary, the project folder, the instructions file and the task and run ids. A refusal says what it found and what to do.
- It prints the binary path and its sha256, and a warning when `SAGE_CODEX_CONTROLLER_SHA256` is not set. Then it prints the task, the run, the model, approval and sandbox of the owner's config, each in quotes, and how to use the client. A model that no layer sets shows `(the Codex default)` after it.
- Each non-empty line is one turn, one at a time, sent unchanged. A line typed during a turn waits, and the client says so. `commands.mjs` classifies the line: the client says that a mode phrase goes to the chief, or that a near line changed no mode.
- It prints the agent messages of the root thread, each with `chief> ` before each of its lines, and each controller warning, each of its lines with the warning prefix. An approval request names the command and says that it did not run. Each turn result says what happened and what to do next; the fix for a refused line shows also when another typed line waits. The reasons of the controller process come in plain words (for example "the controller process ended by itself"), the same words for one event in each line.
- When a turn gets no controller event for 15 s (`WAIT_MS`), the client shows `[Waiting for the model. Press Ctrl-C to stop the turn.]`, once for each turn.
- Controller text never reaches the terminal raw. Each character of these classes becomes U+FFFD: the controls (`\p{Cc}`: C0, C1 and the newline in a client line too), the format characters (`\p{Cf}`: bidi controls, zero-width characters, the soft hyphen, tags, U+0600 to U+0605, U+180E, U+206A to U+206F), the line and paragraph separators (`\p{Zl}`, `\p{Zp}`), and every default-ignorable character (`\p{Default_Ignorable_Code_Point}`: variation selectors, Hangul fillers). So model text cannot move the cursor, write the clipboard, hide or reorder what the owner sees or print a line that looks like the client's. A config value on the Ready line goes through the same filter, in quotes.
- The client writes to its terminal without blocking, so a terminal that takes no output (Ctrl-S, or a stopped terminal) never stops it. When more than 8 MiB of output waits for the terminal (`TERMINAL_QUEUE_BYTES`), the client says so once, stops the turn, and drops output until the terminal takes output again; the result of that turn says that the client stopped it.
- Ctrl-C stops the active turn at once with a message. A line typed during that turn then runs, and the client says that it starts now. A second Ctrl-C stops the controller, also before the chief is ready. SIGTERM stops the controller. The end of the input (Ctrl-D) stops the controller after the lines already typed; during a turn the client says that Ctrl-C stops it now. After the end of the input or a stop, the result of a turn says that the controller stops now.
- A lost terminal (SIGHUP, or an EIO or EPIPE on the terminal) stops the controller at any time, idle or in a turn, and the client writes nothing more. The client writes to its terminal without blocking and opens stderr at its start: after a terminal closes (macOS), a blocking write and the first open of stderr wait for ever.
- The controller runs in its own process group, so a terminal Ctrl-C reaches the client only. The controller still ends with the client: the client stops it on every path, and a killed client closes its stdin, which ends the controller by itself (the gated real test checks this).
- The exit code is 0 only after a stop that the owner asked for (Ctrl-C, Ctrl-D or SIGTERM). A refusal, a crash, a fence, an unknown turn result or a lost terminal gives 1.
- The controller gets the client's environment, so it uses the owner's `CODEX_HOME`, config, hooks and login.

## What it refuses

- A second `openThread`, an `openThread` before the start, a second turn while one is active, and any turn after a fence or a stop.
- Every server request, with error -32601. So an approval request is a refusal: with an approval policy that asks, the command does not run.
- A task id, run id, project, instructions or turn text that fails the checks in `bindTask` and `bindTurnText`.

## What it does not prove

- That the binary that runs is the one that was hashed: a swap between the hash and the launch is not detected.
- That no agent writes a rules or hooks file during the session. The check runs before `thread/start` only. The Codex sandbox keeps each `.codex` folder read-only in its writable roots (read in the fork source, not tested here); with `danger-full-access` nothing keeps it.
- A rules or hooks file added between the check and `thread/start`.
- That the native tool policy is safe for children (T391). The wrapper checks the launch profile and the root's tool names, not the children's tools.
- Real-model behaviour. The gated test in `controller-owned.test.mjs` uses a loopback synthetic provider.
- A bound on memory for a long session with no `onEvent` handler: then `events()` keeps every event of the process. The client gives a handler.

## Checks

Run each test file alone with `node --test`, with fake `ps`, `pgrep` and `kill` first on PATH. `controller-owned.test.mjs` replays `controller-fixture.json`, which comes from the labelled synthetic U3 transcript and the `config/read` format of the real fork binary. Its signal cases run the built client as its own process on a fake controller script, and send SIGINT to the process group of that client only. Its pty cases run the built client on a pseudo terminal (Python `pty.fork`, skipped when `python3` is missing) and close that terminal; one of them stops reading the terminal during a large chief message and checks that the client still runs the next line. Its six real cases run only when `SAGE_CODEX_CONTROLLER_BIN` names the built fork binary; `SAGE_CODEX_CONTROLLER_EVIDENCE` names a folder for their JSON evidence.
