# Changelog

> **Release notes now come per release.** From 12 Nov 2026 (T1014), each release of sage gets its own notes on the [releases page](https://github.com/erickb336/sage-stack/releases), drafted from the pull requests that merged since the release before it. This file keeps the history up to that day, and it gets no new entries.

This is the list of user-facing changes to sage up to 12 Nov 2026, newest first.
Each date is the day of the first commit that made the change. Older changes are in the [git log](https://github.com/erickb336/sage-stack/commits/main). In these entries, "the sage" is the chief, the main session in sage mode.

> **Warning:** before you use waits or programs, update sage and restart every session that was already open. An older session still merges a waiting task, or a task of a program that you did not approve. See [To update sage](docs/guide/using-sage.md#to-update-sage).

## 2026-11-12

- **Clearer notices for a logbook table that the board cannot read (T1012).**
  - The Releases tab says "The releases of <project> cannot be read" only when a damaged table hides releases. A project with no releases says "No releases yet", also when its milestones table is damaged.
  - An old, read-only logbook of a project (after the move) with a damaged table no longer puts that notice above the releases that the tab shows.
  - When a damaged table hides every release, the board still shows the Releases tab, so you can open it and read why.
  - An older logbook that still has programs.tsv (from before the rename to milestones) shows no release and no milestone from a damaged milestones or tasks table, as a newer logbook does. It no longer shows a release as done, or as "0 of 0", from a table that the board cannot read.
  - When an older logbook's programs.tsv cannot be read, "Needs you" says "The milestones table cannot be read" and names programs.tsv and the line. Before, it said "Programs: …" and "without the rows of ." The Releases tab shows that notice once, not a second time.
  - A logbook folder that the board cannot read says "Its folder has no read permission" once. Before, it listed each file of the folder.
  - When the board cannot read the tasks or gates table, a milestone in "Needs you" no longer says "Choose a new pilot, or drop the milestone" or "propose it again". It says that its state cannot be read, names the table, and says "Ask the chief to repair the logbook."
- **In Codex, the shape note is about the chief's last message only (T1011).** Before, when the chief's message missed its kind's shape and a later message fitted, with no message of yours between them, the chief still got the note about the older message. Now each end of the chief's turn removes the older note first, as in Claude Code. A later message that fits, a message that names no kind and a turn with no message all leave no note. Each miss is still counted in `message-misses.jsonl`.
  - A note file that sage cannot read is now removed at your next message, so sage does not try to read it again at each message.
  - You do not need to trust the Codex hooks again: this change is in sage's files only, not in the hook entries of your Codex hooks file, so Codex keeps them trusted.
- **A milestone's word agrees with its tasks' words (T1009).** A milestone and a release now take their state word from the words of their tasks, the same words that the task cards show. Before, they used a second, shorter rule, so a milestone could say "not started" while its tasks said needs you and waiting.
  - Board page, Releases tab, chat board and `status`: an active milestone whose pilot needs you and whose other tasks wait now reads in progress, and so does its release.
  - A milestone whose only open tasks wait, also a briefed task that waits for its pilot, now reads not started, as its cards do. Before, a briefed task counted as started.
  - What stays: the six words, the task cards and the rules of T1002.
- **A finding lined up under the first one is a finding (T1008).** In a review's or QA's report, the first finding often stands on the FINDINGS line, and the next ones are indented to line up under it, as in the report skill's own layout. The report reader refused such a report, because it read an indented finding line as a line that it could not read. So a clean report backed no verdict, and the role ran again. This happened twice on 2026-11-12.
  - Now a list item with a key and a severity is a finding at any indent, also under another finding, at the severity that it gives.
  - This is the safe direction: an indented `- K2 high` under a low finding counts as high, and an indented `- K2 medium` under a high finding still counts as its own medium finding. Read as detail, either one would hide a finding.
  - A list item in the form of a finding in the detail, such as a step written as `- 1 low the first step`, is now a finding too. Before, it made the report unreadable.
  - An indented line in the form of a finding without a list mark (`K2 medium a second bug`) still makes the report unreadable. The detail under a finding still compares with that finding.
  - The report skill and the design page give the new rule.
- **A task that leaves a milestone keeps its release (T1007).** Before, a task that left a milestone also left the milestone's release, with no record. Now it keeps that release as its own release, with a decision row such as `release none → 1.0`, why `T12 left milestone M5, and keeps its release`. So nothing leaves a release by itself.
  - This holds for `task <T> set milestone=none`, also for each task of a dropped milestone, and for a new `milestone propose` whose `--tasks` (or new `--pilot`) leaves a task out. The line of `task <T> set` says `keeps the release 1.0 of M5`.
  - A milestone with no release gives no release and writes no row. An ended task stays in its milestone, so its release does not change.
- **In Codex, a note when the chief's message misses its shape (T1005).** When a message of the chief names its kind on its first line, for example `QUESTION`, and misses the shape of that kind, the chief gets a note with your next message. The note names the kind and each problem, for example a missing "Needed by" part or a task number outside the Ref line. Nothing is blocked, and you see no line. A message that names no kind is not checked. Each miss adds one line (the time, the kind and the names of the problems, never the message's text) to `message-misses.jsonl` in the Codex hooks' folder, so that sage can count the misses.
  - The check runs on Codex's Stop event: a new, eighth entry in your Codex hooks file. After you update sage, the start status says that 1 sage hook entry is missing: say yes, and the chief runs `hooks install` (or run it yourself). Then trust the new hook once with `/hooks` in the Codex CLI. Until you trust it, Codex does not run it, and the start status says that 1 sage hook is not trusted.
- **The chief hears when a message misses its shape (T1004).** In Claude Code, the sage hook now reads each message of the chief when it ends. When the first line names a kind, such as `QUESTION`, and the message does not fit that kind's shape, the chief gets a short note at its next turn: the kind and each problem (at most 20, then the count of the rest), for example a missing "Needed by" part or a task number in the text. The note is about the chief's last message before your next message only: when that message fits, there is no note. You see no change in the message itself, because it is already on your screen; the next message of that kind should fit. Chat that names no kind, the board's text, the Ref line and the Page block are not checked ([sage's messages](docs/guide/using-sage.md#sages-messages)).
  - The hook counts each miss in `shape-misses.jsonl` in its state folder: the time, the kind and the names of the problems, with no text of the message.
  - The check never blocks: an error in it gives no note.
- **The state words on the board and in status (T997).** You now see the six state words of T1002 (not started, waiting, needs you, in progress, done and stopped) where a task, a milestone or a release shows its state. Each word comes from one rule in sage core, so the board, the chat and `status` agree.
  - Board page: each card shows its word with its mark (○ ⧗ ! ▶ ✓ ■) at the top right. A task page, each task row of a milestone page and each milestone shows its word too. The columns do not change.
  - Chat board ("show board"): each task line, each Needs you item and each milestone line has its word after the title, for example `T13 Sample · waiting · …`. The lookup of one task (`show board T13`) shows the word in its second line.
  - A wait names the word of the task that it waits for: "Waits for T12 (in progress)." in place of "(in review)", and "(stopped)" in place of "(abandoned)".
  - `status`: each milestone line has its word after its release, for example `milestone M5 · release 1.0 · in progress · pilot T984: 0 of 8 merged · name: Sage feel`. A done milestone reads `done · 3 of 4 merged`, and a dropped one `stopped · dropped: …`. The release line already had its word. The tasks line keeps the tool's own states.
  - A milestone whose pilot stopped, or is not in the logbook, now needs you in its release's word too, as on the board.
  - What stays: the task page's "Recorded state" line, the `task <T>` line and every write confirmation of the state tool keep the tool's own states, for the chief and the agents.
- **Releases on the board (T996).** The board now shows where each project is in its releases, as in the design that you approved (option B).
  - Board page: a "Where we are" frame above the columns, with boxes inside boxes: release › milestone › task, each with its level, its name and its state word. A box that needs you has a double border. The frame shows each release that is not done, then the open work that is in no release.
  - Each card names its nearest level: "◫ Milestone 5: Sage feel", or "◎ Release 1.0" for a single task, or "no release" when its project has releases.
  - A new Releases tab (`/releases`): each release in order with its word, its count of done tasks, its goal and its milestones and single tasks; then what is in no release; then the done releases.
  - Chat board ("show board"): the same frame as text, after Needs you, and the nearest level at the end of each task line. A project with releases shows its milestones in the frame, not in the Milestones section.
  - A project with no release shows the board as before: no frame, no Releases tab and no release tag. The milestone tag on a card now names its level for every project ("Milestone 5: Sage feel" in place of "Sage feel").
  - A box names a task by its title ("Task: Presentation skill"), with its id after it in grey on the page. A task in progress is a double box that says "you are here", and a box of waiting tasks says what they wait for ("Waiting for Presentation skill"). Each task in a list box links to its page.
  - The approval of a milestone names it as its tag does ("Milestone 6: Faster reviews"), in Needs you in the chat and on the card's band; so does a stuck milestone in Needs you.
  - A releases table that the board cannot read is an item in Needs you that says why, and the board shows the tasks without their releases (no "not in the logbook" release).
  - In the chat, a dropped milestone with tasks still in it keeps its line in the Milestones section when the frame does not show it.
  - The Releases tab says when a project's releases table cannot be read, with the reason and "Ask the chief to repair the logbook", and never "No releases yet" for that project.
  - Every line that you read names a milestone by its level, not by its id: "Needs you: the breakdown of milestone 6", "Waits for your approval of milestone 6 (gate G3)", the chat's Milestones line, a stuck milestone in "Needs you, not on a card", and the task page's milestone link. The Milestone filter list and a gate's own text keep the id.
  - In the "Where we are" frame, a dropped milestone with tasks still in it says what to do: "2 tasks still in it: ask the chief to take each task out of the milestone."
- **Messages in the shapes that you approved (T984).** Each message from the chief now names its kind on its first line, for example `QUESTION`, `REPORT` or `CATCH-UP`, and follows that kind's shape: the question's table of answers with my pick, the report's table of pieces of work, the catch-up's boxes inside boxes from release to task with a state word in each box. Task and pull request numbers go only in a small Ref line at the end. The new presentation skill lists the 14 kinds and the long page, and the cold-read test that the chief runs before it sends a message ([sage's messages](docs/guide/using-sage.md#sages-messages)).
  - A message with a picture, or a message that is too long for the chat, also names its page: a file on your Mac, in the task's pages folder, that shows the whole message with each picture as an image. The image is drawn from the same text as the picture in the chat, so the two never differ. In the Claude desktop app, the path opens in the Browser pane. A design's page has a switch to today's picture.
  - The chief renders these messages with the state tool's new `message` command (the `message` tool in Codex). It refuses a message that is not in its kind's shape, a picture over 46 columns or with tree marks or a box that does not close, and task numbers in the text. Core also has these checks as functions that a later hook can run on a message that the chief writes by hand.
  - Known limits: a page loads nothing and runs only its own switch, but a page that you open can still send its own content out, for example through a link in it. A terminal with an East Asian wide setting draws the box marks two columns wide.

## 2026-11-11

- **Releases (T1003).** A release is a version that you ship, such as 1.0. It holds milestones and single tasks (tasks outside a milestone), and it is optional: a logbook with no release reads and writes as before. The board does not show releases yet (T996).
  - Ask the chief to add a release: `release add --name "1.0" [--goal "<goal>"]`. The name is unique when case and width do not count, and it cannot look like an id (`T12`, `M5`), be `none`, or have a comma or a middle dot.
  - Put a milestone in a release with `milestone M5 set release=1.0`, and a single task with `task T12 set release=1.0`; `release=none` takes it out. A task of a milestone is in its milestone's release, so `task <T> set release=` refuses it and names the two ways out. A task that joins a milestone leaves its own release. Each change writes a decision row.
  - Nothing moves to another release by itself. When you say that a release ships, the chief moves each open milestone and single task to the next release, one command each.
  - `status` shows one line for each release, in the order that you added them, before the milestone lines: its state (not started, in progress, done or stopped), how many of its tasks are done and stopped, its milestones, its single tasks and its goal. A milestone line names its release.
  - In Codex, the `release_add` and `milestone_set` tools do the same, and `task_set` takes `release`.
  - The move to a shared logbook takes the releases by name.
  - `release <T>`, the old word of `unclaim`, still works for this version, with its note. `release add` is the release level: a release name is never a task id, so the two do not clash.
  - Update sage in each Claude Code and Codex session before you put the first milestone or task in a release. Until then an older sage writes the logbook as before. After it, `milestones.tsv` or `tasks.tsv` has a release column, which stays also after you take each milestone and task out of its release. While a table has that column, an older sage still reads the logbook, but refuses every write and says that a newer sage wrote it, so no release is lost.
- **State words for tasks, milestones and releases (T1002).** sage core now maps its 15 recorded task states to the six words that you see: not started, waiting, needs you, in progress, done and stopped. Each word comes with a short reason, for example the question that you answer or the task that it waits for. Milestones and releases get a word too: a release's word comes only from the words of its items. No board or status line shows the words yet; the presentation work uses them next.
  - "Needs you" comes from the same reasons that put a card in the board's Needs you box, so the word and the box agree. The approved design changes two cases, which the board shows later: a done or stopped task keeps its word, and a merge check that refuses a pull request's head is "in progress", because the chief repairs it.
- **Programs are now milestones (T995).** A group of tasks for one goal is a milestone now: `milestone propose`, `task <T> set milestone=<M>`, ids `M1`, `M2`, …, the status line `milestone M5 · …`, the board's Milestones tab (`/milestones`, `/milestone/<key>`), and the Codex tool `milestone_propose`. The word "program" keeps only its meaning of a computer program, and the dictionary now has a milestone row. The README and the docs say milestone.
  - Your logbook changes once, at the first write of this version. Each program gets the next free milestone number. This project's milestones 1 to 4 have no records, so its PG1 "Sage feel" becomes M5. A decision row such as `M5 was PG1` records each new number. An open breakdown gate gets the new first line, `Approve milestone M5? No task builds before you approve.`, and still takes one answer. Your old answers and the old decision rows stay as they are. Before that write, status and the board already show the milestones. When a write stops halfway, the next write finishes the change, with the same numbers.
  - When the old table of programs (`programs.tsv` in the logbook folder) is empty or has a damaged first line, the first write refuses and changes nothing. To repair it, restore that file from a copy. Or, to accept the loss of its programs, run `logbook repair --accept-loss programs`. When a logbook from before the rename lost another table, run the repair that the refusal names.
  - After that write, an older sage in another session stops writing this logbook and says that a newer sage wrote it: update sage in each Claude Code and Codex session. Its status and board still read the logbook, without milestones.
  - The chief command that gives up a task is `unclaim` now, in Claude Code and in Codex (the `unclaim` tool), so that the word "release" is free for the release level. A takeover question now says that a chief "unclaimed" the task last.
  - The old words `program propose`, `--program`, `program=` and `release` still work for one version, and each prints a note with the new word. An old id such as `PG1` names its milestone (`M5`) there, and the line names the new id. The board sends `/programs` to the new list, and an old milestone page `/program/<key>` to the page of its new id. A board tab that was open before the update keeps its live updates. Codex has no tool under the old names.
  - `gate add` refuses a question that starts with "Approve milestone" or "Approve program", because only `milestone propose` opens a breakdown gate.

## 2026-11-10

- **A pinned sage marketplace in Codex gets a warning and a fix (T971).** When your Codex config pins the sage marketplace to one commit (a `ref = "<commit>"` line under `[marketplaces.sage]`), `codex plugin marketplace upgrade sage` fetches the same commit, and `codex plugin add sage@sage` keeps the old copy. The start status and `hooks status` now say so, and give the 3 commands that end the pin: `codex plugin marketplace remove sage`, then `codex plugin marketplace add https://github.com/erickb336/sage-stack.git`, then `codex plugin add sage@sage`. A `ref` that names a branch gets no warning.
  - An install from before T957 has no `hooks` command, so its `hooks install` stops with `unknown command "hooks"`. The Codex guide ([Update and remove](docs/guide/codex.md#update-and-remove)) and the README now give the same 3 commands as the first step for such an install.
- **The gap rule also holds a lead's round, and a late report holds the lead in every logbook (T970).** This polishes the gap rule of T956.
  - A lead's `round` waits for the rows of its helpers' findings, as its state move does, because a round takes its fix keys from those rows.
  - The refusal names `finding add` and its fields (task, source, severity, run, class and summary), so a Claude lead and a Codex lead (`finding_add`) each read their own form.
  - The chief text says that a row of the run counts whoever records it, the chief too, but only with `--run`.
  - Decision: a run that ended as blocked or failed keeps its late report in a legacy logbook too, as in a shared one. Reason: one rule for every logbook is fewer rules, and the late report's findings then hold the lead, so a normal lead cannot go on past them because the chief ended the run first. `task <T>` prints the path of such a report in every logbook. A run that ended as done still keeps no late report.
  - Decision: the findings of a kept report of a blocked or failed run still hold the lead. Reason: the run's status says how the run ended, not whether its findings are true, and a rule that skips such runs adds a case. A row of the run frees the lead, and the chief can still dismiss the finding.
- **A Claude lead with no usage in its notice, and a count that stays (T969).** A lead that ends with a report (`done`, `blocked` or `question`) but whose notice has no usage, for example after a restart, could end only as `failed`. Now the chief ends it with its status and `--usage unavailable`, with `--usage-source`, `--usage-evidence` (the reason) and `--report`, as a Codex run does. A lead with no report still ends as `failed`, and a review run still needs its tokens. The commands reference and the chief's steps name the lead's `--tokens` rule and this way out.
  - At a later stop of the same Codex agent, a record that gives no count (for example a half-written last line) no longer replaces the count of an earlier stop with "unavailable". A new count still replaces the old one.
  - The Codex skill's limits line no longer says that a run has no token count (fixed by T956).
- **The test guard, and a correction of T944.** The T944 entry said that a test run from your checkout cannot reach your real `~/.sage`. That claimed too much: the guard covered only `os.homedir()` in the test's own process, and only for the home that the test started with. Now the guard also refuses the account's home from the system (for example after a test deletes HOME), and each `child_process` call of a test or of sage code whose env has no HOME. A child whose env has no HOME gets the account's home.
- **Limits of the test guard.** These forms pass it. Each needs code that works against the test on purpose, or a path known only at run time (order 70):
  - A child that inherits the real HOME, or gets it in its env, is not refused. Its code reads that HOME, so a test keeps SAGE_HOME and HOME in scratch (orders 53 and 54).
  - The guard does not run inside a child process, so a child's own `os.homedir()` is not guarded.
  - Code that reads the account's home without `os.homedir()` (for example `os.userInfo().homedir`, or `/etc/passwd`) is not refused.
  - A caller under any `node_modules` folder passes, also sage code that a test copies under one: the guard leaves out those folders for Playwright's browser cache.
  - Code that keeps a reference to `os.homedir` or a `child_process` function before the guard runs (a module that loads before `test-env.mjs`) is not refused.
- **In sage mode the chief no longer runs the git forms that throw away uncommitted work in the project, in Claude Code and in Codex, with one core rule (T968).**
  - `git reset --hard`, `git checkout -- .` and `git checkout -- <path>`, `git clean -f` in any form and `git restore` of the work tree are refused for the chief in the project's main checkout. The refusal says why, and names the safe way: make a scratch worktree in the temp folder and run the command there, or ask the owner.
  - In a scratch worktree (a worktree in the temp folder, outside the project's main checkout) they run, also when that worktree is the command's folder.
  - The chief's merge steps run as before: `git merge-tree`, `git commit-tree`, `git worktree add --detach` and `git worktree remove --force` of a scratch worktree. So do `git commit`, `git checkout <branch>`, `git fetch` and reads.
  - A correction of the T936 entry: the chief's git does not all run. `git rm` and `git mv` are write forms, so they were refused since T960, and now the forms above are refused too.
  - A reviewer whose folder is its own scratch worktree runs git there (F-T936-5). In Codex, a reviewer's shell refusal names the scratch-worktree command, as in Claude Code (F-T936-3).
  - awk's comparison in parentheses (`print ($1 > 3)`) and a print into `/dev/stderr` no longer count as a write (F-T936-1).

| Command | Decision | Reason |
| --- | --- | --- |
| `git reset --hard`, `git checkout -- .`, `git checkout -- <path>`, `git checkout .`, `git checkout --force <branch>`, `git switch --discard-changes` | Refused for the chief in the project; runs in a scratch worktree | They can destroy uncommitted work in the owner's main checkout. |
| `git clean -f`, `-fd`, `-xdf`, `--force` | Refused for the chief in the project; runs in a scratch worktree | They delete files that git does not track. A dry run (`git clean -n`, `-fn`) only reads, so it runs. |
| `git restore .`, `git restore <path>`, `--worktree` | Refused for the chief in the project; runs in a scratch worktree | They overwrite changes in the work tree. `git restore --staged <path>` changes only the index, so it runs. |
| `git merge-tree`, `git commit-tree`, `git worktree add --detach`, `git worktree remove --force` | Run | The chief's merge steps. Removing a scratch worktree is allowed. |
| `git commit`, `git checkout <branch>`, `git reset` without `--hard`, `git fetch`, `git log`, `git diff` | Run | They keep the work tree's changes, or git refuses to overwrite them. |
| `git rm`, `git mv` | Refused for the chief, as since T960 | They are write forms. The T936 entry said that the chief's git runs; that was not true for these two. |
| A disguised form: a git alias, a variable, a path without `--` (`git checkout HEAD src/a.js`), `git reset --merge`, `git checkout-index -f` | Runs: a documented limit | The rule guards honest mistakes (standing orders 49 and 70). |
| A reviewer's `git checkout main` with its own scratch worktree as its folder | Runs | That folder is outside the project's main checkout (F-T936-5). |
| `awk '{ print ($1 > 3) }'`, `awk '{ print "x" > "/dev/stderr" }'` | Run | A comparison and a print to standard error write no file (F-T936-1). `print > ("out" NR)` still counts. |
