# Changelog

This is the full list of user-facing changes to sage, newest first. The README has no list of changes: it links here.
Each date is the day of the first commit that made the change. Older changes are in the [git log](https://github.com/erickb336/sage/commits/main). In these entries, "the sage" is the chief, the main session in sage mode.

> **Warning:** before you use waits or programs, update sage and restart every session that was already open. An older session still merges a waiting task, or a task of a program that you did not approve. See [To update sage](docs/guide/using-sage.md#to-update-sage).

## 2026-10-26

- **The README shows How sage works, and the graphics match the code.** The README now has a How sage works section: the two loops, the chief, one lead for each pull request with up to 9 helpers, the agent caps (10 for each project, 20 in all), each task's priority, the routes and a task's life. Its Safety and limits section is gone: Learn more links [Rules held in code](docs/design/rules-in-code.md) and [SECURITY.md](SECURITY.md), which hold the limits, with the cost of agents in the [FAQ](docs/guide/faq.md). The Codex part of the Quick start names the 4 approval prompts of each task. The hero graphic says Claude Code and Codex. The loop graphic shows that the chief runs the design and the PE check, and one lead runs the build, the reviews and QA. The graphic of a task's life shows that findings in review and a QA fail both start a repair, that a task is held after 3 rounds by default, and the other states. The FAQ now says what works in Codex. The Quick start gives each update and Codex install command in its own block.
- **A clean merge of main keeps the reviews.** When a pull request's new head only merges main into the reviewed head, and main's side is in the pull request's base commit on GitHub, the merge check now keeps that head's review and QA verdicts, so the task needs no fresh cycle. CI still runs: record `checks-pass` on the new head. The pull request's diff outside built files must be the same as the reviewed one, so a merge whose only conflict is in a built file, fixed by `npm run build`, counts too; any other change refuses and says why. A file that both sides changed refuses, also when git merges it with no conflict. Apart from the base commit, the merge check reads only git objects (no replace refs), names the earlier head, and writes the carry-over in the decision trail. A built file is one that main's `.gitattributes` marks `sage-built`; in sage, `npm run build` now writes `.gitattributes` from the files that it makes. The Claude Code hook and the Codex merge rule both use it. See [the design](docs/design/sage-mode.md#carry-over).

## 2026-10-25

- **A lead's wait no longer returns at once in a loop.** When a review or QA helper stopped with a report that the hook cannot read and another helper still ran, the lead's wait command returned at once each time, and the lead could not end that run: only the sage does. Now the wait leaves out such a run: it names the run once, with what to do, and waits for the helpers that still run, up to its 9 minutes. When no helper runs, it returns with the list of these runs. The lead names each one in its report as a gap, and ends blocked only when no helper of its own runs. The text of the hook that blocks a lead's stop now says when the wait returns.
- **The Codex guide names the 4 approval prompts of each task.** With autopilot on in Codex, each task still asks you before 4 commands: create the task worktree, commit, push the task branch and open the pull request. Codex asks, because its `workspace-write` sandbox keeps `.git` read-only and the network off; the verified merge asks nothing. The [Codex guide](docs/guide/codex.md#the-approval-prompts-of-each-task) gives Codex's own choices, quoted from its source. It tells you to choose "Yes, proceed" at each of the 4 prompts, every time, and never "don't ask again" at any Codex prompt: each command runs git, and git can run the project's own code outside the sandbox. sage writes no Codex rule and changes nothing in your Codex config.
- **The Codex chief ends each run on the first try.** Codex gives no token count for an agent, so the state tool ends such a run only with `usage` unavailable, `usage-source`, `usage-evidence` and `report`, and no `tokens`. The chief learned these fields only from a refusal, and until then the open runs held the merge. Now the `run_done` tool's description and the chief's dispatch step name each field and give an example call. The Codex chief cannot write the pages folder from its sandbox, so the `pages` tool now saves a run's report itself: give it the task, the run and the report as `text`, and it saves `<R>-report.md` in the task's pages folder, records it, and prints the path for `run_done`. It refuses an empty report and a run of another task, and it never replaces a saved report. The CLI form is `sage pages <T> record --run <R> --text <report>`. The rule of `run done` did not change.
- **Two speed tests of the hook no longer fail on a slow machine.** The 1 MB padding test compares the time of 1000 KB with the time of 100 KB on the same machine, and its only fixed cap is the hook's own 10 s budget: a fixed 2 s cap failed a correct hook on a slow CI runner. The path work tests count filesystem calls as before, but no fixed 120 s timeout kills their child: the test's own timeout stops a hang, and each input shape is now a test of its own.
- **Every task has a priority.** `task add` (and the Codex `task_add` tool) now refuses a task with no priority or a bad one, writes nothing, and says the scale in one line: P0 the owner's current focus and what blocks it; P1 next (function or safety bugs, work in flight, pre-pilot items); P2 later (polish, hardening lows, follow-ups); P3 parked but kept. `task <T> set priority=none` no longer clears the priority of an open task; an ended task's still clears. A follow-up task of `finding move` gets P2. Older open tasks with no priority still work: `show status` names them on a `priority` line, and their board cards show a "no priority" tag, so that the chief sets one.
- **A task moved off a shared pull request's branch gets a way back that works.** When two tasks share one pull request and the chief moves one of them to another branch, the merge check still refuses that pull request. Its refusal now gives the command that puts the task back on the head branch (`task <T> set branch=<the head branch>`), and first the same command for the task whose name the branch carries, when no task names the branch by its `branch=`. Before, it said to rename the branch to a task name, which leaves the other task behind. A head branch that is the branch of no task still gets the rename advice. The sage hook now also refuses a lead's `run add` on a branch that another task uses after the chief moved the lead's task off it, and the refusal names that move.
- **The chief's rules in Codex have room to grow.** Codex counts a hook's text at 4 bytes a token and cuts it above the hook's limit. The two native parts of the chief text now use Codex's real limit of 10000 bytes each, where sage used 7500, so a small change to the chief's rules no longer refuses them. `npm run check` now fails, with the size and what to do, when the chief text does not fit the sage hook or the native parts.
- **One change log file for each pull request.** A pull request now writes its change log entry in its own file, `changes/<task>.md` (for example `changes/T492.md`), with the date and the list item. `npm run build` puts the entries into this changelog, newest date first, and `npm run check` fails when this changelog is not what the build makes. So the entries of two pull requests no longer conflict as text: a conflict in `CHANGELOG.md` is now only in a built file, and `npm run build` ends it. The build stops, and writes nothing, when `changes/` holds a file that is not a `.md` file or when `CHANGELOG.md` holds a line that you wrote by hand, in any form; its message names the file or the line and says what to do, so no entry drops without a message. See [CONTRIBUTING.md](CONTRIBUTING.md#the-readme-and-the-docs).
- **Every review and QA finding names its run and class.** `finding add` (and the Codex `finding_add` tool) now refuses a finding whose source is a review or QA role (code-reviewer, security-reviewer, ux-reviewer, qa or evidence-review) without `--run` and `--class`, and the refusal names the classes. A known key that opens again keeps its run and class. A finding from another source, such as the sage's own note, may still leave them out. So `sage stats` can count review findings by class and by cycle from now on; older rows do not change. The sage's finding for a failed CI check names the task's lead run and the class other.
- **A lead waits for its helpers, keeps its slot, and runs up to 9 helpers.** The sage hook now blocks a lead's stop while one of its helpers runs, and names the lead's new wait command (`node <plugin>/hooks/wait.mjs <T>`). That command needs only Bash: it returns when a helper stops, with the RESULT that the hook kept from its report; for an implementer, its RESULT word and the head that it left on the branch, so that the lead ends its run and starts the reviews there. A lead's slot holds while its lead run runs, however long it waits, in the session that started it. After a restart or a crash, a new session starts a fresh lead for the task: the old session's lead slot frees after an hour with no event of that lead or its helpers, or at once when the sage ends the old lead run and records a new one. The sage's `run done` of a helper run frees that helper's slot at once, also after a restart and a fresh lead's start, and a lead whose lead run the sage ended may stop while its helpers run. A lead runs up to 9 helpers at once (before: 3), within the project's agent cap, and a refusal at a cap names the lead's wait command. The default caps are now 10 agents for each project (`max_agents`, before: 4), so one lead and its 9 helpers fit, and 20 in all (`cap_total`, before: 12); a value in `config.json` still wins. The hook now refuses a lead's checks verdict, the sage's message to a lead that ended (start a fresh lead), and the sage's review or QA verdict on a task with a running lead run unless a finished run of that task, of the role that gives the kind, backs it with its helper's kept report.

  - Not blocked, and written in the guide's limits list: a role agent's start of Codex through text or a script piped into a shell or an interpreter, through a copy of codex (made in the same command or an earlier one), through a link to codex made in the same command, or through text that hides the word codex; and an agent's run of the state tool's write commands from `node -e`, `node -` (standard input), after a `node` option, as a module to load, or from a copied script.   - A `node` script whose name only has the state tool's name in it (`node src/message.mjs`), or that gets the tool's path as data (`node scripts/lint.mjs <tool>`), runs again for every agent. So do normal commands that name codex, such as `~/bin/tool codex`, `pushd packages/sage-codex && ../../node_modules/.bin/esbuild …` and `cat codex.json | python3 -mjson.tool`.
  - The brief tool's message now names each field form that the check takes: a colon, two spaces or a tab after the name, or the name alone on its line.
  - The brief check now starts a field only at a line that is the field's name with a colon (`FORBIDDEN:`), two spaces or a tab after it, or nothing, outside a list or a code block. So a line such as "FORBIDDEN words are flagged" in another field no longer gives a role agent the wrong `FORBIDDEN` text.
  - The chief's setup text in Codex now says that the state CLI only reads (`board`, `config`), and that `program` has no tool yet, so programs do not run in Codex. The limits that stay are in [sage in Codex](docs/guide/codex.md#the-rules-in-codex).

## 2026-10-19

- **Review data for each task.** A finding can name the run whose report holds it (`finding add --run R<n>`) and its problem class (`--class`: state-edge, speed, copy, layout, security or other).
